## 二、核心架构

### 2.1 系统分层（【方案 A】为准，【方案 B】为其前置决策版）

**业务维度：四层优先级漏斗（P0–P3）**

| 层级 | 名称 | 典型规则 | 判断方式 | 来源 |
|---|---|---|---|---|
| P0 | 法务合规红线 | 医疗功效宣称、绝对化用语、未使用安全座椅、儿童独留车内、未授权肖像、AI 内容未标识 | **确定性拦截**：词表／正则／变体命中即驳回，**不交给模型推理** | A §2.2 |
| P1 | 安全与准确性 | 喂养姿势、辅食月龄、安全座椅安装、产品功能边界 | 语义理解 + 规则辅助 | A §2.2 |
| P2 | 通识与常识 | 场景不符合常识、模特月龄不匹配、AI 素材背景细节错误 | 多模态推理与常识判断 | A §2.2 |
| P3 | 措辞与表达 | 品牌语气不一致、用词不精准、可优化表述 | 只出建议，**不改变结论** | A §2.2 |

**工程维度：L0–L7 八层知识底座（【方案 A】§07）**

| 层 | 名称 | 职责 | 主要产物 | 铁律 / 不许做什么 |
|---|---|---|---|---|
| L0 | 原始库 | 把源侧对象登记下来，算出确定性指纹，供后续层做变更判定 | `manifest.jsonl`、`index/l0.jsonl`、`records/`、`registry/kb.json` | **全程只读**；不解析正文、不切分、不判定业务域；分类只靠重跑，**不许手工挪文件或改名** |
| L1 | 文本抽取层 | 从台账抽出「带位置的文本段 + 表格行 + 媒体文本」，图片走 OCR | 资源 json（`segments`／`tables`／`media_refs`）、`index/l1.jsonl`、锚点 | 锚点必须来自原文物理位置，**不得编造**；定位不到就进「无法定位锚点」清单 |
| L2 | 单元化层 | 把抽取结果切成最小可用单元 | `units.jsonl`（约 9,400+ 条） | 按「有没有文本内容」取数，**不按状态字段白名单筛**（历史状态有误标） |
| L3 | 蒸馏层 | 把单元归纳成**一句可判定的结论**（规则），或逐字保留的条款与案例 | `rules.jsonl`、`sample_cases.jsonl`、`scoped_clauses.jsonl`、`rejected.jsonl` | 两道过滤闸门：只保留「文案／表述类」字段产生的单元；质量标记非空的排除。源侧材料未通过的，不许产出规则 |
| L4 | 定稿与发布层 | 给每条定稿记录发一个**永久条款号**，写入定稿文件 | `l4/canonical/*.jsonl`（1,242 条）、`registry/l4.json` 台账 | 号码一经发出**永久占用、不回收**；排序只用规则自身的不变量（不用热度、时间、行序） |
| L5 | 确定性匹配层 | 红线层词表／正则／变体匹配，毫秒级命中即拦 | `p0_patterns.jsonl`、`matcher.py` | 每条词都要有出处（逐字来自源／逐字来自规则原文／等价写法三选一）；对不上的判为凭空，不进匹配表，并单独留痕 |
| L6 | 召回层 | 关键词检索为主、语义向量补召 | BM25 索引 + 向量索引 + `retriever.py`、基准测试 | 默认以关键词检索为主；**门限只用原始分**，不用归一化融合分 |
| L7 | 消费侧 | 输出契约、三态模板、交付 skill 与自检 | `output_template.md`、`kb-content-review` skill、阶段自检 | **引用不到本地锚点的结论，一律不输出**；责任人从配置读，不写死人名 |

> 注：`kb-content-review` skill 的自我描述写的是「知识库（L0–L6）」，【方案 A】正文写的是「L0–L7 八层架构」。**文档之间存在口径不一致，未在任何一份文档中解释**。

**源侧材料来源**（A §05）：飞书多维表、飞书文档、NAS、官网政策页、法规原文。

### 2.2 数据流 / 流水线

#### （a）审前主流程（【方案 A】§01，图 1 还原）

```
送审素材（内容 + 品线 + 渠道 + 送审版本）
  │
 ①检测启动 ── · 完成格式、产品线、产品型号属性匹配
  │           · 语义识别 ＋ 检索定位知识库规则（知识库侧先出候选规则）
  │           → 属性匹配完成
  ↓
 ②OCR 识别 ── · 仅针对图片类内容，识别文字内容、校验文字排版位置合规性
  │           · 抽取结果**两侧共用**
  │           → OCR 识别完成
  ↓
 ③知识库 ＋ 大模型 双校验 ── · 知识库规则作为上下文输入大模型，完成二次合规校验
  │        ├─ 命中 P0 规则 → 命中 P0 红线 → 触发流程阻塞 → 直接返回违规结果（红线零延迟，不等其余层）
  │        └─ 未命中 P0    → 非致命问题 → 纳入待 review 清单（不中断后续流程，继续跑完其余层）
  ↓
 ④结果合并输出 ── · 全量输出知识库与大模型识别的所有问题，无遗漏覆盖全部风险
                  合并方式：同一个问题 → 取交集 ／ 不同的问题 → 走并集
                  → 单一三态 ＋ 完整清单
```

**④ 的两条硬约束**（A §01）：① **全量输出**——两侧识别的所有问题都要出现在清单里，不许因为另一侧没提就丢掉；② **无遗漏**——两侧都没覆盖到的主题不许给 PASS，那是「没查到」不是「没问题」。

#### （b）双校验内部：四层 × 两侧全并行（【方案 A】§02，图 2 还原）

```
送审素材（内容 ＋ 品线 ＋ 渠道 ＋ 送审版本）
   ├── P0 层 法务合规红线
   │     知识库侧：词表／正则／变体 → 命中带 条款号＋锚点＋指纹
   │     模型侧  ：语义核查与边界判断 → 命中带 位置与理由（无库内依据）
   ├── P1 层 安全与准确性
   │     知识库侧：条款与边界规则 → 条款号＋锚点＋指纹
   │     模型侧  ：语义理解 · 危险示范 → 位置与理由
   ├── P2 层 通识与常识
   │     知识库侧：正负样本 · 案例 → 条款号＋锚点＋指纹
   │     模型侧  ：多模态推理 · 画面 → 位置与理由
   └── P3 层 措辞与表达
         知识库侧：Do not say 词表 → 条款号＋锚点＋指纹
         模型侧  ：语境判断 · 建议 → 位置与理由
        ↓（四层同时启动，层间互不等待；层内两侧也互不等待）
   合并两张问题清单
        同一个问题 → 取交集（两轨都命中 → 双轨确认）
        不同的问题 → 走并集（单轨命中 → 全部保留）
        ↓
   单一三态结论 ＋ 完整问题清单      BLOCK ＞ REVIEW ＞ PASS
   P0 命中时可立刻返回 BLOCK（红线零延迟），其余层结果收齐后再并入清单
```

#### （c）合并规则矩阵（【方案 A】§03）

| 情形 | 合并方式 | 三态怎么定 |
|---|---|---|
| 两轨都命中**同一个问题**，结论一致 | 取交集 | 按该问题严重度计入（BLOCK／REVIEW）——双轨确认，置信最高 |
| 两轨都命中**同一个问题**，但结论不一致 | 交集冲突 | **降为 REVIEW**，连同两侧依据一起转人工——不许任一侧单独定案 |
| 只有知识库侧命中 | 走并集 | 按其严重度计入；带条款号／锚点／指纹，可回源 |
| 只有模型侧命中 | 走并集 | 保留在清单里，标注**无库内依据**；倾向 REVIEW，**不由它单独定 BLOCK** |
| 两侧都没发现问题，且两侧都覆盖到该主题 | 取交集 | **PASS——这是 PASS 唯一的成立方式** |
| 任一侧没覆盖该主题（拒答） | 交集不成立 | **拒答，不得输出 PASS** |

对齐规则：**位置相同 ＋ 类目相同** → 视为「同一个问题」。

## 三、技术决策与参数

### 3.1 分层知识库设计

#### 四类知识库 + 未归类暂存区（A §2.1）

| 知识库 | 装什么 | 主要支撑的判定 | 资源登记数（L0 口径） |
|---|---|---|---|
| 外部标准库 | 美国法规、平台政策、行业标准、医学共识、本地常识 | 法务合规红线、安全与准确性 | **55** |
| 内部正负样本库 | 正面：合规优秀内容；负面：投诉、下架、警告、返工、达人争议、审核争议 | 红线、安全准确、通识常识 | **7** |
| 措辞表达库 | Do not say / Say this instead、禁用与慎用表达、中英对照、修订对 | 红线、措辞与表达 | **301** |
| 产品描述库 | 功能边界、型号差异、允许／禁止描述、认证参数、常见误解 | 安全与准确性、通识常识 | **4** |
| 未归类（不猜） | 暂未判定归属的材料，等待重跑归类 | 不参与判定 | **37** |
| **合计** | | | **404** |

分类由规则判定，**不靠人工挪文件**；「未归类（不猜）」是暂存区。

#### P0–P3 各自的库覆盖（B §01，引 PRD 7.1）

| 层 | 谁主判 | 依据来自哪几类知识库 | 结果 |
|---|---|---|---|
| P0 | **知识库**（规则引擎，不用模型） | 措辞表达库 ＋ 外部标准库 ＋ 内部正负样本库 | 命中 → BLOCK，停止后续 |
| P1 | 模型主判，知识库辅助 | 外部标准库 ＋ 内部正负样本库 ＋ 产品描述库 | BLOCK／REVIEW |
| P2 | 模型主判（多模态），知识库辅助 | 内部正负样本库 ＋ 产品描述库 | BLOCK／REVIEW |
| P3 | 模型主判，知识库供参考 | 措辞表达库（Do not say / Say this instead） | 仅建议，不改三态 |

> 措辞表达库**同时覆盖 P0 与 P3**：能写成关键词／正则的进 P0 由规则引擎判，要读语境的进 P3 由模型生成。

#### 入库判据与知识形态

**六种规则形态，分两类**（A §08）：

*4.1 规则形态（套「支持度」口径）*

| 形态 | 来源 | 产出形态 |
|---|---|---|
| `entry` 词条／命中片段型 | 措辞表达库词条 | 禁用表达 + 建议替换 + 依据 |
| `revision_pair` 修订对型 | 修订记录 | 一对修订 = 一条规则（原表述 + 修订后 + 原因） |
| `revision_cluster` 成簇归纳型 | 按修订原因成簇 | 支持度 ≥2 的归纳型规则 |
| `boundary` 边界内容型 | 品线内容边界规则库 | 边界内容 + 触发词 + 豁免 + 建议表达 |
| `saythis` 建议表达型 | 卖点表达边界 | 建议表达 + 限定要求 + 判定理由 |

*4.2 非规则形态（不套支持度，用依据充分性表达）*

| 形态 | 是什么 | 为什么不套规则口径 |
|---|---|---|
| `scoped_clause` 条款 | 一条法规／政策条款或一项登记元数据，**逐字保留**（原文、阈值、词表、生效期、锚点、指纹） | 条款是「判定条件 + 阈值」，不是「命中 → 替换」；强行改写会丢掉原文语境 |
| `sample_case` 案例 | 一条正负样本 = 一个案例（正例→应该怎么做；反例→不能这么做 + 为什么） | 案例是参照，不构成规则；依据充分性用证据强度表达 |

**依据充分性怎么表达**：规则类——支持度 = 1 标「待验证」，≥2 标「已支持」。非规则类——用证据强度表达（**观测 / 归纳 / 推断**）。**两个口径不能混用**——把推断写成观测事实，是这类库最常见的失真方式。

**L3 两道过滤闸门**（A §07）：① 只保留「文案／表述类」字段产生的单元；② 质量标记非空的排除。源侧材料未通过的，不许产出规则。

**入库 / 变更原则**：L0 只读、改动靠「标记」而不是「删除」——删文件会破坏指纹与既有对账基线；来源被业务判定不可用时，在 L0/L1/L2 打排除标记，由 L3 在输入过滤时跳过并单独计一个排除原因（**可逆、可审计**，将来解禁也能重跑恢复）。

**L2 取数原则**：按「有没有文本内容」取数，**不按状态字段白名单筛**（历史状态有误标，会把已完成产物当待处理跳过）。

### 3.2 规则/条款编号体系、锚点、指纹、版本、半衰期

**条款号格式**：`<库前缀>-<形态段>.<序号>`，例如 `W-2.137`（A §5.1）

| 库前缀 | 对应知识库 | 形态段 | 对应形态 |
|---|---|---|---|
| E | 外部标准库 | 1 | `entry` 词条型 |
| S | 内部正负样本库 | 2 | `revision_pair` 修订对型 |
| W | 措辞表达库 | 3 | `boundary` 边界内容型 |
| P | 产品描述库 | 4 | `saythis` 建议表达型 |
| X | 未归类（**不得分配号码**） | 0 | 未登记形态 |

- 每类库**各自一套编号，不全局连号**。
- 号码一旦发出**永久占用**：重跑时已在册的沿用原号，新规则取该段下一个号；某条规则后来消失了，它的号码**也不回收**、不再发给别的规则。
- 排序**只用规则自身的不变量**（不用热度、时间、行序），避免增删导致已发号码错位。

**版本：两层号，不要混成一个字段**（A §5.2）

| 字段 | 含义 | 例子 |
|---|---|---|
| `kb_version` | **每类库独立**的版本号 | `external_standard: v3` |
| `release_id` | **组合发布号**，跨库一次性发布 | `rel-0007` |

- 原始库阶段两者都不产生（版本号恒为 `v0`）；**当前库处于 v0 试用版、未发布**。
- 发布时把「知识库版本 + 规则版本 + 模型版本」三者绑到**每条审查记录**上，做到可回放、可追溯、可回滚。

**锚点**（A §13）：必须来自原文的物理位置（**页码、标题路径、单元格、时间戳**等）；定位不到就进「无法定位锚点」清单，**不许猜**。实例锚点形如 `#广告文案明细/recvuJYdOb1fOj/命中片段`（A §15）。

**指纹**：`source_sha256`（引用契约必填）；L0 层算确定性指纹供后续层做变更判定。图片素材另带 sha256 前 12 位，如 `894c0edc84a736a8…`（A §15）。

**半衰期**：**三份文档均未提及「半衰期」（half_life）这一机制**，也未见 `valid_until`／有效期字段。文档未提。

**抓取层回验闸门**（A §13）：抓来的条款，其摘录必须能在抓取的正文里**逐字命中**；命中不了的不入库。这条是针对「页面脚本被当正文收进来」的事故加的闸门。

**非规则层支持度/证据强度不可混用**（A §08，见 3.1）。

### 3.3 模型选型与多模态处理

**模型选型**（A §15 / B §06 读法）：两轨产出模型**都是 `deepseek-flash`**（会话留痕核实为 `deepseek-official / deepseek-flash`，4 个会话共 **560 条有正文的回答**）。评测设计上**唯一变量是「有没有走知识库」**；图片／视频类另有第三个变量——**图上文字由谁读**。

| 变量 | 模型轨 | 知识库轨 |
|---|---|---|
| 产出模型 | `deepseek-flash` | `deepseek-flash` |
| 图上文字识别 | 自带**多模态视觉直读**（**无指纹**） | **macOS Vision OCR**（带指纹、可复现、能回源），引擎版本 `vision-jxa-2.0`（v2 起） |
| 证据 | 自然语言理由 | 条款号／锚点／`source_sha256`／逐字摘录 |

**多模态处理方式**

- **OCR**：只做**图片类**内容（A §01 ②），识别文字内容 + 校验文字排版位置合规性；**抽取结果两侧共用**（A §01）。
- **视频**：字幕／旁白 + 关键帧 + OCR 的判定路径**已设计但缺视频样本验证**，属「设计完成、待验证」（A §14）；视-1 实际送审对象是一份飞书文档（24,830 字符、9 张表，含 Draft V1–V4 + Script1–2 共 6 个「要发布的东西」），**不是真实视频文件**（A §15 / B §06）。
- **画面类维度**：构图、水印、logo 锁版、肖像、比例、裁切、场景合理性 —— 归 P2，由多模态模型执行（A §02 / B §02）。

### 3.4 裁决语义（PASS / REVIEW / BLOCK / 拒答）

**三态 + 拒答**（A §2.3 / B §01）

| 结论 | 含义 | 动作 |
|---|---|---|
| PASS | 未发现已知底线风险 | 转 sign-off 责任人确认 |
| REVIEW | 需要进一步判断（语境、专业口径） | 建议转法务／医学／专家／北美复核 |
| BLOCK | 命中明确红线，必须修改 | 返回内容方修改后重新提交 |
| **拒答** | **不是第四态，是没有结论**：检索不到可作依据的条目 | 给出检索轨迹；**不得输出 PASS** |

**优先级**：`BLOCK ＞ REVIEW ＞ PASS`——**只降不升**（B §01 依据 4，引 PRD 6.3 执行规则 4「多条规则同时命中时按最高优先级输出」）。

**PASS 的成立条件（最关键的一条）**

- 【方案 A】§03：**PASS 必须是交集——两侧都说没问题才算过**。
- 【方案 A】§10：PASS 要求知识库**认识这个主题**（命中允许表述，或检索到的材料确实被规则引用过且分数足够高）；两条都不成立 → 走拒答。**无命中只表示「没检索到依据」，推不出「合规」**——规避型文案本来就绕开字面。
- 【方案 B】§03：**PASS 权只给知识库层 · 模型层只许降级**；模型层的判断一律不得输出 PASS，拿不准就降成 REVIEW。
- **拒答 ≠ 放行**（B §04 必读）：拒答是「库不认识这个主题」，不是「库认为它合规」。

**PRD 6.3 的四条执行规则**（B §01，仅方案 B 引用）

1. P0 命中即停止后续审查 →「命中即停」的出处；
2. P1 与 P2 可并行 → 允许的是**层内并行**；
3. P3 只出建议、不改结论；
4. 多条命中按最高优先级输出 → BLOCK ＞ REVIEW ＞ PASS，即「只降不升」。

**置信度如何表达**：引用契约要求标「判定：事实／推断 ｜ 置信度：高／中／低」（A §11）。**三态的具体数值阈值、置信度的量化口径，文档未提**；只给了检索侧的分数门限（见下）。

### 3.5 检索门限与参数（A §6.1）

| 项 | 取值 | 依据 |
|---|---|---|
| 关键词检索门限 | **原始分 ≥ 8.0** | 落在两组实测分数的重叠区之间，取偏保守值 |
| 语义补召门限 | **余弦 ≥ 0.60** | 实测该值是唯一能把无关组全部挡在外面的取值 |
| 「够格当依据」的附加条件 | 还必须**同时命中规则层** | 单靠分数不够——两组分数实测有重叠，光看分会把无关内容当依据 |
| 覆盖门限（判 PASS 的前提） | **检索分 ≥ 16.0 或命中安全词** | PASS 必须建立在「知识库认识这个主题」之上，不是「没查到问题」 |
| 检索模式 | 关键词为主，语义为补 | 实测同一批查询上关键词检索的准确度高于等权融合，中文侧尤其明显 |

### 3.6 输出契约

**一条结论的依据必须包含**（A §11，硬门禁）

```
《<库名> <版本>》第 <条款号> 条（链接：<url>）
锚点：<anchor>　｜　指纹：<source_sha256>
逐字摘录：「……原文照抄……」
判定：事实／推断　｜　置信度：高／中／低
```

| 必须带 | 禁止 |
|---|---|
| 库名（不许自造库名）、版本、条款号、锚点（原文物理位置）、来源指纹、逐字摘录 | 只给锚点不给指纹／转述、概括、润色摘录／裸链接当依据／引用不存在的库名／引用不到本地锚点仍输出结论 |

**按问题数量分流**（A §12）

| 结论 | 问题数量 | 输出方式 |
|---|---|---|
| PASS | — | 一句话总结 + 转 sign-off 责任人（前置条件：知识库认识该主题；不成立则拒答） |
| REVIEW | 1–2 | 逐条：类别-子类 + 位置 + 引文 + 原因 + 依据 + 锚点 + 判定 + 置信度 |
| REVIEW | ≥3 | 分类汇总（各类问题数）+ 报告链接 + 建议转对应复核人 |
| BLOCK | 1–2 | 逐条：同上 + 修改建议 |
| BLOCK | ≥3 | 分类汇总 + 报告链接 + 请修改后重新提交 |
| 拒答 | — | 必须给检索轨迹：查了什么、用了哪几种模式、为什么判断没依据、无命中说明原文 |

> 分界理由是「**3 个及以上问题超出人能快速浏览的范围**，逐条展开反而增加负担」。

**受控词表**（A §12）：分类不能自造。对齐 PRD 的 **9 大场景域**（车内场景／功效宣称与广告用语／喂养场景／人物肖像与 AI／睡眠场景／洗护与沐浴／出行与户外／居家与用电／玩具与玩乐）与 **7 类一票否决项**（车内安全座椅类／医疗功效宣称／绝对化用语／无依据销量排名／危险行为示范／未成年人未授权出镜／AI 内容未标识）。出现词表以外的类别，记为「未分类」并写进报告，**不许现编一个**。

**责任人写成角色位，不写死人名**（A §12）：输出里的 @ 对象是角色（sign-off 责任人／复核责任人／内容方修改责任人），取值从配置读；未配置时保留角色名并标注「未配置」。

- **A 是定稿文档**：`v1.0`，文末明写「**本文档合并了两份同属「内容治理 Agent 开发方案」的材料：《双轨跑法建议 v14》（审查怎么跑）与《知识库框架说明 v0》（依据从哪来）**」。
- 所以 A 与 B 不是两个并行方案，而是**A = B（审查链路）+ 新增长期架构（知识底座 L0–L7）**，且 A **在合并时改了 B 的核心合并语义**。

- **S9**：跨文档引用、法规废止关系、上下位法关系**目前都没有建模**；`GRAPH_NODES`/`GRAPH_RELATIONS` 为死代码。
- **S11**：**没有配额与限流**——「一旦开放给外部 Agent 循环调用，这就是第一个会出问题的地方」。

## 六、对「多模态内容审核 Agent」最重要的硬事实清单

1. **审查链路是「四层 × 两侧」全并行**：P0–P3 四层同时启动，**每层都同时开知识库侧和模型侧**，层间互不等待、层内两侧也互不等待；P0 命中可立刻返回 BLOCK（红线零延迟），其余层结果收齐后再并入清单。（A §01、§02）
2. **知识库规则不是外挂，是喂给模型的上下文**：第 ③ 步原文是「知识库规则作为上下文输入大模型，完成二次合规校验」——模型拿到的就是知识库检索出的候选规则，做的是补等义句、补画面、补语境。（A §01、§02）
3. **合并规则：同一问题取交集、不同问题走并集**；对齐判据是「**位置相同 ＋ 类目相同**」；两轨结论不一致 → **降为 REVIEW** 并转人工，不许任一侧单独定案。（A §03）
4. **PASS 只有一种成立方式：两侧都覆盖到该主题且都没发现问题**；任一侧没覆盖 → **拒答，不得输出 PASS**。「没命中」推不出「合规」。（A §03、§10）
5. **只有模型侧命中的问题不许单独定 BLOCK**——保留在清单里但标注「**无库内依据**」，倾向 REVIEW。（A §03）
6. **拒答不是第四态，是没有结论**；拒答必须给检索轨迹（查了什么、用了几种模式、为什么判断没依据）；拒答 ≠ 放行。（A §2.3、§12；B §04）
7. **输出按问题数量分流**：1–2 条逐条输出（类别-子类 + 位置 + 引文 + 原因 + 依据 + 锚点 + 判定 + 置信度）；**≥3 条改为分类汇总 + 报告链接**，理由是「3 个及以上超出人能快速浏览的范围」。（A §12）
8. **引用契约是硬门禁，格式固定 4 行**：`《<库名> <版本>》第 <条款号> 条（链接：<url>）` / `锚点：<anchor>｜指纹：<source_sha256>` / `逐字摘录：「……」` / `判定：事实／推断｜置信度：高／中／低`；禁止裸链接当依据、禁止转述概括、**引用不到本地锚点一律不输出**。（A §11）
9. **条款号是永久占号**：格式 `<库前缀>-<形态段>.<序号>`（如 `W-2.137`），`E`=外部标准／`S`=内部正负样本／`W`=措辞表达／`P`=产品描述／`X`=未归类（**不得分配号码**）；号码一经发出永不回收，排序只用规则自身不变量（不用热度、时间、行序）。（A §5.1）
10. **版本是两层号，不能混**：`kb_version`（每类库独立，如 `external_standard: v3`）与 `release_id`（跨库组合发布号，如 `rel-0007`）；发布时把「知识库版本 + 规则版本 + 模型版本」三者绑到**每条审查记录**上。（A §5.2）
11. **检索门限四个硬数字**：关键词检索**原始分 ≥ 8.0**；语义补召**余弦 ≥ 0.60**；「够格当依据」还必须**同时命中规则层**；判 PASS 的覆盖门限是**检索分 ≥ 16.0 或命中安全词**。检索**以关键词为主、语义为补**（实测关键词准确度高于等权融合，中文侧尤其明显）。（A §6.1）
12. **取依据有固定顺序，前面的能定论就不往后走**：① 红线确定性匹配（词表／正则／变体，毫秒级）→ ② 规则层（按库 + 关键词找已定稿规则）→ ③ 单元层（关键词为主 + 语义补召）→ ④ 原文层（按锚点回原始材料核对）。（A §10）
13. **多模态分工写死在 PRD 层**：P2 通识常识层由「**大模型语义理解 + 视觉识别（多模态）**」执行；画面、构图、水印、logo 锁版、肖像、比例、裁切全部落在这层，**知识库在 P1／P2 只是辅助**。（B §01、§02）
14. **两条轨的读图方式不同，这是评测里的第三个变量**：模型侧用自带**多模态视觉直读（无指纹）**，知识库侧走 **macOS Vision OCR**（引擎 `vision-jxa-2.0`，**带指纹、可复现、能回源**）；**OCR 只做图片类内容，抽取结果两侧共用**。（A §01、§15；B §06）
15. **OCR 对输入版本极度敏感**：图-4 副本 3 处 vs 库内原件 2 处——`IBCLC` 被读成 `IBCC`（丢一个 L）、`$199` 读成 `$19`，**一个字符就让一条命中消失**；修法是「素材固化到带指纹的单一版本 + 关键 token 回原图局部复核」。（A §16 #5）
16. **OCR 的输入格式只覆盖 `png／jpg／jpeg／webp／gif`，PDF 未覆盖**——扫描件 PDF 走不进管线，等于一条无审查通道；修法是补 PDF→图→OCR，放在 PRD 14 的 W3。（A §16 #9）
17. **视频能力「设计完成、待验证」**：字幕／关键帧的判定路径已设计，但**缺视频样本来验证**；唯一的「视-1」案实际送审对象是一份飞书文档（24,830 字符、9 张表、6 个「要发布的东西」），不是真实视频文件。（A §14、§15）
18. **画面类问题 100% 落在知识库覆盖之外**：4 个图片案里知识库侧**一次 PASS 都没给出过**，全部返回拒答；图-1/2/3 三案**两轨零重叠**，且这三案的问题「**此前是被拒答掩盖掉的**」。**知识库轨回答的是「语言宣称有没有越界」，不回答「这张素材能不能用」。**（A §15）
19. **当前唯一的瓶颈是知识库只蒸了一类**：509 条规则**全部出自措辞表达库**；外部标准库、正负样本库、产品描述库**暂无规则**；而 P1／P2 的库辅助当前**实际是空的**，只有模型在跑。**改法是把规则蒸出来，不是改流程**——两个阶段跑同一套流程、合并规则完全不变。（A §14、§04；B §04）
