## 3. 失败项 + 原因码 + 要人做什么

### 3.1 ★ 主问题：15:50 那次重建把 L4 台账打坏了（733 个号从唯一台账里消失）

`kb/l4/registry/l4.json` 被 `l4_article.py:200` **从零重建**（`reg = {...}` 整块新造，不是增量合并）。而该脚本只读 `kb/l3/candidates/rules.jsonl`，所以它重建出来的台账**只装得下 W-1/W-2 两段**。

对照证据（备份 `kb/l4/_pre-rebuild-20260930-1550/l4.registry.json.bak`，sha `7d53459a…`，已记进同目录 `SHA256SUMS`）：

| 字段 | 重建前（备份） | 现在 | |
|---|---|---|---|
| `assignments` | **1242**（`r:`509 `sc:`358 `scl:`375） | **509**（只剩 `r:`） | ❌ 丢 733 |
| `numbering.issued` 段 | **5**：`W-1` `W-2` `W-3`(157) `S-1`(201) `E-1`(375) | **2**：`W-1` `W-2` | ❌ 丢 3 段 |
| `canonical.state` | 「已填（20260929-1100）：四个形态文件，共 1242 条定稿记录；status=stable」 | 「**空（本批不写…）**」 | ❌ 语义反转 |
| `canonical.files` | 4 个文件的 `lines/bytes/sha256` | **整块消失** | ❌ |
| `promotion_rule.criteria` | C1–C8 逐条 + `criteria_passed: "8/8"` | **整块消失**（缩成 5 行） | ❌ |

**定稿文件本身没被动**（四个 canonical 文件 sha 与 `SHA256SUMS` 逐字节相同：`a1b0cb25…` `2624daf5…` `5c38b2bc…` `a745f722…`；`canonical/rules.jsonl` 仍是空串 sha `e3b0c442…`）。**坏的只有台账。**

**为什么这是硬伤**：`no_reuse` 的**唯一依据就是台账**。实测口径：

```
canonical 里在用的条款号        1242 个  （E-1:375 S-1:201 W-1:56 W-2:453 W-3:157）
台账里还记着的                  509 个
★ canonical 有、台账无          733 个  ← 全部是 E-1 / S-1 / W-3
```

台上这 733 个号在 canonical 里**仍然占用**，但台账已经不认。下一次任何脚本拿 `sample_cases.jsonl` / `scoped_clauses.jsonl` 从零发号，`next_seq` 会从 `S-1.1` / `E-1.1` / `W-3.1` 重新开始 → **直接与 canonical 里在用的号撞车**，C1（条款号唯一）届时才会转红，而那时已经晚了。

**原因码**：`overwrite_in_place_atomic` 层的**重建脚本与其声明引擎不匹配** —— `layers.yaml` L4 `engine` 只登记了 3 个脚本（`l4_article.py` / `l4_integrity.py` / `l4_report.py`），而真正产出 1242 条定稿与富台账的 `kb/.work/batch9_canonical.py` **不在 engine 里**，且实测 `grep -n "apply\|dry" kb/.work/batch9_canonical.py` **无输出 → 它没有干跑档**。
→ 照 `layers.yaml` 跑 L4 的声明引擎，**必然**把台账塌成 509。这是结构性问题，不是执行失误。

**要人做什么**（三选一，都要人拍板）：

1. **从备份恢复台账**（最小、最可复算）：
   以 `kb/l4/_pre-rebuild-20260930-1550/l4.registry.json.bak`（sha `7d53459a…`）为基线恢复 `kb/l4/registry/l4.json`，并补一条 run 记录说明 15:50–15:52 发生了什么。
   —— 但这是**修**，按边界应走 `kb-repair`。
2. **把 `batch9_canonical.py` 登记进 `layers.yaml` L4 `engine` 并补 `--apply` 干跑档**，否则重建台账这件事在链路里没有合法执行者。
3. 若确认这两段（`W-3` / `S-1` / `E-1`）今后改由别的形态段承接，则需在编号方案里显式登记，并把 733 个号按 `no_reuse` 追认回台账。

> ⚠️ 三条都**不是**本次授权的动作：此刻没有一条闸门在红（L3/L4 都过），`kb-repair` 的「必须以一条已红闸门为输入」不成立；且这是 L4 台账写入，属写档三条件管辖。

### 3.2 「重新发号」被本层契约禁止

`kb/l4/registry/l4.json → numbering.no_reuse`：

> 号码一经发出永久占用：重跑时已在册的 `rule_id` 沿用原号；新规则取该段 `next_seq`；**即使某条规则后来消失，它的号码也不回收、不再发给别的规则**。

`layers.yaml` L4 再钉一遍：「条款号一经发出永久占用、不复用；`kb/l4/canonical/*.jsonl` 只加不改」。
→ 想"从 L3 候选重新发号"= 要先清台账；清了就与 canonical 里 1242 个在用号冲突，且违反 `no_reuse`。**不能做。**

### 3.3 「重跑 l4_article.py」是空操作，且救不回丢的号

只读复算（照 `l4_article.py` 编号逻辑重演一遍，不写盘）：

```
候选（最新行口径）: 509 条 ｜ 文件 1018 行
现有台账已发号: 509 个 ｜ 段: ['W-1', 'W-2']

★ 重跑会新发号: 0 条   沿用: 509 条
★ 重跑后 issued 段: ['W-1', 'W-2']    （与现在相同）
★ 会向 kb/l3 追加: 0 行
★ prefix_unchanged（本次）= True

★ 关键：l4_article.py 只读 kb/l3/candidates/rules.jsonl
   sample_cases.jsonl          358 行 —— 本脚本**不读**，其号不可能被重发/恢复
   scoped_clauses.jsonl        375 行 —— 本脚本**不读**，其号不可能被重发/恢复
   external_standard.jsonl     123 行 —— 本脚本**不读**，其号不可能被重发/恢复
```

**结论**：重跑一次 = 发号 0 条 + L3 追加 0 行 + 把 `l4.json` **再覆盖一遍**（新 `run_id`，同样是塌成 2 段的精简版）。
好处为零；代价是再留一条"看起来正常"的运行痕迹，把 733 个号的丢失**再夯实一层**。

### 3.4 真正"没号"的 123 条不在这个脚本的射程内

`kb/l3/candidates/external_standard.jsonl`（sha `7e3ac8ae…`，123 行，`article_no` 全空）才是真没号的。但它：
- `l4_article.py` **不读**这个文件；
