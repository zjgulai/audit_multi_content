## 3. 关键复算：删除不是「拿掉几条」，而是**把整段重编**

各段编号都是 **1..N 连续无空洞**，即 **条款号 = 该段内的位次**。
因此删掉段内 k 条后重跑，剩余条目按位次前移 —— 级联位移（本会话实测，按 `no_reuse` 声明的 order_key 复算）：

| 段 | 段内条数 | 删 1 条 → 号被改动的条数 | 删 5 条 → 号被改动的条数 |
|---|---|---|---|
| W-1 | 56 | 27 / 55 | 23 / 51 |
| S-1 | 201 | 100 / 200 | 96 / 196 |
| E-1 | 375 | 187 / 374 | 183 / 370 |
| W-3 | 157 | 78 / 156 | 74 / 152 |
| W-2 | 453 | 226 / 452 | 222 / 448 |

**即：只要删 1 条，整个段里约一半条目的条款号当场变号**，而这些号同时写在 canonical、写进导出 CSV、
写进 `kb/l3/registry/l3.json` 与各份评审依据单里（本会话实测这些文件确有 `W-3.*`／`S-1.*`／`E-1.*` 引用）。
这与 `numbering.no_reuse` 的「号码一经发出永久占用、不回收、不再发给别的规则」直接冲突。

**「删掉不合意的，重跑就会算出对的号」这个直觉，在本库里是两个错误叠加**：
① 号是位次的函数，不是「谁被删过」的函数 —— 删除只会让**别人**错位，不会让被删的那条「回正」；
② `no_reuse` 明令号不复用，重跑根本不回收号。

## 4. 重跑（`rm -rf runs/` + `l4_article.py`）为什么是**主动破坏**

1. **`rm -rf kb/l4/runs/` 会打崩两个活检查器**（裸 `json.load`，无 try/except）：
   - `kb/l8/workflow_check.py:118`、`:129` 读 `kb/l4/runs/20260923-1445.json`、`:133` 再读 `.get("artifacts")`；
   - `kb/.work/l7_integrity.py:35`、`:60` 读同一文件。
   文件一没，两处直接抛异常；这也是「L3 未被改动」断言的**唯一基线**。
2. **重跑引擎不是 canonical 的作者，且会撞号。** 现台账只认 `W-1`／`W-2`；
   `kb/.work/l4_article.py:162` 的 `n = next_seq.get(seg, 1)` 对**台账里没有的段从 1 重发号** ——
   一旦带 `--apply`，会重新发出 `W-3.1…`／`S-1.1…`／`E-1.1…`，
   与 canonical **已在用的同名号正面相撞**，结果是**同一号对应两条不同内容**。
   该文件 `:205`、`:233-239` 还是硬编码存根（`canonical.state` 被写成 `"空（本批不写…）"`）。
   1242 号的真正作者是 `kb/.work/batch9_assign.py` + `kb/.work/batch9_canonical.py`。
3. 本工作区**无 git**（`git rev-parse` → `fatal: not a git repository`），删掉不可恢复。
