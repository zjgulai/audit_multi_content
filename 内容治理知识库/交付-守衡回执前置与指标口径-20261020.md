## 一、改了什么（4 个文件）

| # | 文件 | 改动 | 为什么 |
|---|---|---|---|
| ① | `tools/agent/agent.mjs` | `handleMessage` 在**读素材之前**判一次送审（`reviewGate.isSubmission`，与闸门同一把尺子），是送审就先发回执；发过的时刻经 `ackSentAt` 交给闸门 | 回执原先排在「下载图 → 画面读数 → 本机 OCR → 摘水印」之后：同一步骤实测 5.8 s、线上抖动 27.8 s，再叠排队 ⇒ 飞书侧真值 60/120/180 s |
| ② | `tools/agent/agent.mjs` | `runSubmissionGate` 收到 `ackSentAt` 就**不再发第二张**；指标行改成 `group_response_ms`（回执−真 ingress）＋`ack_decision_ms`（闸门内置办）＋`prep_ms`（读素材那段）＋`stage=early|gate`＋`ingress=create_time|local|handle_entry` | 旧口径下 `tIngress` 缺省成"进闸门那一刻"，量到的是"回执自己发出去花了多久"（1.4 s / 0.383 s），**结构上不可能变红** |
| ③ | `tools/ws_daemon.mjs` | 新增 `ingressMsOf(msg)`：取**消息 `create_time`**（飞书服务端，最接近"她按下发送"），离谱值退回本机此刻并标来源；`onMessage` 里第一时间取、传给 `handleMessage` | 这是②的数据来源。实测事件里 `message.create_time` 存在（`wm_events.jsonl` 可核） |
| ④ | `kb/l8/measure_group_response.py` | 解析新字段；**只拿 `ingress=create_time` 的读数判达标**，旧口径（无该字段）一律 `no_reading` 并单独报条数；口径句同步 | 新老两套口径混在一起算出来的数既不诚实也不可比 |

**两条边界（判据的一部分，不是防御代码）**：
- `ackAt >= tIngress` 才打指标。没有真 ingress 时（批量工具 / 自证），兜底值是"进闸门那一刻"，而回执已前置发过 ⇒ 算出来是**负数**（实测 −842 ms）。负数不是"很快"，是两个时刻量的不是同一段 ⇒ **宁可不打，也不编数**。
- 闸门那条发回执的路**故意保留**：引用某条带图的消息时，张数要到读入阶段才知道，前置那一支判不出来。

## 四、附：这轮顺带查到的两件事（未改，需单独立项）

1. **旁挂是非原子写**：`kb/l8/review_run.sh` 里 `python3 … > "$SIDECAR"` 是**截断重定向**，
   读方（S1 契约、守衡）可能读到 0 字节/半份 —— 我实测撞到过 0 字节和 `JSONDecodeError`。
   修法现成（先写 `.tmp` 再 `rename`，与 `ws_daemon.writeRunState` 同一手法），**未改**。
2. **飞书重投是真的**：`ws_events.jsonl` 里同一条消息被投多次，首次到达很快（1.3 / 10.8 / 12.2 s），
   之后的重投可到 63 s / 328 s / 4016 s。⇒ 现在 `ingress` 用 `create_time` 之后，
   这段重投延迟**不会**被算进响应时延（只认首次那条），但它是"结论送不出去"的另一个候选成因。
