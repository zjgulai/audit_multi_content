## 4. 为什么「删掉再重跑」拿不到你想要的号

读 `kb/.work/l4_article.py` 实证（第 137–177 行）：

```python
prev_assigned = {}                       # 从台账读回已发号
...
if rid in prev_assigned:                 # 已在册 → 沿用，绝不重发
    mapping[rid] = prev_assigned[rid]
    reused.append(rid)
```

1. **已在册的 509 条**：重跑一律**沿用原号**。删掉 canonical 再跑，这 509 个号**原封不动回来** —— 删除对它们零作用。
2. **不在册的 733 条**：会被当成**首次分配**重新推导。而编号依赖 `order_key`、`scheme`、`block_by_library`、`form_block_retired_at_run`、`reserved_policy` —— 这 9 个键**恰恰是当前台账丢掉的那 9 个**。在**方案定义残缺**的状态下重推，得到的号**可能与现在不同**。
3. 后果：那 733 条已经被下游引用。条款号是**引用契约**的一部分（`kb/l7/registry/l7.json → citation_contract`：`must_include` 含「条款号」「anchor」「source_sha256」）。重排号 = 让**已发出的引用全部指向错误的条款**。

**所以这条路是负收益**：509 条纹丝不动，733 条有漂移风险，换来的是引用面崩塌。
