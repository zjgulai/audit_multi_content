### 3.3 更糟的是它现在**自相矛盾且不再幂等**

```

而 kb/l4/canonical/ 实测：1242 条定稿，article_no 唯一 1242 个
  → 其中 733 条（E-1 × 375 · S-1 × 201 · W-3 × 157）在**现台账里查不到任何号**
```

这 733 条对应的输入文件还在（`sample_cases.jsonl` 358 行、`scoped_clauses.jsonl` 375 行），
而 `l4_article.py` 是**覆盖式写 `l4.json`** 的脚本。于是「号不复用」这条红线**在当前状态下已经守不住**：
谁按现台账跑一次 `--apply`，引擎会认为 E-1 / S-1 / W-3 **从未发过号**，从 `next_seq=1` 重新发
→ 新号 `E-1.1`、`S-1.1`、`W-3.1` 与 canonical 里**已在用的同号**正面相撞。

### 3.4 所以"顺手改一个字段"是错的解法

- ❌ **手改**：直接把 `canonical.state` 字符串写回备份值 = 绕过 `write_mode: overwrite_in_place_atomic`，
  且**只补一句备注、不补 733 行台账** → 改完看起来正常，实际断链更深（下一个人会以为台账是全的）。
- ✅ **正确的解法**：这是一次**写坏了的库内写入**，该走 `kb-repair` 或重跑 `kb-pipeline --only L4`；
  判据是「修完 `l4_gate.py` 仍 ✅ 过 + `numbering.issued` 回到 1242 + `promotion_rule` 回到 8 键整块 + 补 run 记录」。

### 3.5 ★ 本轮新增发现：`canonical.state` 只是**症状**，且平台期比 15:58 那轮更明确

**① `canonical.state` 的错值不是"没人管"，是"改过一次也没碰到它"。**
16:03:27 有**另一个并发进程**对同一个 `l4.json` 做过一次修复
（`kb/l7/_backups/canonical-registry-sha256-20260930-160316/CHANGE.md`：用户请求"注册表 sha256 与实文件对不上，改成一致"）。
该次修复**只改了 `inputs` 块的 2 个键**，`canonical.state` 与 `promotion_rule` **一字未动**（本轮实测复认）。
→ 说明这两个字段**不在任何现有闸门的复算范围内**：`l4_gate.py` 只复算 `promotion_rule.criteria` C1–C6，
不校验 `canonical.state` 是否与 canonical 事实一致，也不校验 `numbering.issued` 是否覆盖全部 canonical 号。
**这就是它们能被写坏、且坏了没人拦的结构性原因。**

**② 台账缺口是 `canonical.state` 问题的严格超集。**
本轮把 three-way 对账做成了严格口径：

```
现台账号 509 ｜ 备份台账号 1242 ｜ canonical 号 1242
canonical 号 − 现台账号 = 733   （现台账漏登记）
canonical 号 − 备份台账号 = 0    （备份台账是完整的）
备份台账号 − 现台账号    = 733   （现台账净丢失）
```

→ 「现台账漏登记」与「备份台账净丢失」**完全同集**，都是那 733 个。
即：**备份台账是一份可信的回灌基线**，修台账不必重发号（重发必撞号，见 §3.3）。
这比 15:57 单"733 个已发号码从台账消失"的说法更进一层 —— 给出了**可直接执行的修复路径**。
