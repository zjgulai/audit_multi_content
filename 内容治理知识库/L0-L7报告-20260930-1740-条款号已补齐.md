## 二、为什么发不出去：三层阻断，一层比一层深

### 第 1 层（表面）：引擎看不见这 123 条

`kb/.work/l4_article.py` 的候选源写死一行：`CAND = kb/l3/candidates/rules.jsonl`。
123 条在**另一个文件**里，与 `rules.jsonl` 的 `rule_id` **交集 = 0**（实测）。
引擎读不到 → 永远发不出号。这不是权限、不是闸门，是**取数面**问题。

### 第 2 层（更麻烦）：就算读到了，也没有段可落

引擎用 `FORM_BLOCK = {entry:1, revision_pair:2, boundary:3, saythis:4}` 把 form 映射成段号。
123 条的六个 form 一个都不在表里 → `block_of()` 返回 **0** → 段 = `E-0`。

而 `E-0` 在权威方案里**根本不存在** —— 它是个"万能兜底段"。
在 `no_reuse`（号码一经发出永久占用、收不回）的前提下，把一条规则静默塞进万能段，
等于**永久固化一个错误标识**。

> 关键事实：这张 `FORM_BLOCK` **早就废止了**。`kb/.work/batch9_assign.py:44` 原文：
> 「旧 numbering.form_block（entry=1/revision_pair=2/boundary=3/saythis=4）**自本批（20260924-1320）起废止**：
> 它是全局 form→段 映射，其 boundary=3 与 W-3 直接冲突，继续沿用会让同一段号指两个形态。
> 旧表只作历史留痕保留，**不得再用于任何新分配**。」
>
> 也就是说：`l4_article.py` 一直在用一张**自己被声明废止**的表发号。

### 第 3 层（最要命，也是本轮最大发现）：台账被覆盖过，733 个已发号丢了

**证据**：现库 `kb/l4/registry/l4.json` 的 `numbering` 只有 **11 个键**；

|---|---|---|
| `numbering.scheme_version` | `article-no-2` | **缺失** |
| `block_by_library`（权威分段表） | 有（12 段） | **缺失** |
| `reserved_policy` / `order_key_per_form` / `scheme` | 有 | **缺失** |

| `assignments` | **1242** | **509** |
| `numbering.form_block` | 保留但标注**已废止** | 被重新写成**生效值** |

**根因**：`l4_article.py` 在 `--apply` 时**整份重建** registry（现造一个 `reg` 字典再覆盖写），

**这也是"为什么以前几次都发不出号"的真答案**：前几轮报告只看到第 1、2 层就停了，
没人发现台账已经被换过 —— 因为第 3 层不会报错，它只是**安静地少了一半**。

## 三、补号的依据：全程照库自己的方案走，没有自造段

**原则**：段是库的**已声明事实**，不是我现场发明的。三步都落在库自己的文件里。

### 3.1 复原依据是"已证事实"，不是"猜"

损坏前的全量台账留在归档里。我把它与现库 `kb/l4/canonical/*.jsonl` 的 1242 个 `article_no` **逐号对账**：

```

归档号集合 1242 == 现库号集合 1242  →  True
```

**1242/1242，零处不符**。所以复原的 733 个号（W-3 157 + S-1 201 + E-1 375）是**已经发出去、
有定稿实物对应**的号，不是新发号。

### 3.2 E-2 是唯一正确的段（不是"挑一个"）

`article-no-2` 的 `block_by_library` 里，`external_standard` 库**只有两个段**：

| 段 | form | 状态 | 条数 |
|---|---|---|---|
| `E-1` | `scoped_clause`（限定条款型） | 已发 | 375 |
| `E-2` | `clause`（法条型） | **`reserved_unused`（预留未用）** | 0 |

这 123 条的 `form` ∈ 六个条款级形态，**与 E-1 的 `scoped_clause` 是不同形态**，
且 `kb/l3/registry/l3.json → rule_forms` 把 `external_standard` 整个库记作**单一家族**：
「`{判定条件, 阈值/词表, 条款锚点, 生效期}`」—— 这就是**法条型**。
→ **唯一正确的段是 `E-2`**，没有第二个候选。

而 `reserved_policy` 原文写着怎么用它：
> 「state=reserved_unused 的段是**预留但本批 0 条**：号码不预发、不占位，**等该形态首次产出时才从 .1 起发**。」

本批就是该形态**首次产出** → 发 `E-2.1 … E-2.123`。
排序键用 `rule_id`（内容派生的稳定 id），与方案里的 `order_key_per_form` 一致 ——
不用行序、不用时间、不用命中数，这样规则增删不会让已发号错位。

### 3.3 段的"承载哪些 form"写进台账，不写进代码

`seg_of()` 查不到段就**报错停机**，绝不回落已废止的 `form_block`。实测这条防线当场抓到一次真问题：
方案的 form 名与候选件的 form 名**不是一套**（方案用 `wording_entry`，候选件写 `entry`）——
若不登记就发号，W-1 的 56 条会当场落空。登记后（数据写在
`numbering.block_by_library[seg].forms`）才继续。
