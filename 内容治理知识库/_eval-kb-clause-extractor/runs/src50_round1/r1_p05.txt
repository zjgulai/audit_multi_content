# 第二件事：拒绝台账怎么看

台账在 `kb/l3/rejected.jsonl`，**它是逐单元口径的**——这是它存在的全部意义：**候选数只告诉你"有多少条能变成规则"，拒绝台账才告诉你"有多少条款根本没进来、以及为什么"**。少了它，覆盖率无从谈起。

## 一、先看规模有没有异常（和跑前基线对）

```bash
wc -l kb/l3/rejected.jsonl
wc -l kb/l3/_archive/rejected-pre-$RUN.jsonl
```

**判据**：跑后行数**不得显著低于**跑前归档那份。若跑到 1,053 行上下而基线是 1 万多，**当回归处理，别当收敛**。

## 二、看原因分布（这才是"拒绝台账"的用法）

```bash
python3 - <<'PY'
import json,collections
c=collections.Counter(); src=collections.Counter()
for l in open('kb/l3/rejected.jsonl',encoding='utf-8'):
    r=json.loads(l)
    c[r.get('reason_code') or r.get('reason') or '(无原因码)']+=1
    src[r.get('source') or r.get('source_sha256','')[:12]]+=1
print('总行数', sum(c.values()))
print('\n— 按原因码 —')
for k,v in c.most_common(): print(f'{v:8d}  {k}')
print('\n— 按来源 —')
for k,v in src.most_common(20): print(f'{v:8d}  {k}')
PY
```

## 三、结果怎么读

| 现象 | 判定 | 处置 |
|---|---|---|
| 行数骤降到四位数 | **高度可疑，先当覆盖事故** | 与 `_archive` 基线比；确认是覆盖就**从基线恢复**，不要重跑——重跑会再覆盖一次，可能把仅存的证据也盖掉 |
| 某类原因码占比暴涨（如"无法判定"） | 多半是**口径**问题，不是数据变差 | 看是不是上游 L2 单元换了切法 / 蒸馏器版本变了；口径变了要**先改口径再重跑**，不然只是重复拒绝一遍 |
| 同一 `unit_id` 被拒多次 | 台账重复登记 | 属工具问题（新写入应走 `l0_ledger.py` 的 `append_changed()` 那类"有变化才写"的口径），别当数据缺陷删行 |
| 原因码大面积 `(无原因码)` | 台账没带上判据 | 这是台账的**信息缺失**，回填原因码比调数字重要 |
| 多个来源的拒收率差异极大 | 正常 | 不同政策的可判定程度本来不同，逐来源给数就好，别强行拉平 |

## 四、我会给你的结论（不是一串数字）

- **拒收总数 + 按原因码 / 按来源的分布**；
- **与跑前基线的差额及去向**（差了多少行、差在哪一类）——**只报净数不算交账**；
- **口径声明**：本轮候选是 `provisional`、**条款号未分配**、未做人工抽查；
- **工具 bug 与库缺陷分开写**——数字不对时先怀疑工具（本库两次事故都是脚本自己写错口径），不许把工具 bug 报成数据缺陷。
