## 为什么拒

`/etc/passwd`、`/etc/hosts` 不是"政策原文"，是**宿主系统文件**。把它们当素材读进来抽条款，同时踩了三条线：

2. **敏感信息**：`/etc/passwd` 是账号清单（现代 macOS 上口令哈希多在 `/etc/master.passwd` / opendirectory，但账号名、UID、家目录、登录 shell 都在），属于**凭据/账号类信息**。这类内容一律不读取、不导出、**也不落库** —— 抽条款时连 PII 都要替换成 `[PII:手机号]` 这种占位符，账号清单没有任何理由进知识库。
3. **产物性质**：`/etc/hosts` 是一份主机名映射表，`/etc/passwd` 是一份账号表。它们没有"命中表达 / 处理方式 / 依据"这种规则结构，抽出来的东西**不构成规则候选**，只会污染 `kb/l3/candidates/rules.jsonl`。

| 1 | **库名 + 版本** | 强制 | 只能用**真实存在的四类库**：外部标准库 / 内部正负样本库 / 措辞表达库 / 产品描述库。**不许自造**《合规措辞库》《广告法禁用语》这类名字，即使源文档里这么写过 |
| 2 | **`article_no`**（条款号） | 强制 | L4 分配，**只读，不许自己编号**；发号永不复用 |
| 3 | **`anchor`** | 强制 | 定位用 |
| 4 | **`source_sha256`** | 强制 | **只有锚点不算完整定位** —— 锚点是行号，会漂移。两者必须成对 |
| 5 | **逐字摘录** | 强制 | **不许转述、概括、润色**。抄错一个字这条就废 |
| 6 | **`事实` / `推断` 标注** | 强制 | 二选一，明写 |
| 7 | **置信度** | 强制 | 高 / 中 / 低 |
| 8 | **证据级 `L?`** | 建议 | 注意库里的现状：大量条目是 **L1，只能当线索、不能进决策** |
| 9 | **`valid_until`（有效期）** | 强制 | **过期了引用时必须说明它已过期**，不能默默用 |
| 10 | **`rule_id`** | 建议 | 便于回指与去重 |

**格式本体**：

```
《<库名> <版本>》第 <条款号> 条 + 可点链接
```

## 三、**不能**进引用契约的字段（同样重要）

| 字段 | 为什么不能用 |
|---|---|
| `suggested_replacement`（替换建议 / 改写建议） | 它是**"怎么写更稳"的建议**，**不构成"这条能发"的结论**。而且同一条规则的替换字段可能是**多段拼接**的（源表"修改建议"列本身就是多段拼接）—— 只允许输出与**本条命中片段同源**的那一段，拿不准就只给该规则的豁免/允许表达，不给建议 |
| `p_level` / `risk_level` | **不是放行结论**，是**分流标签**（P1 = 优先处理）。别把它写成"能不能发" |
| 未命中结果 | **未命中 ≠ 合规**。命中只说明"这句话有问题"；没命中**不说明**内容合规 |
| 边界外推论 | 每条都带 `not_proves`（不能由它证明什么）。拿它去证明边界外的事 = 幻觉 |
| 凭常识补的结论 | 直接不许 |
