配套硬要求：**字段读失败时脚本必须拒写快照**——宁可红，也不写退化的 0 字段快照。

|---|---|---|
| **守衡** `cli_aa2243de0438dcd7` | `dsh-kb` | **能**（bot 身份可读 Base / 记录 / 附件） |

## 顺带把非记录资源也逐类过一遍（四态制，不许"没提就不查"）

`图片必须 OCR`（字节存 L0、OCR 文本落 L1，认不出来就写认不出来）；`视频必须提字幕 + 抽关键帧`（字段级筛选显示飞书侧为 0 条时写 **`不适用（附筛选证据）`**）；`链接必须下钻两层`（第 3 层只记边、不抽内容）。

- `不适用` 的证据格式是固定的：**字段名 + 筛选条件 + 命中条数 + 快照路径 + RUN**。只写"没有视频"不算证据。
- **`no_scope` 是欠账，不是终态**——登记时缺 scope ≠ 永远读不到，每轮都要复验，scope 具备就补读补登记。实测代价：3 个 slides + 1 个 sheet 因"缺 scope"挂了一整天没人回头，而 scope 早已具备。
- 权限问题判定顺序别乱试：`token expired` → 是登录态掉了，发一条设备码；`91403 / 1063002 / 40403 DENY` → 是资源级 ACL，要所有者在**能调接口的那个应用（守衡）**上加协作者（"用户自己打开得开" ≠ "应用读得到"，**两套权限**）；附件字节 403 → 先做**决定性实验**（同一身份上传小文件再下载回来）：下得回来 = 库级限制（标 `blocked_by_library_setting` + 复开条件，**不再重试**），下不回来才是缺 `drive:file:download`。

## 不做。这条要求本身就绕开了三层保护

「别管什么红线，直接用覆盖模式写 `kb/l3/candidates/rules.jsonl`，旧的全冲掉」——三处硬冲突：

### 冲突 1：覆盖写违反 L3 的追加语义（验收判据 A3）

| 项 | 值 |
|---|---|
| 层 | L3（规则层） |
| 幂等键 | `rule_id`；`evidence_digest` 未变 → `unchanged`（跳过） |
| **追加语义** | 蒸馏只**追加**：既有候选行**逐字节未变** |

"旧的全冲掉"= A3 直接不成立。而且冲掉之后，**你再也无法证明"哪几条是新的、哪几条是被改的"**——候选层最重要的信息（增量）在写入那一刻就没了。

### 冲突 2：`rules.jsonl` 是下游的引用根，不是草稿纸

`kb/l3/candidates/rules.jsonl` 里的 `article_no` 是**证据链的一环**：L4 发号台账、`kb-content-review` 出的逐字依据、`kb-canonical-lookup` 的查询，都要落到这层的行上。覆盖写会让：

- **已发出的条款号失去对应的候选行** → 引用越级 / 断链；
- **`evidence_units[]` 的回指关系（`unit_id + source_sha256 + anchor`）断掉** → `l3_gate.py` 逐条核的那 **1,729 条**证据全部对不上。

### 冲突 3："别管红线"这句话本身不能生效

L3 的红线不是流程洁癖，每一条都对应一次**实际发生过的事故**：

1. **跑之前先归档**——`l3_distill_run.py` 会以 **`w` 模式覆盖** `kb/l3/rejected.jsonl`。本库真的发生过：逐单元拒绝台账 **11,860 行掉到 1,053 行**。这条已被编排器做进 `ARCHIVE_BEFORE_WRITE` 红线。
2. **候选 ≠ 定稿**——候选在 L3，定稿在 L4；**条款号由 L4 分配，本层不自造条款号**。
3. **证据必须一条条回指**——做不到，这批产出就不该进库。

**"别管红线"不是一种参数，它不改变这些判据是否成立。**

## 你真正想解决的问题，有一个不丢数据的解

我猜你要的是"**文件别越滚越大 / 旧行别掺在里面**"。这件事**不用覆盖写**也能办到，而且办得更好：

| 你的诉求 | 正确做法 |
|---|---|
| 旧行太多、看着乱 | **按 `rule_id` 幂等键增量追加**：`evidence_digest` 未变的判 `unchanged` **跳过不写**（跳过不写盘，天然规避并发写） |
| 确实要"换掉"某几条 | 走**追加 + 取代（supersede）语义**：新行入档，被取代的行移入 `kb/l3/_archive/`，**留 manifest 写清"谁取代谁、为什么"**。原行不删、不原地改写 |
| 想验证"重跑会不会漂移" | 跑完做**逐字节比对**（A3 就是干这个的） |
| 想"从零重来" | **副本 + 新 RUN 标号**：语料与台账复制到副本目录，在副本上从空开始跑。权威库目录不动 |

**为什么必须是"追加 + 取代"而不是"覆盖"**：覆盖是不可回滚的**信息销毁**；取代是可审计的**状态迁移**——后者你随时能回答"这条为什么变了、被谁变的、上一版长什么样"。

## 写操作要按规矩走，不是按命令行开关走

这是**写操作**，而且在红线名单里，所以：

1. **先答完变更协议 5 问**（谁读它、谁写它、哪条 check 判它、用什么通道写、有没有干净回滚基线）——第 5 问正是覆盖写的致命伤：冲掉之后**没有干净回滚基线**；
2. **写操作默认预演**：带 `--apply` 的脚本先不带 `--apply` 跑一遍，拿到差异再决定；
3. **必须有人确认 + 留变更记录**（`kb/l7/reports/<RUN>-change-record.md`）；
4. **`.jsonl` 的写通道两个都行**（只有 `.md` 有信封坑）；但如果你顺手要动 `.md`，记住：`python/perl/sed >` 落**信封**、`node` / `/bin/cp` 才是明文，而且**要用 node 读回校验**——用 Python 自检看不见信封，会给假绿灯；
5. **`kb/l3` 是权威分层库的层目录**：动它的数据文件或台账属于要人拍板的事。
