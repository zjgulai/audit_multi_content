===ROUTE 9: kb-clause-extractor===
蒸馏规则候选，每条必须**同时**带「命中表达」和「处理方式」—— 只给其一，落不了形态，会被拒收而不是变成弱候选。

## 一、候选记录的形态（每条长这样）

| 字段 | 含义 | 缺了会怎样 |
|---|---|---|
| `form` | prohibition / mandate / disclosure / substantiation / recommendation / scope | 无 form 无法归类 |
| `condition` | 判定条件（什么时候算命中） | 缺 → 判不了 |
| `forbidden_expression` 或 `命中表达` | 词表/正则/阈值 | 缺 → 不可机械判定 |
| `required_action` | **处理方式** | 缺 → `obligation_without_action`，拒收 |
| `evidence_quote` | 逐字摘录（不转述） | 缺 → 证据不成立 |
| `evidence_units[]` | `{unit_id, anchor, source_sha256}` 三件套 | 缺 → 闸门 C1 不过 |
| `evidence_level` | cited / synthesis / inference / hypothesis | 缺 → 分不清观测与推断 |
| `p_level` | P0/P1/P2 分流标签 | 缺 → 无法分流（注意：p_level 不是放行结论） |
| `article_no` | **一律留空** | 填了 = 越级自造条款号（L4 才发号） |
| `status` | `provisional` | 候选 ≠ 定稿 |

切 clause 级单元 + 指纹，是 **L2 层**的活（`clause` 切分器，`kb-ingest-extractor` 是那一层的入口）；条款蒸馏才是 L3。切法我按 registry 现成口径给你，**但文本没给，所以切不了** —— 先要输入。

## 一、切分口径（`kb/l2/registry/l2.json` → `splitters.clause`）

| 项 | 值 |
|---|---|
| kb_type | `external_standard` |
| 最小单元 | **一个法条** |
| 边界识别 | 章 / 节 / 条；正则 `第X条(之Y)` / `§X.X` / `Art. N` / `Article N` / `Section N` / `N.N.N` |
| 段内多项 | **可拆**（一项义务一个单元） |
| 相邻段 | 同 `clause_label` 的相邻段按物理续接**合并**，打 `joined_parts` 标记 |
| 当前切分器版本 | `l2-0.3` |

## 二、每个单元的字段（12 个，一个不能少）

```
unit_id          kb_type            resource_id       source_sha256
anchor           unit_type          text              char_count
heading_path     pair_ref           parent_unit_id    order_in_parent
```

## 三、你说的「指纹」= 两个东西，别混

| 名字 | 是什么 | 怎么来 |
|---|---|---|
| `source_sha256` | **资源正文指纹**（整份文本的 sha256，16 进制 64 位） | 从 L1/L2 落盘记录读，**不能编** |
| `seg_anchor` | **段级定位**，形如 `#l.1-506/seg-64` | 与 `anchor`（如 `#l.1-506`）配对，精确到切出来的那一段 |

`unit_id` 本身也是确定性指纹：`sha1(splitter_version | resource_id | source_sha256 | unit_type | anchor | …)[:20]`，20 位十六进制。现成样例（外标 clause 单元）：

```json
{"anchor":"#l.1-506","seg_anchor":"#l.1-506/seg-64","source_sha256":"b079385463060a8b87c423f6961c3a9879296054b618fe7c41856a0d778ef8ba",
 "unit_id":"7df4bc719607df3cbee8","unit_type":"clause","order_in_parent":1,"char_count":210,"text":"…"}
```

## 四、幂等 & 对账（切完必须核）

- **幂等键**：`resource_id + source_sha256 + splitter_version`；三者都没变 → `unchanged`，**跳过**（不重切）。改了指纹或切分器版本才会重切。
- **对账规则**：每类库「L1 中有内容的资源数 == 被切分资源数 + 明确跳过资源数」，**差额必须为 0**。

## 五、一个已知陷阱（提前说，省一轮返工）

台账里 `mid_sentence_fragment`（26 条，原因：「单元从句子中间开始（首字符小写），是把上一句切了一半的残片，判定条件不完整 —— **应在 L2 侧重切，不在 L3 侧补全**」）和 `heading_only`（19 条：「仅小节标题字母/序号，无判定内容 —— 建议 L2 侧重切，**标题应与正文同单元**」）说明：**按「条」切不够，还要保证不把一句话切一半、不让标题单独成单元**。这是这次切分要盯的两个点。

## 六、我要你给的东西

1. **待切分文本**（或资源 id / 表@rev / URL —— 有 id 我直接从 L0 取正文）；
2. 文本的语言与法规形态（决定用哪条正则，以及要不要 `joined_parts` 合并）；
3. 是否需要**行级锚点**：只有「表@rev」时，回源只能判断「这个表变过没有」，判断不了「哪条记录变了」—— 有 `record_id` 就能补上行级锚点。

## 七、边界

- 切分是**写操作**（落 `kb/l2/units.jsonl`），我不替你跑；这条线上我没有执行权限。
