## 3. 为什么必须先在飞书侧有记录

`kb/l8/apply_ocr_to_l1.py` 回写 L1 时，附件级那批行**只更新已存在的行**：

```python
key = f"bitable:{TABLE}:{rid}/fldnvxjaSr/{tok}"
old = latest.get(key)
if old is None:
    continue          # ← 附件级行不存在就直接跳过，不新建
```

也就是说：
1. 附件级台账行得由 **L0 同步**先写出来（`kb/l8/ingest_l0_new_records.py` / `align_l0_feishu.py`）；
2. `rid`（父记录）和 `tok`（file_token）**都来自飞书**；
3. 本地图片文件没有这两个标识 → 跑完 OCR 只会得到**孤儿资源**，进不了 L1 台账、也就进不了索引和后续召回。

### 这一条 skill 自己也写死了（Gotcha 首条）

> 引擎**不读本地文件夹**：输入是飞书侧快照 ndjson 的记录，本地散图进不来；新素材必须先登记进 L0。

配套的安全边界：**输入只能是 L0 已登记的 resource**，不许遍历工作区之外的目录去「找图抽」。
所以「本地目录」这条选项不是"多花点功夫"，而是**要先在 L0 侧把素材登记成记录**，之后才有得抽。

本地图这条路的真实代价（选它之前先认下来）：
- `apply_ocr_to_l1` 的附件级回写会直接跳过 → 只有 `media_*.json` + `ocr.json`，台账里没有对应行；
- 段锚点 `anchor_spec` 由父记录决定，缺父记录就得自己编一套 → 与既有 anchor 语义不一致；
- `l1_gate.py` 的复用闸门**仍能过**（它只看缓存质量，不看来源），所以"闸门绿"不等于这条路合规；
- 需要额外写一个一次性落盘脚本 —— 那已经越出 `kb-media-extractor` 的口径，属于新建一条写入路径。

## 4. 拿到来源后的执行清单（幂等键已定，可直接跑）

幂等键：`(resource_id, extractor_version=l1-0.1, source_sha256)`；OCR 缓存另按**文件 sha256** 命中。

```bash
cd <内容治理工作区根>

# ① 预演（不落盘，先看会写什么）
kb/kbpy l8/ocr_attachments.py <OCR_RUN>
# ② 落盘：建 kb/l1/media/media_<table>_<rid>/、写 ocr.json、写 _cache/*.json、写 2_内部正负样本库/media_*.json
kb/kbpy l8/ocr_attachments.py <OCR_RUN> --apply
# ③ 把 OCR 文本回写 L1 台账（附件级 + 媒体容器级）
kb/kbpy l8/apply_ocr_to_l1.py <OCR_RUN> <L1_RUN> --apply
# ④ 补 media 的单元索引
kb/kbpy l1/index/rebuild_l1_index.py --write --run <L1_RUN>
# ⑤ 闸门
kb/kbpy l7/scripts/l1_gate.py
kb/kbpy l7/scripts/l2_gate.py
kb/kbpy l1/index/rebuild_l1_index.py --check
```

反例提醒（别踩）：
- `--purge-images` **不是预演开关**：它删的是 **L1 的工作副本**（`kb/l1/media/<rec>/` 里的图），**不是 L0 原图**；要删库重来那种做法一律不接；
- 坏缓存（引擎版本不对 / `sha256_state` 非 full / 正文含 U+FFFF / 整图丢失）**不得复用**，命中就得重跑 OCR；
- OCR 空结果如实登记成 `empty` + `status_reason`，**不许拿别的字段凑正文**；
- 一切写操作**先预演、后 `--apply`**；只读会话里如实回报「写不了」，不得假装已落盘。
