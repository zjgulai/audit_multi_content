# 复测口径变更 · 只评 skill、不跑底层作业（2026-10-04，用户裁定）

## 一、用户口径（原话）
> 「L0的为什么跑那么久，只评测skills，跟飞书侧对齐的先不跑」

## 二、为什么会跑 9 小时（实测根因，三段叠加）

1. **用例提示词本身是"干活型"**：L0 的 A 卷提示词直接要求做对账 ——
   `A1 只对账 L0：库里和飞书侧现在一致吗？给我差异清单和一句话结论。`
   `A2 L0 和飞书对一下，重点看这轮有没有漏抓的记录。`
   `A3 帮我核对一遍 L0：飞书侧从昨天到今天有没有变。`
2. **被测会话真的去干了**：拉飞书 8 张表做对账；又因沙箱只读（提权无审批通道 ⇒ fail-closed）跑不了官方脚本，
   退化成内存比对 ⇒ 实测 **144–308 秒/条**（`a-round-1.jsonl` 6 条实测：197.5 / 232.3 / 308.1 / 187.1 / 144.4 / 244.7）。
3. **测试台允许它跑到底**：`run_round.py: PER_CASE_TIMEOUT = 1800`（30 分钟）⇒ 每条都等到作业做完。
   ⇒ 104 条/轮 × 3 轮 ≈ **9 小时**（L0）；kb-check 50×3 ≈ 3–5 小时。

## 三、改法（已下发两条修复线）

**触发评测只需要知道「该不该加载这个 skill」**，而判定本来就取客观证据
（`run_round.py` 注释：触发判定取该会话 session.jsonl 里的 `skill` 工具调用 / 斜杠注入的 skill_content）——
**那个信号在会话开头就出现，不必等底层作业跑完**。故：

1. `PER_CASE_TIMEOUT` **1800 → ~120 秒**；被测会话**不需要完成** L0↔飞书对账 / kb-check 的体检作业。
2. ★★ **防假分**：限时会导致 `reply` 空/半截 ⇒ **这类记录不许按「不触发」计**（否则把限时造成的空回复
   当成漏触发，P/R/F1 全假）。必须打 `证据不足/无效`、单独列补跑清单、重跑，**不静默计入四格**。
3. **先冒烟 2–3 条**（1 正 + 1 负 + 1 边界）证明 `session_found=True` / `reply` 非空 / `skills_loaded` 有值，
   再启动全量。（本批已因「没冒烟就全量」白跑过一轮：6 条全是空 `reply`。）
4. runner 必须活着（受管后台任务 / 前台跑完再结束 turn）＋ **逐条落盘**。
5. **偏离必须留痕**：报告里写明「被测会话被限时 ~120s、未完成底层作业」——不许写成"标准口径完整复测"。

## 四、预期效果
单条 ≤120s ⇒ L0 104 条/轮 ≈ **35 分钟**量级（分片可再压）；3 轮 ≈ 1.5–2 小时 + B 卷门禁（10×3）。
