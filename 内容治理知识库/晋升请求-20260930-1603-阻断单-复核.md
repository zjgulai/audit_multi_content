## 3. 阻断理由 ③：`canonical.state` 不能"顺手改" —— 它是损坏台账的一格，不是过期备注

### 3.1 现值 vs 备份值

```
现 kb/l4/registry/l4.json（41,347 B，mtime 15:52，sha256 f3682d69…）
  canonical.state = "空（本批不写；定稿要过抽查闸门，抽查是人工环节，不在本批）"

kb/l4/_pre-rebuild-20260930-1550/l4.registry.json.bak（115,414 B，mtime 09-29 10:32，sha256 7d53459a…）
  canonical.state = "已填（20260929-1100）：四个形态文件，共 1242 条定稿记录；status=stable"
```

**数据本身没坏**：canonical 四个形态文件与备份目录**逐字节一致**（sha256 全等，与备份目录
`SHA256SUMS` 相符）。坏的是**台账**（`l4.json`），14:50–15:53 那次重建把它写缩水了。

### 3.2 同一次重建写丢的东西（本次逐项复算）

| 字段 | 备份（真值） | 现在 | 性质 |
|---|---|---|---|
| `canonical.state` | 1242 条定稿、status=stable | 「空（本批不写）」 | 定稿状态被抹成未定稿 |
| `promotion_rule` | **12 个键**（C1–C8 判据 + `human_spotcheck` + 抽样方案 + `status_enum`） | **5 个键** | 晋升档位整块丢失 |
| `numbering.issued` | **5 段** W-1(56) W-2(453) W-3(157) S-1(201) E-1(375) = **1242 号** | **2 段** W-1(56) W-2(453) = **509 号** | **733 个已发号码从唯一台账消失** |
| `numbering.next_seq` | W-1=57 · W-2=454 · **W-3=158 · S-1=202 · E-1=376** | 只剩 W-1=57 · W-2=454 | **三个段的续号游标丢失** |
| `numbering.totals` | `assigned_total: 1242`、`segments_used: [E-1,S-1,W-1,W-2,W-3]` | `assigned: 509`、`segments: 2`、`libraries_used: ["wording"]` | 口径自相矛盾 |
| `numbering` 其余键 / `assignments` / 逐文件 `sha256` | 有 | **消失 / 缩水** | 编号方案可复算依据与完整性锚点丢失 |

`numbering.issued = 唯一台账`（`layers.yaml` L4 `outputs` 原话）——丢的不是备注，是**唯一台账的 733 行**。

### 3.3 它现在**自相矛盾**，而且"号不复用"这条红线**已经守不住**

```
现台账声称：libraries_empty = ["external_standard","internal_sample","product_desc","unknown"]
             assigned_total = 509
而 kb/l4/canonical/ 实测：1242 条定稿，article_no 唯一 1242 个
  → 其中 733 条（E-1×375 · S-1×201 · W-3×157）在现台账里**查不到任何号**
```

`l4_article.py` 是**覆盖式写** `l4.json` 的脚本。谁拿现有输入跑一次 `l4_article.py --apply`，
引擎会认为 E-1 / S-1 / W-3 **从未发过号**，从 `next_seq=1` 重新发 → 与 canonical 里**已在用的同号正面相撞**。
15:50 那次没炸，只是因为喂进去的输入里没有这三批候选（`newly_assigned=0`）——**不是幂等成立，是撞号面恰好没被覆盖**。

### 3.4 所以"顺手改一个字段"是错的解法

- ❌ **手改**：把 `canonical.state` 写回备份字符串 = 绕过 `write_mode: overwrite_in_place_atomic`
  （tmp → 逐行 `json.load` 验 → `os.replace`），且**只补一句备注、不补 733 行台账**
  → 改完看起来正常，实际断链更深：下一个人会以为台账是全的。
- ✅ **正确的解法**：这是**一次写坏了的库内写入**，该走 `kb-repair`（台账修复）或重跑
  `kb-pipeline --only L4`；判据是「修完 `l4_gate.py` 仍 ✅ 过 + `numbering.issued` 回到 1242 +
  `canonical.state` / `promotion_rule` 回到带判据的整块 + 补一条 run 记录」。
  **用备份回灌还是重发，要人定**，不是顺手。
