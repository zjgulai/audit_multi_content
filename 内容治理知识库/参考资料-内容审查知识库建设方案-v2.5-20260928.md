## 1. 一页结论

- **现状**：知识库管线（L0–L7）已跑通、定稿 1,242 条带条款号记录；但**四类库只蒸出「措辞表达库」一类 509 条规则**，外部标准库条款层为空、正负样本库噪声大、产品描述库几乎为空；**画面类 100% 无库内规则**，视频能力「设计完成、待验证」。
- **要建什么**：把「多模态送审 → 多 skills 编排 → 双轨校验 → 三态+拒答 → 回流」这条工作流补全，并把它依赖的知识库从「只有文字措辞规则」补齐到「四类库都有规则、画面/视频有据可引」。
- **分几期**：W0 归位修复 → W1 覆盖对账 → W2 外部标准条款层 → W3 样本清洗 → W4 产品事实+场景补规则 → W5 定稿发版。**首期不依赖外部权限**。
- **首要瓶颈**：四类库只蒸出一类 → P1/P2 层的库辅助实际是空的，只有模型单侧在跑。改法是**把规则蒸出来**，不是改流程、改门限。

## 2. 目标与边界

### 2.1 审什么

| 维度      | 内容                                                                   |
| ------- | -------------------------------------------------------------------- |
| 市场      | 美国（含德语等多语本地化站）                                                       |
| 业务线     | 吸奶器 / Baby Monitor / Bottle Washer / 喂养品线                            |
| 模态      | 文字（caption/listing/PDP/社媒/独立站）/ 图片（含 OCR 文本）/ 视频（字幕/旁白/画面/时序）        |
| 渠道      | TikTok 广告二创 / Amazon Listing·主图·A+ / Momcozy 独立站 PDP·落地页             |
| 场景域（9）  | 车内 / 功效宣称与广告用语 / 喂养 / 人物·肖像与 AI / 睡眠 / 洗护与沐浴 / 出行与户外 / 居家与用电 / 玩具与玩乐 |
| 优先级     | P0 法务红线 / P1 安全与准确性 / P2 通识与常识 / P3 措辞与表达                            |
| 一票否决（7） | 车内安全座椅类 / 医疗功效宣称 / 绝对化用语 / 无依据销量排名 / 危险行为示范 / 未成年人未授权出镜 / AI 内容未标识   |

**输入规格（已敲定）**：图片 ≤20MB；视频 ≤500MB 且 ≤10 分钟；单任务批量 ≤50 个文件。超出走人工/拆分，不自动处理。

**品类粒度（已敲定）**：一版**不区分 SKU 粒度**，大多数场景判断品类即可；仅产品信息需区分型号/SPU 时，在 JSON 里**预留 `model` 字段**，不在一版铺开 SKU 级事实。

**审查维度（对齐 PRD §5.2，问题分类的受控词表来源）**：消费者安全 / 品牌信任 / 合规 / 经营风险 / 产品准确性。

### 2.2 不审什么

- 生产中间物（brief / 脚本 / AI 文案），不做历史内容全面倒查。
- 创意质量、视觉美学、字体色号、转化效果。
- 不替代法务 / 医学 / 专家 / 北美本地同事的最终判断。
- 源侧「规则库」表（50 条记录）**暂不纳入知识库**，待产品后续确认后再迭代（当前从材料里读取，见 §5 边界）。

### 2.3 四态语义（裁决出口）

| 态          | 含义              | 成立条件                                   |
| ---------- | --------------- | -------------------------------------- |
| **PASS**   | 未发现已知底线风险       | **唯一成立方式**：两侧（知识库 + 模型）都覆盖到该主题，且都没发现问题 |
| **REVIEW** | 需进一步判断          | 两轨冲突降 REVIEW；单轨命中倾向 REVIEW             |
| **BLOCK**  | 命中明确红线          | P0 确定性命中即 BLOCK；模型侧单轨命中**不得单独定 BLOCK** |
| **拒答**     | 不是第四态，是**没有结论** | 任一侧没覆盖该主题；必须给检索轨迹；**不得输出 PASS**        |

两条铁律贯穿全文：**拒答 ≠ 放行；没命中 ≠ 合规。**

**总纲（已敲定）：本 Agent 输出的是预审结论，PASS / REVIEW / BLOCK 最终都需人工确认后生效——不存在「自动放行」的内容类型。**

**置信度分流（对齐 PRD §6.6）**：≥0.90 直接输出结论（PASS/BLOCK）；0.70–0.89 → REVIEW「建议人工确认」；<0.70 → REVIEW「不确定，重点人工看」；**P0 层级不适用置信度分流，命中即 BLOCK**。知识库「没命中」落到 <0.70 REVIEW（即上文「拒答」的 PRD 语义：不设独立第 4 态，用低置信度 REVIEW 承接）。

## 3. 系统总图（端到端链路 + 状态机）

### 3.1 端到端链路（用户说「审核一下」→ 最终出报告）

> 一条「审核一下」从进到出的完整追踪。每一步标注**产出的数据契约**和**状态流转**；契约字段定义在 §4.1，状态机在 §4.2。

![图 3.1 端到端链路](fig-3.1-端到端链路.png)

> 图源 `e2e-flow.mmd`（Mermaid 源码，可重新渲染）。侧枝：缺料 → NEEDS_INPUT；P0 命中 → 立即 BLOCK（红线零延迟，直接进飞书输出）。

> 文字版（含每步产出/状态判注）：

```
用户输入「审核一下」+ 素材（URL / 文件 / 文本 / 批量 ≤50）
  │
  ▼
[① 入口路由] brand-review-intake-router
  │  产出 input_manifest：content_id / product_line / sku·品类 / channel / content_type / content_version / sha256
  │  状态判：输入不完整或读不到 → NEEDS_INPUT（缺什么补什么，1 business day 超时升级给提交方）
  │
  ▼
[② 多模态标准化] brand-image/video-safety-review ← N2 kb-media-extractor
  │  文字直读 / 图片 OCR(Vision) / 视频 ASR+OCR+镜头切分
  │  产出 coverage：text / ocr / asr / keyframes 完成状态 + 抽取结果(provider/provider_version/content_hash)
  │  状态判：抽取失败或覆盖不全 → 不产出 PASS，转 NEEDS_INPUT / REVIEW
  │
  ▼
[③ 待审对象标定]（§9.10）明确哪段是「被审文案」、哪段是提问/批注/水印/上下文
  │  产出：待审对象边界标注（防「审错对象」）
  │
  ▼
[④ 知识库检索] kb-content-review 四层下探（①红线匹配 → ②规则层 → ③单元层 → ④原文层）
  │  产出：候选规则（库名+条款号+锚点+source_sha256）+ covered 标记
  │
  ▼
[⑤ 双轨校验] P0–P3 × 「知识库侧 + 模型侧」全并行 —— 明细见 §3.2
  │  知识库规则作为上下文喂给模型，做二次合规校验
  │  P0 命中 → 立即 BLOCK（红线零延迟，不等其余层）
  │
  ▼
[⑥ 合并] 同一问题取交集 / 不同问题走并集；两轨冲突降 REVIEW；两侧都没覆盖 → 拒答
  │
  ▼
[⑦ 决策] brand-review-decision-engine → 三态 + 拒答 + 完整风险项（risk_items + decision_trace + next_owners）
  │
  ▼
[⑧ 报告留痕] brand-review-report-memory → JSON + Markdown 报告 + 绑版本（version_gate：reviewed_hash / release_hash）
  │
  ▼
[⑨ 飞书输出] brand-feishu-review-adapter → 飞书表格 patch + 报告链接 + 飞书群消息（chat_message）
  │
  ▼
[⑩ 人工确认] PASS → sign-off 确认 / REVIEW → 转专业复核（§4.3 路由）/ BLOCK → 提交方修改后以新 content_version 重提
  │
  ▼
[⑪ 回流] 人工结论 → 候选规则/正负样本 → owner 审批后进生产（治理原则，非 PRD 要求）→ 蒸馏(L3) → 知识库迭代（评测，§11）
```

> **一条链路走通的判据**：从 ① 到 ⑨ 不需要人工介入即可产出「表格 + 报告 + 群消息」；⑩ ⑪ 是人工确认与回流，是闭环的后半段。**③ 待审对象标定是本链路里新增的防错闸门**（对应 §9.10）。

### 3.2 双轨校验明细：四层两侧各跑什么

| 层      | 名称     | **知识库侧**（带条款号+锚点+指纹）                                      | **模型侧**（带位置+理由，无库内依据）                        |
| ------ | ------ | --------------------------------------------------------- | -------------------------------------------- |
| **P0** | 法务合规红线 | 词表／正则／变体**确定性匹配**，命中即 BLOCK（毫秒级）；每个词有出处（逐字源/规则原文/等价写法三选一） | 语义边界核查：等义句、英文屈折形态、连字符变体（`FDA-approved`）、隐含声称 |
| **P1** | 安全与准确性 | 外部标准条款、产品描述库边界规则                                          | 语义理解：危险示范、使用姿势、功能越界；**抽奖要件／价格标注／命名规范／产品边界**  |
| **P2** | 通识与常识  | 内部正负样本（案例参照）                                              | 多模态推理：**画面／构图／水印／肖像／比例**、场景合理性               |
| **P3** | 措辞与表达  | Do not say / Say this instead 词表                          | 语境判断并给出替代表达建议（不改变主结论）                        |

> **关键**：① 四层同时启动，每层「知识库侧 + 模型侧」同时跑，**互不等待；层内两侧也不互相等待**；② P0 命中时结论可立刻返回 BLOCK（红线零延迟），其余层结果收齐后再并入问题清单；③ **没有主判与辅助之分**——每层的两侧都是完整的一遍审查，各自出问题清单，结论在最后一步按「同一问题取交集、不同问题走并集」合并（对齐判据：位置相同 + 类目相同 → 视为「同一个问题」）。

## 4. 统一数据契约 + 状态机 + 路由 + SLA

> 这一节是「skill 之间的接缝」——它定义多 skill 编排时**每一步传什么、状态怎么流转、结论转给谁、多久处理**。字段取自 `brand-content-review-agent/contracts/` 与 `knowledge-base/routing-policy.json`、`sla-policy.json`（实测）。

### 4.1 统一数据契约（skill 间传递的 payload）

**审查主 payload（对齐 PRD §5.4 结构化 JSON 规范）**：

| 字段                                                              | 说明                                                                                                                                                             |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `review_id` / `content_id` / `submitted_by` / `submitted_at`    | 审查 id / 内容 id / 提交人 / 提交时间                                                                                                                                     |
| `product_line` / `channel` / `content_type` / `content_version` | 产品线 / 渠道 / 内容类型（text·image·video·mixed）/ 送审版本（`model` 字段预留，仅产品信息需分型号时用）                                                                                        |
| `agent_version` / `rule_version` / `knowledge_version`          | **三个版本字段**（对齐 PRD §11.2 第 7 条「规则/知识库/模型版本绑定审查记录」）                                                                                                              |
| `decision` / `confidence` / `summary` / `issue_count`           | 三态结论 / 置信度 / 一句话总结 / 问题数量                                                                                                                                      |
| `issue_summary_by_category`                                     | 按「维度-子类」汇总问题数（如 `合规-医疗宣称: 2`）                                                                                                                                  |
| `report_url` / `record_url`                                     | 报告链接 / 记录链接                                                                                                                                                    |
| `risk_items[]`                                                  | 风险项：`risk_id / risk_type(维度-子类) / risk_category(维度) / severity / priority_tier / location / original_text / reason / evidence_doc / evidence_url / suggestion` |
| `next_action` / `next_owners[]` / `signoff_owner`               | 下一步动作 / 下一责任人 / sign-off 负责人                                                                                                                                   |
| `human_review`                                                  | 人工复核：`reviewer / reviewed_at / conclusion / comment`                                                                                                           |

> 工程补充（PRD §5.4 未要求，作为 skill 间**内部流转**字段保留，不写进对外 JSON）：`input_manifest`（文件/hash/抓取状态）、`coverage`（各模态抽取完成状态）、`decision_trace`（分层命中/消歧/阈值）。

**多模态抽取契约（`offline-extraction-result.json`）**：`provider` / `provider_version` / `content_hash` / `status(complete/partial/failed)` / `ocr_status` / `asr_status` / `keyframes_status` / `ocr` / `transcript` / `keyframes` / `observations` / `errors`。任何抽取结果必须回传素材 hash + provider/version + 覆盖状态 + 定位证据；未完成提取保留 `incomplete`，决策引擎不允许 PASS。

**输出契约（`feishu-adapter-output.json`）**：`idempotency_key`（`review_id + content_version` 幂等）/ `engine_result` / `table_patch`（飞书表格写回）/ `report_url`（报告链接）/ `mentions`（@角色位）/ `chat_message`（飞书群消息）。

**引用契约的模态差异（本次澄清）**：

| 模态       | 「逐字摘录」是什么                | 锚点                              |
| -------- | ------------------------ | ------------------------------- |
| 文字       | 原文照抄                     | `#para.35` / `#<表名>/<rec>/<字段>` |
| 图片       | OCR 抽出的图上文字原文            | `#img.N[@r120,80,400,300]`      |
| 视频·字幕/旁白 | ASR 转写原文                 | `#t.00:12:30-00:15:10`          |
| 视频·画面问题  | **无「逐字摘录」**，只有帧锚点 + 画面描述 | `#t.…` + 代表帧                    |

> **视频画面类问题（危险动作/构图/肖像）没有逐字摘录，只能给「帧锚点 + 画面描述」，据此只能判 REVIEW、不得单独定 BLOCK**——这与「模型侧单轨命中不得单独定 BLOCK」一致。

### 4.2 状态机

![图 4.2 状态机](fig-4.2-状态机.png)

> 图源 `state-machine.mmd`。对外状态 = 待审 / PASS / REVIEW / BLOCK / 已修改 / 已发布（PRD §8.2）；NEEDS_INPUT 是内部流转态。

> 文字版（内部流转态）：

```
NEEDS_INPUT ──(补齐素材)──▶ PRECHECK ──▶ 判定 ──┬──▶ PASS ──▶ HUMAN_SIGNOFF ──▶ RELEASED
   ▲                                            ├──▶ REVIEW ──▶ HUMAN_SIGNOFF ──▶ RELEASED
   │                                            ├──▶ BLOCK ──▶ 提交方修改 ──▶ 新 content_version 重新进 ①
   │                                            └──▶ 拒答（无结论）──▶ 转人工复核（给检索轨迹）
   └────────────────────────── 读不到/覆盖不全 ────────────────────────────┘
```

- **拒答不是状态**，是「没有结论」：给检索轨迹后转人工，不许当 PASS 放行。
- **BLOCK 后修改重提**：以新 `content_version`（新 hash）重新走 ①，是新单，不是覆盖旧单。
- **SLA 超时绝不自动改结论**（见 §4.4 clock_rules）。

> 对齐 PRD §8.2：多维表**对外状态** = 待审 / PASS / REVIEW / BLOCK / **已修改 / 已发布**；上图的 NEEDS_INPUT/PRECHECK/HUMAN_SIGNOFF/RELEASED 是**内部流转态**，对外只落 PRD 的 6 个状态。

### 4.3 责任人路由（取自 `routing-policy.json`）

| 命中词（match）                                                       | 转给（owners）     |
| ---------------------------------------------------------------- | -------------- |
| 医疗 / health / 功效 / safety / 消费者安全 / 睡眠 / 喂养                      | **医学顾问 + 法务**  |
| 产品 / 型号 / 功能 / 规格 / 容量 / 认证 / product                            | **产品负责人 + 法务** |
| 背书 / endorsement / testimonial / 达人 / influencer / 排名 / 绝对化 / 平台 | **法务 + 渠道负责人** |
| 本地 / 语境 / 文化 / locale / cultural                                 | **北美同事**       |

- 兜底复核人：**法务 + 北美同事**；PASS 转 **Sign-off 负责人**；BLOCK 转 **内容提交方**。
- @ 对象是**角色位**，取值从配置读，未配置时保留角色名并标「未配置」。

### 4.4 SLA（取自 `sla-policy.json`）

| 状态          | 优先级 | 目标时限    | 超时升级到               |
| ----------- | --- | ------- | ------------------- |
| BLOCK       | P0  | **立即**  | 项目统筹 + 内容提交方        |
| REVIEW      | P0  | 4 个业务小时 | 项目统筹 + 法务负责人        |
| REVIEW      | P1  | 4 个业务小时 | 项目统筹 + 对应专业负责人      |
| REVIEW      | P2  | 1 个工作日  | 项目统筹                |
| PASS        | any | 1 个工作日  | 项目统筹 + Sign-off 负责人 |
| NEEDS_INPUT | any | 1 个工作日  | 项目统筹 + 内容提交方        |

**计时规则**：input_manifest 齐全才开始计时；等提交方补料时暂停；每次 SLA 事件记录时区（`America/Los_Angeles`）与业务日历版本；**SLA 超时绝不自动改结论**。

> **对齐说明**：上表「人工复核时限」是工程自定（`sla-policy.json`），**PRD 未规定复核 SLA**；PRD 的响应性能要求见 §11.2「非功能需求（PRD §12）」。

## 9. 核心难点 = 设计决策（与 §8.3 的区别）

> **§8.3 答「缺什么、怎么补」**（工程施工面：OCR 收编、条款层、产品事实库、ASR…）；**本节答「不缺东西、但必须定性的裁决语义/设计原则」**（设计决策面：拒答建在哪、画面类怎么处理、PASS 边界、条款号/版本、OCR 权威性、中英同义…）。前者补能力，后者定规矩，两者互不替代。

### 9.1 拒答只能建在消费侧

- **决策**：索引层不提供拒答；拒答在 `kb-content-review`（L7 消费侧）实现，并给检索轨迹。
- **理由**：L6 实测 B 组三种模式 `hit@3` 全 0 却都返回 Top3——索引层永远给结果。
- **落地**：门限只判「够不够当参考」，成为**依据**必须**同时命中规则层**；拒答输出查了什么/几种模式/为何无依据/`no_hit_semantics` 原文。
- **验收**：B 组 query 一律拒答，无 PASS。

### 9.2 画面类零覆盖只能蒸，不靠改流程

- **决策**：明示「本库不覆盖画面类」；补规则路径是**蒸**。
- **理由**：9 案里图-1/2/3 知识库侧一次没命中；知识库轨只答「语言宣称越界」，不答「素材能不能用」。
- **落地**：`GUIDE.md`、输出模板、registry `not_proves` 显式写明；场景域逐域盘点成蒸馏工单。
- **验收**：场景域表里画面类「无规则」域数逐季下降。

### 9.3 外部标准条款层为空（顺序不可颠倒）

- **决策**：解权限 → 抓取回验 → 抽条款 → 编 `E-2` → 蒸规则。（对应 §8.3 G2，本处定「顺序」）
- **理由**：外部标准库 2,038 单元里没有「条款」类型；权威指南（睡眠/喂养/安全标准）因 PDF 缺下载授权进不来。
- **落地**：三批并行——① 立刻抓自有站 166 条 + 22 条平台政策直取；② 解飞书 scope；③ FDA 24 条换官方源。
- **验收**：FDA/FTC/平台政策条款入 `E-2`，摘录能在抓取正文逐字命中。

### 9.4 PASS 覆盖边界对扰动不稳

- **决策**：覆盖信号加扰动回归用例；PASS 出口一律附覆盖依据。
- **理由**：删掉图上两行 logo 文字，BM25 28.755→24.988 就把「拒答」翻成「PASS」。
- **落地**：增删 logo/标点/换行/大小写/全半角进回归集；PASS 前置写成硬规则（不是「没查到」就算过）。
- **验收**：扰动用例不翻态；PASS 记录都带「命中哪条允许表述」。

### 9.5 条款号永久占号 + 版本两层号（可复现）

- **决策**：条款号从 L4 台账只读不重编；`kb_version`（每类库独立）与 `release_id`（跨库组合发布）两层不混。
- **理由**：同一个 H07 报出两个条款号（W-1.6 / W-1.53）就是「只绑 v0 常量」的后果。
- **落地**：发 `release_id`（如 rel-0001 标注试用版未发布）+ `versions.jsonl` 版本行；审查记录绑「release_id + kb_version + 规则 source_sha256」。
- **验收**：重跑新发号=0；任意审查记录能定位到当时规则版本。

### 9.6 中英同义与屈折/连字符变体漏检

- **决策**：补中英同义族 + 英文屈折形态；连字符变体单列（`FDA-approved`/`FDA approved`）。
- **理由**：中文「不会疼」、英文 `increased her milk supply`、`FDA-approved` 都漏判 PASS。
- **落地**：复用 L5 `word_level_grounding`（逐字源/规则原文/等价写法三选一，对不上判凭空不进表）。
- **验收**：金标准里这三类正例命中；`dropped_ungrounded` 留痕。

### 9.7 产品事实库是 PASS 的前置依赖（品类级 + 预留型号字段）

- **决策**：无品类功能边界/型号差异/认证/测试报告时，只能通用风险预审，不能自动 PASS；**一版不区分 SKU 粒度，判断品类即可，JSON 预留 `model` 字段**。
- **理由**：P1 层「产品功能边界、命名规范、价格标注」依赖产品事实库，当前该库只有 9 个 L2 单元。
- **落地**：合并产品事实库 + 审批队列（规格由产品 owner，客观/比较由产品+法务，健康/安全/功效由产品+法务+医学）。
- **验收**：活动事实库在 owner 审批前保持为空；未审批事实分流 REVIEW。

### 9.8 OCR 输入版本敏感

- **决策**：素材固化到带指纹单一版本；关键 token（资质缩写/数字/型号）回原图局部复核。
- **理由**：`IBCLC` 读成 `IBCC` 就少一条命中。
- **落地**：OCR 引擎升级版本化 + 留备份；复用闸门 `ocr_cache_reusable()`。
- **验收**：送审与复核读同一 `sha256`；引擎升级后关键 token 复核通过。

### 9.9 OCR 权威引擎 vs 多模态模型直读

- **决策**：macOS Vision（带指纹可回源）= 权威；模型直读（无指纹）= 仅存疑复核。
- **理由**：模型直读产出过不了引用契约防幻觉硬闸门（锚点+sha256+逐字摘录）。
- **落地**：冲突时以 Vision + 回原图局部复核为准。
- **验收**：引用契约里所有图片依据锚点都来自 Vision OCR 结果。

### 9.10 判定对象错位（审错了对象）

- **决策**：输入侧**显式标注「待审对象」边界**——哪段是「被审文案」，哪段是提问/批注/水印/上下文，后者不参与判定。
- **理由**：技术方案实测两个事故——文-3 把**用户提问里的示例句**当成被审文案判了 BLOCK；图-4 把**中文列内部批注**（「不用设计，拿来打样即可」）当外发文案审。批量+多模态下这种「审错目标」是系统性误判，比漏判更隐蔽。
- **落地**：`intake_router` 产出待审对象边界标注（§3.1 第③步）；`risk_items` 每条必须回指到待审对象内的具体位置，指不到就不输出该条。
- **验收**：金标准加「提问/批注/水印混入」对抗用例，误判归零。

### 9.11 多语种审查（德语等本地化，一版模型侧兜底 + P0 词同义族）

- **决策**：一版**多语种内容只走模型侧**，命中标注「无库内依据」倾向 REVIEW；同时给**关键 P0 红线词建多语种同义族**（并入 §9.6 同义族工作）；其他语种（法/意/西等）延后。
- **理由**：知识库 509 条规则是**中/英文**，但渠道含德语站（`de.momcozy.com`），文-2 实测就是德语站（抓到 `schmerzfrei` 等）；一版不做全语种词表（成本高，且多语种审核依赖本地复核）。
- **落地**：P0 红线词（医疗功效/绝对化/FDA approved 等）建德/英同义族进 L5；其余多语种内容走模型侧，产出标注「无库内依据」。
- **验收**：金标准加德语用例（`schmerzfrei` 等），P0 同义族命中；多语种模型侧命中一律 REVIEW、不单独 BLOCK。

## 12. 风险与依赖（对齐 PRD §16）

| 风险/依赖       | 影响         | 应对                             |
