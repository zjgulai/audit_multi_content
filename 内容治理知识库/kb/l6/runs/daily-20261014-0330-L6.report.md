## 6. 三模式对比（A/B 两组查询）

查询集 14 条：A 组（库里有对应内容）中英各 4 条，B 组（库里没有对应内容）中英各 3 条；每条在三种模式下各取 Top3，逐条人工判断。判定口径：hit_at_3 = Top3 里至少一条与查询意图相关；precision_at3 = 相关条数/3。A 组测检索能力，B 组测拒答行为。判断为人工逐条给出，缺判断记 unknown 不算命中。三种模式都不带相关性阈值，一律返回 Top-N —— 因此 B 组是否拒答要按返回结果是否相关来读，而不是按有没有返回结果来读。

**模式对比结论（如实写，包括不好看的那一面）**

1. **A 组召回没有因为上了向量而提升**：bm25_only 已 hit@3 = 1.0（8/8 全中），hybrid 1.0（5/8），vector_only 只有 0.8。A 组按任务要求用「库里现成的等价词」构造，属词面型查询，是 BM25 的主场；2019 年的多语 MiniLM 对这类短查询的语义邻域铺得偏宽。

## 11. 自主决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | embedding 按必装项处理：装 fastembed（ONNX）并复用已有权重，不回退 bm25_only | 不能让向量路径成为没跑过的代码路径；缺 embedding 才允许回退，而本机条件满足（onnxruntime 就绪 + 外网可达） |
| D2 | 判定模型能不能用靠真实握手：发一次 embedding 请求，校验返回 384 维、全有限、范数正常 | 端口开着或依赖存在都不算数；握手结果写进 registry |
| D3 | 超长单元按段落/句边界分段（每段 ≤120 token），单句超限按 token 二分硬切；不截断 | 实测该模型在 128 token 处静默截断（两段只共享前 300 字的文本得到完全相同向量），31,450 字的单元只进约 1% 内容 |
| D4 | 分段上限取 120 而不是 128 | 空串就已占 2 个特殊 token，贴边切有被截断的风险 |
| D5 | 切块时把换行与标点留在前一块，保证各段顺序拼接**逐字等于原文**，并写进自检 | 第一版切句丢了换行符，1,899 个单元里 168 个拼不回去；不修就等同静默丢内容 |
| D6 | BM25 侧不装任何库，继续用自实现倒排；先拿耗时再谈换不换 | 实测单查询 p50 0.044 ms、吞吐 2.25 万 q/s，比 L5 扫 1MB（631ms）快约 1.4 万倍；换库还会改切词与得分口径，把已跑通的索引与自验作废 |
| D7 | 向量与 BM25 统一用全局 doc_id（单元在可用集合里的序号）当融合键 | 上一版向量用矩阵行号、BM25 用文档号，1,573/1,578 对不上，融合会张冠李戴；本版加了编号同源断言 |
| D8 | 向量只建一套多语索引，不按语言分库；BM25 才分语言子索引 | BM25 必须分是因为切法不同；向量用同一多语空间，中文查询才可能碰到英文素材 |
| D9 | A/B 分组与判断标准照任务来：A 组用库里现成的等价词（词面型），B 组选语料 0 命中的主题 | A 组词面型会让 BM25 占优，这是构造使然，如实写，不挑查询把数字做漂亮 |
| D10 | 相关性判断给三档（相关/弱相关/不相关），命中率只按「相关」算；B 组一律不相关 | 避免用「弱相关」抬命中率；B 组返回内容确实都不对题 |
| D11 | 把「RRF 分不能当阈值」写进 registry.known_limitations | 实测 RRF Top1 分恒为 0.016393（名次倒数），A/B 两组看起来一样高；下游拿它当相关性阈值会被误导 |
