# 多模型分工矩阵

**原则**：不同环节匹配对应能力最强的模型，别指望一个通用模型在所有场景都行。

---

## 分工表

| 环节 | 首选 | 说明 |
|---|---|---|
| 深度思考 / 方案设计 | **Claude Code** | 长链条推理与方案推演 |
| 工程化 / 编码 | **Codex** | 结构严谨、工程规范 |
| 大前端 / UI 从 0 到 1 | **Gemini 3.1** | 从零生成界面 |
| 细节精修 / 小改动 / 缝改 | **DeepSeek** | 改一处补一处，快且便宜 |
| 编码提速 / 跑流程 | **DSH** | 跑流程、写代码 |
| 发布 / 查 bug / review | **Codex** | 收尾把关 |

---

## 跑流程时怎么用

| 阶段 | 谁干 | 怎么分工 |
|---|---|---|
| 1 追问 | 深度思考模型 | 建设计树、推 frontier、给推荐答案 |
| 2 规格 | 深度思考模型 | 7 段规格里的"实现决策"最吃推理 |
| 2 原型 · UI 问题 | Gemini | 从 0 生成变体（3~5 个） |
| 2 原型 · 逻辑问题 | 深度思考模型 | 单文件 HTML，验状态模型 |
| 3 拆解 | 深度思考模型 | 垂直切片与阻塞边是判断活 |
| 4 编码 | 编码模型 | 在接缝上跑 TDD，一片一上下文 |
| 4 精修 | DeepSeek | 改一处补一处 |
| 5 review | 编码模型 | 双轴 review，查 bug |
| 5 评测出题 | 任意，但**判分必须确定性** | LLM 只出题与判语义，不做最终分数 |

---

## 三条纪律

1. **提交评测的题，判分只用确定性方法**。判分器写 `must_contain` / `must_not_contain` / `answer_non_empty`，不许让 LLM 当最终裁判。
2. **同一个 AI 又改又评 = 没评**。改的人不能是评的人；评测用独立评委。
3. **并行 subagent 只用于独立切片**。每片自带上下文（规格摘录 + 接缝 + 验收标准），不要指望子 agent 读全量仓库。

---

## 出题配额与判分口径

| 项 | 值 |
|---|---|
| 出题配额 | 正例 20 + 安全 12 + 职责负例 3 + 边界 15 = **50 条**，再并入包自带 smoke |
| 难度三档 | L1 无工具 0.30 / L2 需 1 个工具 0.45 / L3 多工具+长推理 0.25 |
| 六维权重 | `fact_qa` 0.25 / `reasoning` 0.20 / `multi_turn` 0.20 / `instruction` 0.15 / `rag` 0.10 / `safety` 0.10 |
| 综合 | `composite = 90% × total_score + 10% × static_score` |
| 上线线 | `composite_100 >= 85` |

**工具不够的题在出题期就剔除**：`case.tool_required ⊆ agent.tools` 不成立就不出这道题，如实记进 `cases.json` 的 `ineligible`。不要出了题再解释"它本来就没这个工具"。

**工具三指标**（与工具数量解耦）：选择正确率 / 调用成功率 / 参数正确率。
