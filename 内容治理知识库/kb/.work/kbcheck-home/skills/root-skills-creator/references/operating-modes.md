# Operating Modes - 模式分级

**核心原则**: 按用途选择门禁轻重，不做一刀切。

同一套创建流程，按 skill 的用途决定做到多深。避免"记笔记模板也要走完整发布流程"和"团队 skill 没有门禁"两个极端。

## 两级模式

| 维度 | **explore**（探索） | **release**（发布） |
|------|--------------------|--------------------|
| 适用 | 个人原型、验证想法、临时工具 | 团队共享、对外发布、生产依赖 |
| 意图对话 | 1 轮核心问题 | 完整核心分叉澄清（≤2 轮） |
| 评测 | 至少 1 次 with/without 对比 | 完整 RED→GREEN→REFACTOR + 压力场景 |
| 触发测试 | 可选 | 必须（positive/negative loading evals） |
| 六维度评分 | 参考 | 必须：封顶后轨道 C >= 85 且调用门槛通过（root-skills-eval） |
| 自动优化 | 可选 | 未达标才必须：opt 只改 `{skill}-fix/` 副本，永不写回正在创建的目录 |
| DoD 清单 | 简化 | 完整 |
| 打包 | 不需要 | 必须可打包可安装 |

## 选择规则

- **默认 explore**——"Add deeper profiles only when earned"（只有在证明需要时才加深度）
- 升级到 release 的信号：
  - 其他人将依赖这个 skill
  - 会跨会话/跨项目复用
  - 输出会被当作交付物提交
- 不确定时先 explore 跑通，再问用户是否升级

## 渐进式采用

不要一开始就做全套门禁。顺序：
1. explore：骨架 + 最小评测（证明有价值）
2. 若值得：补触发测试 + 评分（证明可用）
3. 若发布：补 REFACTOR 压力测试 + DoD + 打包（证明可交付）

每层只有上一层通过才进入。
