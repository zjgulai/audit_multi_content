# LoD 升降级与 L4 纠错：什么时候上移，什么时候必须退

> 来源：Kb2Agent（MKD）§8.3 LoD 升降级触发判据 + §1.5 L4 纠错链路，本技能裁剪。
> **用途**：`lod-ladder.md` 判「该蒸到哪一层」，本文件判「**什么时候该换层**」——升级要证据，降级也要证据，两个方向都得有闸门。

---

## LoD 升降级：8 条阈值

不是所有知识都该往 L4 迁移，也不是所有 L4 Skill 都该永远待在 L4（§8.3 · "不是所有 L4 Skill 都应该永远保持在 L4"）。

### 升级条件（向更高 LoD 迁移）

| # | 阈值信号 | 方向 | 含义 |
|---|---|---|---|
| **升 1** | 同类查询 30 天命中率 **> 80%** | L0/L1 → L2/L3 | 知识被高频复用，值得固化 |
| **升 2** | 这类任务的多步推理耗时 **> 15s** | L1/L2 → L3/L4 | 推理成本高，应预提炼 |
| **升 3** | 人工纠错率 **< 3%**，**连续两个月** | L2/L3 → L4 | 知识已稳定，可固化为 Skill |
| **升 4** | 用户**复用同一查询结果**做下游决策 | 任意 → L4 | 知识已成为流程节点 |

### 降级条件（回退到低 LoD）

| # | 阈值信号 | 方向 | 含义 |
|---|---|---|---|
| **降 1** | Skill 命中正确率**连续下降 > 5%** | L4 → L2/L3（保留原始案例） | Skill 已过期或失真 |
| **降 2** | 新增 Skill 使用量 **< 5 次/月** | L4 → L1（转向量检索） | 固化成本无法被复用摊薄 |
| **降 3** | 业务规则**月均变更 2 次以上** | L3/L4 → L1 | 知识更新速度超过 Skill 维护速度 |
| **降 4** | 用户反馈「答案太模板化，缺少灵活性」 | L4 → L2（保留原子洞察） | Skill 过度约束了回答空间 |

**五条读法与配套动作**：

1. **升 3 是唯一一条「允许」升到 L4 的稳定性证据**，而且要求**连续两个月**。配合 `half-life-routing.md` 那条反直觉结论——高频不是升 L4 的充分条件，**变更慢 + 纠错率低才是**。升 1 只到 L2/L3，不给 L4。
2. **8 条阈值里 4 条是降级，比例 1:1**。这不是对称美学，是**防棘轮**：只有升级判据的系统会单向堆积到 L4，然后集体过期。上一节那条官方建议是对的——**每次更新 Skill 必须跑回归，只有分数提升才允许覆盖入库**（§8.2.4 · "只有当 9 维度综合得分提升时"）。**升要证据，降也要证据，两个方向都得有闸门。**
3. **降级方向必须回退到「保留原始案例」的那一层**，不是单纯删 Skill。降 1 写明「保留原始案例」，降 4 写明「保留原子洞察」——**降级丢的是契约，不是底料**。底料丢了，下次想升回来就得重新解析一遍原材料。
4. **降 2「< 5 次/月」和升 1「命中率 > 80%」量的是两件事**：命中率量「准不准」，使用量量「值不值」。一个 Skill 可以又准又没人用——那种情况下固化成本永远摊不薄，该降。
5. **这 8 条阈值是判据，不是采集方案**。素材没写这些数怎么采、多久采一次、谁来采。**这是素材未覆盖的缺口**：落地时每个 Skill 至少要挂上「命中率 / 正确率 / 调用量 / 规则变更次数」四个计数器，否则 8 条判据一条都跑不起来。`【review 待人工定】`（§8.3 · "以下是升降级的判断标准"）

## L4 纠错链路：五步回滚

L4 的错误会以**最高复用效率**扩散——所有调用这个 Skill 的 Agent 一起受影响（§1.5 · "错误会以最高复用效率扩散"）。所以 L4 必须比别的层多一条向下回溯的路。

### 先看信号：L4 不会报错，只会变味

L4 出错通常不触发系统告警，靠间接信号暴露（§1.5 · "不会触发明显的系统告警"）：

- 用户说「Agent 给了很像对的、但方向不对的建议」——**注意这句里没有"错"字**
- 下游业务指标出现无法解释的下降（转化率、决策准确率）
- 同类任务的 Skill 执行成功率**悄悄**下滑，幅度不触发任何阈值告警（§1.5 ·「悄悄降到」；素材原举的具体百分比属易漂移量，本文件不复述）
- 某类查询开始产出「正确但无用」的答案：结构完整、逻辑空洞

第三条最该盯的其实是「**悄悄**」——它说明这类退化在监控面板上是渐变的，没有单一时刻可以归因。第四条最阴：结构完整所以评测器不会判它错。

### 五步回滚

```text
L4 Skill 出错
  ↓ 步骤 1：隔离受影响的 Skill 版本，暂停自动迭代
  ↓ 步骤 2：找到最近一次「业务验证通过」的版本，回滚
  ↓ 步骤 3：沿该 Skill 的 created_from 锚点，回退到它实际来源的知识层
  ↓ 步骤 4：继续回退到原始来源文档，验证其是否仍然有效
  ↓ 步骤 5：确认根因后，从正确的 LoD 层重新蒸馏
```

**步骤 3 要说清**：不是「一律回退到 L3 知识图谱」——**很多 L4 Skill 根本没有图谱支撑**（§1.5 · "knowledge_layer: L2 # 该Skill基于的知识层级"）。回滚要沿着这个 Skill 自己的 `created_from` 锚点回到**它实际基于的那一层**，锚点指向哪就回哪。

**回滚要带够的锚点**（每个 Skill 必须记，§1.5 · "每个 Skill 必须记录的纠错锚点"）：

| 字段 | 作用 |
|---|---|
| `created_from.source_docs` | 向下追溯的入口，步骤 4 用它找原始文档 |
| `created_from.knowledge_layer` | 步骤 3 回哪一层，由它决定 |
| `created_from.raw_cases` | L0 原始案例清单，出错时可回看 |
| `rollback_to` | 上一个业务验证通过的版本号 |
| `last_validated` + `validated_by` | 「验证通过」是谁在什么时候判的 |

### 关键原则：没有前一版本锚点，不许覆盖入库

> 每次 Skill 版本迭代，**必须保留上一个「业务验证通过」的版本作为回滚点**。**不允许在没有前一版本锚点的情况下覆盖入库**（§1.5 · "不允许在没有前一版本锚点的情况下覆盖入库"）。

这条是全文件最值钱的一条，理由是**成本收益不对等**：保存一个版本快照的成本极低，但它把 L4 错误的平均修复时间从「数天」压到「数小时」（§1.5 · "从'数天'缩短到'数小时'"）。

它反的是工程直觉：版本快照看起来是「冗余的旧东西」，清理它看起来像好习惯。这里的判据相反——**没有回滚锚点的 Skill 一次都不许覆盖入库**，宁可多存一份快照。

顺带一条推论：`last_validated` / `validated_by` 为空，等于这个 Skill 没有可回滚的锚点。**回滚点必须是被人判过「业务验证通过」的那一版，不是「还在的最新那一版」。**
