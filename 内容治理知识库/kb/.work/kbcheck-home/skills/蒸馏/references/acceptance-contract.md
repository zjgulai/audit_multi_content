# 验收契约：蒸之前先写死"什么叫过"

> 来源：Kb2Agent 的 acceptance contract（dataset + thresholds + regression + 四角色签署）与 capability-map 的 `forbiddenClaims`，按本技能裁剪成开工前就能写完的一页。
> **一句话**：**没写验收契约就开工 = 蒸完才争论"这算不算蒸好了"。**

---

## 一、开工前必须写死的四行

在阶段 0 结束时填完，写在蒸馏记录顶部：

| 字段 | 写什么 | 反例 |
|---|---|---|
| `must_include`（≥2 条） | 蒸出来的正文**必须**能回答的具体问题 | 写"要覆盖会议要点"（没法判） |
| `must_not_include`（≥1 条） | 明确**不许**出现的：重复已有 Skill 的内容 / 编造的出处 / 与素材无关的常识 | 留空 |
| `confidence_floor` | 每条判断的最低佐证要求（本技能默认：≥2 处跨章节独立佐证） | 写"尽量多" |
| `owner` | **谁为这条判断的正确性负责**（具名人，不是"团队"） | 写"大家" |

**owner 为什么必须有**：Kb2Agent 的结论是——写的人不承担读者用错信息的后果，是低质量知识持续产生的结构性原因。没有人名，就没有质量激励。

---

## 二、四条入库验收谓词（沿用，收口到这）

`structural_completeness` / `source_traceability` / `no_duplication` / `boundary_declared`，代码类素材另加 `code_executable`。
**全过才收；缺一条不产出正文，只产出一份缺口清单。**

---

## 三、交付物硬要求（v1.1.2 起）

除了 SKILL.md 与 references，蒸馏产物必须自带：

| 要求 | 判据 |
|---|---|
| **tests ≥ 2** | SKILL.md 目录下 `tests/` 至少两条：一条正例（该触发且做对）、一条边界（不该触发或该追问）。缺 tests 的产物**不许入库** |
| **E 级上限 = E2** | 蒸馏产物只能声明到 **E2（草稿级、可审查、未获批）**；正文与记录里**不许写"生产就绪""已上线""已验证可用"** |
| **productionReady / canonicalWrite 恒 false** | 不自动写回权威库、不自动覆盖已装 Skill——**写回是人的动作** |
| **出处带内容指纹** | 每条判断除时间戳/板位外，追加素材片段的内容指纹（前 16 位哈希或逐字锚句），防素材改版后锚点漂移 |

---

## 四、负例校验（fail-closed：过不了负例就不算过）

产物定稿前，用下列负例反查一遍。**任一条命中 → 回炉，不许发布**：

| # | 负例（拿来打自己的产物） | 命中说明 |
|---|---|---|
| N1 | 把最关键的那条判断删掉，Skill 还成立吗？ | 成立 → 说明这条判断没进正文或在凑数 |
| N2 | 把素材换成同类但结论相反的一份，产物会变吗？ | 不变 → 说明产物是模板填空，不是从素材蒸出来的 |
| N3 | 把每条判断逐条追问"你从素材哪里来的"，都答得出吗？ | 答不出 → 出处造假 |
| N4 | 产物里有几条是"裸模型自己也会说"的？ | >0 → 同质化，删掉 |
| N5 | 产物里有没有把"待确认项"悄悄写成结论？ | 有 → 违反"不猜"纪律 |
| N6 | 有没有把实时/易变数据写成了判断？ | 有 → 应该走 CACHE 档，回 §入口四档 |

## 五、四角色署名（重资产场景可选）

素材涉及对外承诺、合规、财务口径时，按 Kb2Agent 的四角色分离署名——**四类人各自签各自的那一行，一个人签四行等于没签**：

| 角色 | 对什么负责 |
|---|---|
| 内容负责人 | 判断本身对不对、边界写没写清 |
| 证据负责人 | 出处是否可追、指纹是否对得上 |
| 测试负责人 | tests 是否真跑过、负例是否真拦得住 |
| 批准人 | 是否允许从 E2 升级到可发布 |

**轻量场景**：至少要有 `owner` 一个人名；四角色全签只在重资产场景要求。
