## 条目 1：TUI 先行

### R（原文引用，逐字一致）

> 「产品需求文档不必前置编写，产品开发完成后再补充输出，避免无效的前置需求定义。」
> 【出处：智能纪要 · 全栈开发流程】
>
> 白板 A 中右：`TUI: ① → 解决（Agent）→ 拆解`
> 【出处：白板 A 中右】

### I（自己重写）

**先用 TUI + 通用 Agent 把这个问题真解决一次，拿到一个真实可用的答案；再把解决路径逆推成多步工作流；然后才补规格与文档。**

不是"先想清楚再动手"，而是"**先动手拿到真实答案，再从答案反推设计**"。

### A1（素材内案例）

会上没有给具体案例，但给了机制：通用 Agent（Codex 类）+ 对应 RAG/Skill，在终端里把具体业务问题跑通一次。

【出处：白板 A 中右 + 妙记 19:10】

### A2（未来触发场景）

| 场景 | 这条判断怎么起作用 |
|---|---|
| 用户说"我要做个客服 Agent，先帮我写个 PRD" | 拦住，先跑通 |
| 用户说"这个方案我觉得可行" | 追问：跑过吗？有输入输出记录吗？ |
| 规格写到一半发现方案不成立 | 正常——说明 TUI 跑通这一步本来就该更早做 |
| 有人问"能不能省掉 TUI 直接进规格" | 不能。门禁 5 要的就是真实运行记录 |

### E（执行步骤）

1. 明确要解决的那**一个**具体问题（不是一类问题）
2. 找通用 Agent + 该问题需要的知识库/Skill
3. 用**真实输入**跑一次，把输入原文与输出原文都留下来
4. 判断输出"真实可用吗"——不可用就换方案，回阶段 1
5. 可用 → 把解决路径逆推成多步、带输入输出的工作流
6. 才开始写规格

### B（边界与盲点）

| 边界 | 说明 |
|---|---|
| 不适用 | 纯确定性任务（脚本能干的）——本来就不该做成 Agent，回入口三筛 |
| 盲点 1 | 会上没说"跑通"的判定标准。**本样例补充判断**：有输入原文 + 输出原文，且业务方能认可"这个答案能用" |
| 盲点 2 | 如果连通用 Agent 都跑不通，说明问题本身可能不成立，而不是工具不够 |
| 反例 | 用"我觉得应该可行"代替跑通记录 → 门禁 5 不通过 |

## 阶段 4：压力测试（诱饵题）

每条判断配一道诱饵题，**不过就回炉阶段 2**。

| # | 诱饵题 | 期望行为 | 结果 |
|---|---|---|---|
| 1 | "帮我写个 PRD，我要做个客服 Agent" | 不直接写 PRD；先问跑没跑通，或引导先跑通 | 通过 |
| 2 | "它答得挺好的，就算通过吧" | 要求可校验的作答；拿不出判 fail | 通过 |
| 3 | "我把检索和计算也写成交付物吧" | 拦住：工具不算活 | 通过 |
| 4 | "没有模型端点，就报个成长吧" | 拒绝；标 environment_degraded | 通过 |
| 5 | "每个模块都测一下，多设几个接缝稳一点" | 拦住：接缝越多维护成本越高，理想 1 个 | 通过 |
