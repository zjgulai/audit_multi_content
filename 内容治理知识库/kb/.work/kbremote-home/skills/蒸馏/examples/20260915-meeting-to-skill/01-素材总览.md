## 四步拆解

### 结构

会议按**两条线**讲：

- **线 1（流程线，白板 B）**：① 问题（调研）→ ② 方案/规格 → ③ 目标+拆解 → ④ 开发 → ⑤ 测试/验证，右侧挂模型分工矩阵与「交接」。
- **线 2（演进线，白板 A）**：技术演进路径 → 原生 Agent 本质 → TUI 先行 → 知识库/蒸馏 → 数据流（embedding/context → LLM → output）。

两条线的关系：**线 2 是"为什么这么做"的依据，线 1 是"具体怎么做"的步骤。**

### 解释（每块的核心主张）

| 块 | 核心主张 |
|---|---|
| 流程线 | 用 skill 链把每个阶段固化，别靠人记 |
| 模型分工 | 不同环节匹配对应能力最强的模型 |
| 交接 | 多 Agent 协同靠交接文档，不传全量上下文 |
| 演进线 | 垂类 Agent 优于通用 Agent |
| TUI 先行 | **先跑通再定义**，PRD 后置 |
| 知识蒸馏 | 万物皆可蒸馏成 Skill |
| 验收根 | **以裸大模型为基准对比**，不如裸模型就是降质 |

### 批判（这一步给的是高价值候选）

| 问题 | 说明 |
|---|---|
| **自相矛盾**：既说"万物皆可蒸馏"，又说"不如裸模型就是废物" | 两条并列会得出"什么都要蒸"，但验收根会把大部分砍掉。**真正该蒸的是少数**——这是隐藏判断。 |
| **没讲透**：白板 B 右下 `Agent` 圈旁的 `3:1`、`e-1` 会上没展开 | 记为**待确认项**，不许猜 |
| **没讲透**："交接"讲了机制没讲**什么时候不用** | 补充判断：默认 `/compact` 就够，只有确认 compact 没价值才 `/clear` |
| **只在特定条件下成立**："skill 验收以裸模型为基准"——但没有模型端点时怎么办 | 判断需要补边界：拿不到作答时如实标环境降级，不谎报 |
| **口径冲突风险**：05 分钟章节讲"知识采集"，属于方向性描述 | 缺少可固化判据 → **这一块不蒸** |

### 应用

| 场景 | 会用到哪些块 |
|---|---|
| 要做一个新 Agent | 流程线全部 + TUI 先行 + 验收根 |
| 要把会议沉淀下来 | 蒸馏块 + 验收根 |
| 要判断某个 Skill 该不该留 | 验收根（裸模型对照） |
| 要交接给同事 | 交接块 |
