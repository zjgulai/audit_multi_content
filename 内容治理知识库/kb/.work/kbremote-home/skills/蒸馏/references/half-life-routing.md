# 半衰期刻度：入口判断的第一把尺

> 来源：Kb2Agent（MKD）§2.5 知识半衰期 + §8.1 何时不该用 RAG + 导论洞察 3 与反模式 2，按本技能入口四档裁剪。
> **用途**：`intake-routing.md` 的 CACHE 档只写了「半衰期 < 7 天」一句，本文件是它的完整刻度——**先量半衰期，再决定蒸、缓存还是只留指针**。

---

## 为什么半衰期排在第一把交椅

决策矩阵告诉你**怎么处理**一份素材，半衰期告诉你**该不该处理**。顺序不能颠倒：先量半衰期，再选产品形态，再分类输入，再选输出形式（§2.5 · "但没有告诉你该不该处理"｜§2 五步路由表 · "第一步：看知识半衰期"）。

量错这把尺的代价不对等——其他维度判错是效率损失，半衰期判错是**给 Agent 喂过期事实**，而它答得和真话一样自信（§导论洞察 3 · "会让 Agent 用过期事实自信作答"）。

**量什么**：看这份素材里最关键的那个字段多久变一次，不要看整份素材。一份行业报告里夹着一张当月活动排期表，这份素材的半衰期是那张表的，不是报告的（§2.5 · "看最关键字段多久变一次"，量法参考 §2.6 Triage 输出里的 `half_life_days` 字段——**半衰期是入库时写出的数字，不是事后补的标签**）。

## 四档刻度表

| 半衰期 | 典型内容 | 处置 | 为什么 |
|---|---|---|---|
| **< 48h** | 竞品价格、库存水位、广告投放、当日销售 | **只存指针**：URL + 时间戳 + 摘要，查询走实时 API / NL2SQL | 入库即腐烂；Agent 从库里调到的是昨天的数，但它不会告诉你在看昨天的数（§2.5 · "入库即腐烂"｜§8.1 场景 2 · "任何形式的入库"） |
| **1 周 – 1 月** | 平台规则、竞品评论趋势、活动数据 | **缓存层**（Redis／数据库）+ TTL 自动失效。**不做 Skill，也不进向量库** | Skill 比数据更难更新，见下节（§2.5 · "Skill 比数据更难更新"） |
| **1 月 – 1 年** | 行业报告、竞品分析、SOP 文档 | **完整入库** + 更新提醒机制；每条带 `created_at` + `valid_until` | 稳定到值得建，但不稳定到可以不管。不标时间戳 = 让 Agent 永远相信它（§2.5 · "让 Agent 永远相信它"） |
| **> 1 年** | 方法论、原理性知识、历史决策记录 | **深度蒸馏，L4 Skill，持久化** | 高频复用时蒸馏的前期投入能被摊薄；反过来，频繁重建是纯浪费（§2.5 · "频繁重建，浪费资源"） |

判不出来就往下取整：**拿不准 1 周还是 1 月，按 1 周处理**——错判成缓存只是多查一次，错判成 Skill 是错到下次改版为止。

---

## 那条反直觉的：1 周到 1 个月的素材不该做成 Skill

直觉是「用得多就该固化成 Skill」。素材给的是**反过来**的：这个区间最该防的就是把它做成 Skill。

理由是**更新成本的量级不对等**：数据在缓存层里改一个字段就完了；Skill 是一份有触发条件、步骤、边界的执行契约，改它意味着重新提炼 + 重新验证 + 重新走一遍闸门（§1.2 · "可执行契约"｜§2.5 · "Skill 比数据更难更新"）。数据一天变三次，Skill 一天改不了三次——**变更周期短于你的维护周期，就该停在缓存层**（§2.5 · "变更周期短于你重建 Skill 的周期"）。

**两处独立佐证**（跨章节，不是同一段说两遍）：

1. **§2.5 表格**：这一档的「错误做法」栏直接写的就是「做成 Skill」，理由「Skill 比数据更难更新」。
2. **§8.3 降级条件**：另一条独立通道——已经做成 L4 Skill 的内容，一旦「业务规则频繁变更（月均 2 次以上）」，判据要求把它**从 L3/L4 退回 L1**（转为向量检索），理由「知识更新速度超过 Skill 维护速度」。这是同一机制的反向确认：**维护速度追不上变更速度，Skill 就要往下降**。

这条为什么值钱：它把「高频复用 → 升级到 L4」这条看似无条件正确的规则**加了一个反向约束**。8.3 的升级条件和降级条件拼起来才是完整判据——只看升级条件，你会把一份平台规则（用得很多、三个月改一次）蒸成 L4，然后每季度修一次，越修越跟不上。**高频不是升到 L4 的充分条件，变更慢才是。**

## `valid_until`：缺省 90 天，没有例外

**每条入库的知识单元必须带 `created_at` + `valid_until`。没写 `valid_until` 的，默认 90 天后触发人工复审**（§2.5 warning · "默认 90 天后触发人工复审"）。

这是硬规则，不是建议，理由有三层，各自独立：

| 层 | 讲的什么 | 出处 |
|---|---|---|
| 字段层 | 没有时间标注，Agent 无法判断哪条内容是新鲜的 | §2.5 warning · "Agent 无法判断哪条内容是新鲜的" |
| 信号层 | 库里有大量 `updated_at` 距今不到 48 小时的条目 = 已经踩了反模式 2 | §导论反模式 2 · "距今不到 48 小时" |
| 价值层 | 复利效应来自「矛盾已被标注」，没标注的矛盾 = 噪音 | §1.3 LLM-Wiki · "矛盾已被标注" |

**90 天是兜底不是标准答案。** > 1 年的那档可以标更长，< 48h 的那档根本不该入库。90 天的意思是「你没想清楚它的有效期」——想不到就写 90 天，让复审来兜。

## 头号反模式：库里混存不同半衰期的内容且无标注

素材把它列为「最常见也最危险的知识库反模式之一」，理由是这**直接废掉 Agent 的时效判断能力**（§2.5 warning · "最常见也最危险的知识库反模式之一"）。危险点在于它不报错：库照常召回，Agent 照常作答，只有人会看出这条三年前的竞品价格早就不能用了。

**清库信号**（三个都来自素材里各自独立的信号栏，凑齐任意一个就该动）：

- 库里出现大量 `updated_at` 距今不到 48 小时的条目（§导论反模式 2）
- 查询量每天不足 50 次，却在维护完整索引管道（§导论反模式 3 · "每天不足 50 次"）
- 团队查库前先问同事「这个库里的内容还准吗？」（§导论反模式 5 · "内容还准吗？"）

**处置不是删，是分档**：把 < 48h 的条目降级成指针，把 1 年以上的留在库里打上长 `valid_until`。混存的根因是入库时没量半衰期，删条目治不了根。

## 顺手省一次工：半衰期也是「别建库」的判据

半衰期判完，还有两个更省的出口，都在素材里给了**数字门槛**，够用的直接走：

| 判据 | 数字门槛 | 动作 | 出处 |
|---|---|---|---|
| 文档短 + 查询少 | 文档 < 100 页 **且** 查询频率 < 50 次/月 | 长上下文全文直读，别切块别建索引 | §8.1 场景 4 · "优先试长上下文基线" |
| 文档少 + 查询少 | 10 个文档这个量级 + 每天不足 50 次查询 | 直接长上下文，整体成本低一个数量级 | §导论反模式 3 · "低一个数量级" |

长上下文不是 RAG 的补丁，是在蚕食它的适用边界（§导论洞察 10 · "蚕食它的适用边界"）。**判据是三维的：低频 + 短文档 + 强上下文依赖，三条同时成立才走直读**——只有一条成立就老老实实建库。

## 与 `intake-routing.md` 的接口

| `intake-routing.md` 写的 | 本文件补什么 |
|---|---|
| CACHE 档：「半衰期 < 7 天（实时运营数据）」 | 拆成 `< 48h`（只存指针）和 `1 周–1 月`（缓存层 + TTL）两档，两档的**动作不同**——前者连缓存都不建 |
| PROCESS 档：三筛全中就走六阶段 | 补 1 月–1 年的 `valid_until` + 更新提醒；> 1 年才进深度蒸馏做 L4 |
| 十类素材表 J 行：「看板数字是实时事实 → 只留查询方式」 | 理由落到刻度上：BI 数字属 `< 48h` 档，只有**看板口径/指标定义**才升级到 1 月+ 档 |
| 完整度评分（0.67／0.33 那套）是**质量**维度 | 半衰期是**时效**维度，两把尺都量，互不替代 |

**一句话**：`intake-routing.md` 说「半衰期 < 7 天走 CACHE」，本文件说「7 天以内还要再分一次，48 小时以内连缓存都不建」。

## 边界（本文件不管什么）

- **管时效，不管质量**：判断密度够不够、裸模型会不会说，走三筛与 `triple-verification.md`。
- **管该不该存，不管存成什么形态**：该蒸到哪一层 → `lod-ladder.md`。
- **半衰期是估算不是测量**：素材没给字段变更频率时，本文件不提供猜法——按上面「判不出来往下取整」处理，并在蒸馏记录里留一行。
- **「三个月后会不会有人因为找不到这条信息而受损失」这条归档判据**仅出现在 §2.6 一处，独立佐证不足，本章**未据此产出判断**，出处留档待复用。`【review 待人工定】`（§2.6 · "会有人因为找不到这条信息而受损失吗"）
