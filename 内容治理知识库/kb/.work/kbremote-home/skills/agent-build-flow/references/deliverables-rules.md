# 数活儿规则：`deliverables` 怎么定

`deliverables` 是 `agent.yaml` 里**最容易写错、后果最严重**的字段——它决定"这个 Agent 能干几件活"，而评测范围、出题覆盖、职责负例全靠它对齐。**定义错了，评测通过但业务不认。**

---

## 一句话判据

> **交出去的东西不一样 → 两件活；一样 → 一件活。**

数活儿：`len(deliverables)`。

---

## 不算活的东西（写进去会让数量虚高）

| 会被误当成活 | 为什么不是 | 正确的落点 |
|---|---|---|
| 工具（搜索、计算器、翻译） | 工具是手段，不是交付物 | `tools` |
| Skill | 同上 | 提示词/引用 |
| 行为约束（不编造、不越权、要脱敏） | 是约束，不是一件产出的活 | 提示词 + 安全用例 |
| 同一交付物的变体（同一答复的不同长度） | 交出去的东西一样 | 同一件的 `fields` 或 `acceptance` |
| 流程步骤（先查再算再答） | 是过程，不是交付物 | `task_types` |

---

## 正例与反例

### 反例 1：把工具当活

```yaml
# 错：3 件活？其实只有 1 件
deliverables:
  - id: search
    name: 检索知识库
  - id: calc
    name: 数值计算
  - id: answer
    name: 业务答复
```

→ 交出去的东西只有"业务答复"一样。检索和计算是 `tools`。

### 反例 2：把变体当活

```yaml
# 错：长答复/短答复交出去的是同一件东西
deliverables:
  - id: long_answer
    name: 详细答复
  - id: short_answer
    name: 简短答复
```

→ 一件活，两种格式。合并为一件，用 `fields` 或 `acceptance` 描述。

### 反例 3：把安全约束当活

```yaml
# 错：不编造是行为约束
deliverables:
  - id: no_hallucination
    name: 不编造事实
```

→ 删掉。写进提示词，并配安全用例。

### 正例：确实有两件活

```yaml
deliverables:
  - id: answer
    name: 业务答复
    format: text
    fields: [结论, 依据]
    acceptance: 先给结论再给依据；引用资料时标出来源；没有依据就明说没有，不编造
  - id: weekly_report
    name: 周度汇总报告
    format: markdown
    fields: [本期问题TOP5, 处理率, 待办]
    acceptance: 数字要和台账对得上；对不上的要在报告里注明差异原因
```

→ "一条答复"和"一份周报"交出去的东西完全不同，是两件活。

---

## 硬校验：每件活都要能写出一条工作流

对每一件活，写出：

```
输入 → 步骤（≥2 步）→ 交付物（= 这件活的产物）
```

**写不出来的，不是一件活。** 三个自检问法：

1. 这件活有**输入**吗？（没有输入就没有触发场景）
2. 中间有**步骤**吗？（一步到底的，通常是个 `tool` 而不是一件活）
3. 产出的东西和别的活**长得不一样**吗？

---

## `acceptance` 必须用业务语言

`acceptance` 会被业务方读、被评测映射。**禁止写实现细节。**

| 错的写法 | 为什么错 | 对的写法 |
|---|---|---|
| 函数返回 HTTP 200 | 业务方看不懂，评测也映射不上 | 提交后 3 秒内返回受理结果 |
| `assert len(x) > 0` | 是实现断言，不是验收标准 | 结论栏不许为空；无依据时明确写"暂无依据" |
| 走 search_kb 工具 | 工具是手段不是标准 | 引用知识库内容时必须标出来源出处 |
| 准确率 > 0.9 | 没有说清在什么数据上、谁判定 | 在 XX 台账的 50 条真实问题上，人工判定正确率不低于 9 成 |

**自检**：把 `acceptance` 念给需求方听，他能不能判断"这条过没过"？不能就是没写好。

---

## 从规格反推的步骤

1. 从规格的「用户故事」段落，按"用户最终拿到手的东西"分组
2. 每一组给一个 `id` / `name` / `format` / `fields`
3. 对 `acceptance`：回到阶段 1 的第 5 问（怎么算成功），把它翻译成可判定的句子
4. 跑一遍硬校验：每件活写出一条工作流
5. 数一遍 `len(deliverables)`，问用户：**"这个 Agent 能干 N 件活，对吗？"**
