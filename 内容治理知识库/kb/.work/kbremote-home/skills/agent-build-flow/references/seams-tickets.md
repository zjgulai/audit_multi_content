# 接缝、垂直切片与拆解

这三件事在同一个阶段（阶段 2 尾 + 阶段 3）决定，写错了要到阶段 4 才暴露，代价最大。

---

## 一、接缝（seam）选择规则

**接缝 = 你打算在哪个边界上测试这个功能。**

| 规则 | 说明 |
|---|---|
| 优先用已有的接缝 | 不要为新功能造新边界 |
| 用尽可能高的接缝 | 高处的接缝覆盖更多行为 |
| 越少越好，理想是 1 个 | 接缝数量是维护成本 |
| 必须新建时，建在你能找到的最高点 | — |

**必须在写规格时和用户确认。** 后面 TDD 会严格按这个接缝来，**改接缝等于返工**。

### 反例

| 错的接缝 | 为什么错 |
|---|---|
| 给每个函数都造一个边界 | 接缝太多，重构时测试全废 |
| 在最低层的工具函数上测 | 覆盖不了业务行为，测了个寂寞 |
| 新功能另起一套边界 | 明明已有更高层的入口可用 |
| 接缝没定就先写测试 | 阶段 4 才返工，前面全白做 |

---

## 二、垂直切片（tracer bullet）四条规则

1. 每一片**纵向贯穿所有层**（schema、API、UI、测试），**不是**某一层的横向切片
2. 一片做完就能**独立演示或验证**
3. 每一片的体量要能**塞进一个全新的上下文窗口**
4. 需要预重构的，**先做预重构**（先让改动变简单，再做简单的改动）

### 反例

| 错的拆法 | 症状 | 后果 |
|---|---|---|
| 横向切片 | 工单叫"建所有表结构""写完所有 API" | 无法独立验证，进度不可见 |
| 一片太大 | 一片里 5 个模块 | 上下文爆掉，review 不了 |
| 一片太小 | "加一个字段" | 工单管理成本 > 收益 |
| 该预重构的不预重构 | 每片都顺手改同一处结构 | 每片都在解冲突 |

## 三、阻塞边 `blocked by`

**`blocked by` = 哪些工单必须先完成。** 没有阻塞边的工单可以立刻开始。

工作方式叫"**走 frontier**"：任何阻塞项都已完成的工单，就是现在能做的。纯线性链条就是从下往上。

### 工单模板

```
# <NN>: <标题>

**What to build：** 这张工单让什么端到端行为跑起来（用户视角，不是逐层实现清单）

**Blocked by：** 卡住它的工单编号/标题，或"无（可立即开始）"

**Status：** ready-for-agent

- [ ] 验收标准 1
- [ ] 验收标准 2
```

工单同样**避免写具体文件路径和代码片段**（原型片段例外，规则同规格）。

本地文件模式：**一票一文件**，放 `.scratch/<feature-slug>/issues/<NN>-<slug>.md`，按依赖顺序从 `01` 编号（阻塞项在前）。
**永远不要把所有工单塞进一个文件。**

## 四、例外：宽重构走 expand–contract

**宽重构**= 一次机械改动（改列名、改共享符号的类型），**爆炸半径**横跨整个代码库，一次编辑就打破成千上万个调用点，**任何垂直切片都落不了地**。

**不要硬切成曳光弹**，按三步走：

```
① expand（扩张）    新形式与旧形式并存，谁都不坏
② migrate（迁移）   按爆炸半径分批改调用点（按包、按目录），
                    每批一张工单，阻塞于 expand
                    因为旧形式还在，每批之间 CI 都能保持绿
③ contract（收缩）  确认没有调用者之后删掉旧形式，阻塞于所有 migrate 批次
```

**降级方案**：如果连分批都不能单独保持绿，就保留这个顺序，但让它们共享一个集成分支，**全部阻塞于最后一张"集成并验证"工单**——绿只在那张工单上承诺。

## 五、先 quiz，后发布

把拆解结果**编号列出来**，每张工单给三样：

- **标题**
- **Blocked by**
- **What it delivers**（这张工单让什么端到端行为跑起来）

然后问用户三个问题：

1. 粒度合适吗？（太粗 / 太细）
2. 阻塞边对吗？每张工单是否只依赖真正卡它的工单？
3. 有没有该合并或该再拆的？

**迭代到用户批准为止，再发布。** 不批准就重拆，不许"先发布再改"。

---

## 六、阶段 4 的接续

- 在**约定好的接缝**上做 TDD
- 接缝没确认 → **不写测试**（回阶段 2）
- 一次只推进**一个**垂直切片
- 每轮：红（先写失败测试）→ 绿（最小实现）→ 重构
- 每次循环跑：类型检查（频繁）、单个测试文件（频繁）、全量套件（最后跑一次）
