# Intent Dialogue - 意图对话

**核心原则**: 需求澄清只问核心问题，不搞无限访谈。

创建 Skill 前需要理解用户意图，但不要把用户拖进 20 个问题的问卷。只问影响方向的关键分叉，其余按合理默认推断。

## 规则

1. **每轮最多 1 个核心分叉问题**——当前最影响后续路径的那个。
2. **最多 2 轮**——两轮之后记录偏好推断，继续推进，不再追问。
3. **非核心缺口自行推断**——用上下文和常识给出合理默认，标注假设即可。

## 核心分叉问题清单

按优先级排序，只挑当前真正卡住路径的问：

| 分叉 | 问题 | 影响 |
|------|------|------|
| 目标 | 这个 Skill 要让 agent 能做什么？（一句话） | 决定整个正文 |
| 触发 | 用户什么话/场景下应该用它？ | 决定 description |
| 产出 | 期望的输出格式/交付物是什么？ | 决定 output contract |
| 验证 | 结果可客观验证吗（文件转换/提取）还是主观（风格）？ | 决定是否需要断言评测 |
| 模式 | 个人用还是团队发布？ | 决定 explore/release 门禁 |
| 边界 | 哪些相邻需求**不应**触发它？ | 防过度触发 |

## 从对话历史提取

如果用户说"把这个流程变成 skill"（当前对话里已经演示过工作流）：
- 先从历史提取：用了哪些工具、步骤顺序、用户纠正过什么、输入/输出格式
- 只把缺失的补问给用户，不重复已知信息

## 记录偏好推断

2 轮后仍未确认的，写入输出契约的说明区，格式：

```text
假设记录:
- [假设1]: 触发词按中文口语表达覆盖（如用户为中文用户）
- [假设2]: 输出格式沿用用户示例
请在后续确认，如不符随时纠正。
```

## 为什么这样做

- 用户通常不知道"好 skill"长什么样，问太多细节反而增加负担
- LLM 有良好的推断能力，非核心细节可以合理默认
- 核心分叉必须确认：方向错了，后面全白做
