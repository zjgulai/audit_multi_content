## 一、单元切分（你要的第 1 件事）

### 1.1 切分结果

995 个条款单元**逐个过判定**，不是抽样：

| 类别 | 数 | 说明 |
|---|---|---|
| 条款单元总数 | 995 | 该资源在 L2 的全部 `unit_type=clause` |
| → 切成可判定规则条款 | **104** | 见第二节 |
| → 逐单元拒绝（留台账） | 891 | 见第四节 |
| → 未登记 | **0** | 对账 `unaccounted == 0` |

每个单元都落了 `unit_id + anchor + source_sha256` 三件套（`ftc-health-products.units.jsonl`，995 行）。
**这三件是 `l3_gate.py` 判据 C1 每天逐条核的东西**，缺一样规则就进不了库。

### 1.2 ★ 先说这批单元的真实质量：不是「法条」，是网页正文被硬切

L2 侧 `splitters.clause` 的正式口径是「**一个法条 = 一个单元**」，正则可认 `第X条` / `§X.X` / `Art. N` / `Section N`。
但这份 FTC 政策是**网页**，没有法条编号可认，于是切分器退化成按长度/块切，结果是：

| 现象 | 数 | 证据 |
|---|---|---|
| 导航/菜单/页脚被切成「条款」 | 19 | `Skip to main content`、`Show/hide Enforcement menu items`、`Browse legal resources` |
| 正文被拼成 4,000 字符巨块（L2 的截断上限） | 26 | 一个单元里连缀着好几条条款 |
| 纯标题行独立成单元 | 19 | `B.`、`II.`、`IV.` |
| 残片（脚注引注/导航项/人名）独立成单元 | 302 | `[26] Deception Policy Statement , 103 F.T.C.`、`Chairman Andrew N.` |

**这直接影响你要的第二件事**：按「一个法条 = 一个单元」的口径，上面这些单元本身就是脏的。
我对它们的处理是 **在 L3 侧如实拒绝并写明「应在 L2 侧重切」**，而不是硬容错 —— 硬容错会把脏单元洗成看起来干净的规则。

## 二、可判定规则条款（你要的第 2 件事）

从 995 个单元里蒸出 **104 条**。每条能落表的形态是固定的六件：

```
rule_id ｜ article_no（留空，归 L4）｜ form（规则形态）
condition（判定条件）｜ threshold_or_lexicon（阈值/词表）｜ required_action（处理方式）
evidence_units[{unit_id, anchor, seg_anchor, source_sha256}]  ← 证据回指
```

### 2.1 形态分布

| form | 条数 | 含义 |
|---|---|---|
| `recommendation` | 37 | 宜为某行为（should） |
| `substantiation` | 20 | 须举证/实证支撑 |
| `disclosure` | 17 | 须披露/显著标识 |
| `prohibition` | 15 | 禁止性要求 |
| `mandate` | 11 | 须为某行为 |
| `scope` | 4 | 适用范围界定 |

### 2.2 质量分级（决定要不要人工先看哪一批）

| quality | 条数 | 含义 |
|---|---|---|
| `strong` | 68 | 判定条件里就含义务/禁止模态（`must`/`should`/`is responsible for`）→ **可直接落表候选** |
| `unconditional` | 35 | 无显式条件，按无条件义务适用（原句就是一句硬要求） |
| `weak` | 1 | 判定条件是交叉引用句（`See also…`），条件边界须人工确认 |

> 分级只按「判定条件是不是那句话本身」机械判，**不是法务判断**；104 条一律 `verification=待人工复核`。

## 三、★ 为什么这次是「本单自己蒸」而不是跑库里的蒸馏器

库里的 L3 蒸馏器 `kb/l8/l3_distill_run.py` **对条款单元是无条件拒绝的**。第 337–356 行逐字如下：

```python
    cl = grp.get("clause", [])
    if not cl:
        CONS["no_clause_text"] += 1
        rejected.append({... "未产出可用条款文本（正文为页面脚本或编码载荷）…"})
        continue
    for u in cl:
        CONS["clause_not_actionable"] += 1
        rejected.append({... "条款文本不可判定：非自然语言条款（页面脚本 / base64 编码载荷）…"})
```

`for u in cl:` 的循环体里**没有任何判定**，直接落 `rejected`。
**不是「判过了不合格」，是「根本没判」** —— 无论条款写得多清楚，一律判「不可判定」。

所以：**直接跑那个脚本，本单这 104 条会被整批丢掉**（这也是 `kb/l4/canonical/rules.jsonl` 至今 0 字节的机理：条款素材在 L3 被全数丢弃，L4 无号可发）。
本单因此在只读前提下自己实现判定，并在第四节给出**逐单元、可核对的拒绝理由**替代那句通用话。

> 另：`l3_distill_run.py` 会以 `w` 模式**覆盖** `kb/l3/rejected.jsonl`。本库真发生过拒绝台账
> 从 11,860 行掉到 1,053 行（`kb-clause-extractor` 红线①）。**本次未跑它，`kb/l3/rejected.jsonl` 未被触碰。**
