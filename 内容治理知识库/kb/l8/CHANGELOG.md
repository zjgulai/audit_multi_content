**触发**：当天对账报出「3 条 FDA 监管依据 404 失效」，差点被当成紧急事项去修数据。

### 改了什么

| # | 位置 | 原行为 | 新行为 | 为什么 |
|---|---|---|---|---|
| 1 | `UA` 常量 | 写死伪装 Chrome 122 的 User-Agent | 默认用 urllib 默认 UA；确需伪装时用环境变量 `L0_URL_UA` | **fda.gov 对假 Chrome UA 整站返 404**（连首页、`robots.txt` 都 404），造成 8 条假红（3 条 FDA + CDC + Meta×2 + momcozy×2） |
| 2 | 取 URL 列表处 | 只筛 `status not in (gone, retracted)` | 增加 `is_bad_key()`：键体非 `http(s)://` 开头、或台账已标坏键备注的，**跳过并单列** | 台账 09-29 已把「字段显示文本被当成 URL 主机名」的键定性为坏键（`change=l0_url_bad_key_note`，5 条），但脚本没认这个标记，把坏键当真 URL 去抓 → `UnicodeEncodeError` / `unknown url type` |
| 3 | 异常分支 | 所有失败一律 `unreachable` | 细分 `fail_class`：`missing_page_candidate`(404) / `blocked_candidate`(400,403) / `dns_fail` / `network_error` / `timeout` | 「页面没了」与「反爬挡我」的处置完全不同，混成一个数就会误导 |
| 4 | 追加台账的闸门 | 失败项**永不落台账**（`if APPLY` 只写正常项） | 新增 `--append-failures`：把 404/403/DNS 三类失败写成台账行，**默认不开**（保持只读） | 失效链接原先只能在一次性报告里看到，第二天就无人知晓 |

### 关键口径（别改错）

- **404 ≠ gone**。skill 红线是「标 `gone` 要**双证**：人确认 + API 报不存在」。所以落台账用的是**非终态**：
  - `missing`（404，待多轮复现或人确认）
  - `blocked_by_ua_policy`（400/403，**非页面失效**）
  - `dns_fail`
- 落账走 `l0_ledger.append_changed`：**状态没变就只刷 `last_seen.json`，不重复追加**（台账防膨胀）。
- `--append-failures` 只写失败项；正常项仍要 `--apply` 才写。

### ⚠️ 本轮发现的结构性问题（**未修，待裁**）

**单元级「换代」在 `units.jsonl` 里不会淘汰旧代**：`units.jsonl` 是 append-only，
失效只写进 `manifest_l2.jsonl`；而 `l6_scope_lib._invalidated_resources()` 取的是**资源级最新 result** ——
资源一旦被重切，最新 result 就从 `invalidated` 变成 `split` ⇒ **旧代单元重新变为「可入索引」**。

**实测规模**（本轮后全库）：**107 个资源存在多代 sha 单元，旧代单元共 211 个**
（例：`advertising.amazon.com/help/G4U9JBZH3664JWX2` 下 4 代并存：21 + 1 + 1 + 1）。
其中相当一部分旧代正文是**JS 噪声**（`.work/l6_scope_lib.py` 注释里已记过一次同类退化）。

**要人裁**：是补「单元级淘汰」（`retired_units.jsonl` 已有该机制，见 `l6_scope_lib.py:41`），
还是接受多代并存并在检索侧去重。**属判定标准，不由 agent 自行决定。**

### 为什么必须**配套**改阈值（这条不一起改，周更就是半成品）

原口径：新鲜 ⟺ 该层最近一次成功 RUN 在 **24h** 内（`layer_freshness.STALE_AFTER = 86400`）。
排期一改成每周，一周里有 **6 天**各层全判「陈旧」⇒ 评审链 ②c 复判仍超期 ⇒ **全周拒答**；
而且就绪巡检的**受控自愈**会**每天**把这一轮踢回来（冷却 45 分钟／当日 ≤3 次）⇒ **周更名存实亡**。
⇒ 阈值同时改成 **7 天周期 + 1 天余量 = 8 天**。

**放宽阈值 = 同时放宽了保护**（原先跑挂了 24h 内就知道，现在最长 8 天才红），
所以同批补了**快信道** `check_weekly_run_ran()`：排期时刻过 **12h** 还没跑成 ⇒ **当天**就报、
走**阻断级冷却**（一天最多一条）。它问「跑没跑」用的仍是 `layer_freshness.judge()` 的 `change_state`，
**没有新造第二把尺子**；阈值那件事仍归 freshness。

## 2026-10-16 · ③ 撤回群里那几条日更摘要：**没做成**（`230009`）—— 把"撤不回来"这件事也留痕

**触发**：Owner「**昨天发群里的日更撤回**，这个问题你修复后落库」。
**结果**：❌ **机器撤不回来**。两条都返回 `code 230009 Message has expired when recall message`。

### 实测（命令与回执都在这儿，可复算）

```
lark-cli im messages delete --message-id om_x100b62271c828ca4cf058358ba68216 --as bot --profile dsh-kb --yes
  → ok=false  code=230009  "Message has expired when recall message."
lark-cli im messages delete --message-id om_x100b63ca749d28a0df0d2b621d340ec  --as bot --profile dsh-kb --yes
  → ok=false  code=230009  "Message has expired when recall message."
```

（干跑 `--dry-run` 是通的 —— 身份、权限、消息 ID 都没问题，**卡在时限**。）

**判据出处**：[撤回消息 · 服务端 API](https://open.feishu.cn/document/server-docs/im-v1/message/delete)
—— `230009` 的官方语义是「**消息发出时间过长，不能执行当前操作**」，
撤回时限**由企业管理员设置**（不是固定的 24 小时）。实测**5.6 小时前**那条（今天 04:18 发、09:53 撤）**已超**。
⇒ 时限是**租户级设置**，而且**改设置不追溯**已发出的消息 —— 所以这不是"再试一次"能解决的。
