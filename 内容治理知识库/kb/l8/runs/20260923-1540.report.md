## 一、结论与产物清单

**结论**：现象是**写通道**造成的。`kb/.work/gen-host-library.py` 用 python 的 `open(...,"w")` 写 `.md`，
在这台机器上落盘成 **4096 字节前缀信封**；加载器（Electron 运行时，已载入
`/usr/local/.trld/lib/libtr_monitor_enc.dylib`）`readFileSync` 读到的正是信封，
于是 `splitFrontmatter`（`/^---\r?\n…/`）失配 → `meta = null` → **E001 × 509**。
`cat` / `python3` 等通道看到的是明文，所以文件「看起来」完全正常 —— 两边看的是同一 inode 的两种视图。

**修复**（R1 + R2，未改加载器）：改用加载器同一运行时的 node 明文写通道重写装载位，
每个文件写完立刻读回断言。结果：**E001 0**、`3_措辞表达库` **509 条 / 未归库 0**、
`kb_search` 三词命中 **111 / 1 / 509**、健康分 **50 → 75**（熔断线 60）、三件套完整率 **0.00 → 1.00**。

## 三、四个实验：差异在写通道还是读通道（第二步）

见 `kb/l8/diagnosis.md`。四组原始数据一句话版：

- **E1**：同一路径同一 inode（65787955），bash/Electron 看 8047 字节、python/ChatGPT-node 看 3951 字节
  （后两者逐字节相同）。**不是同一份字节，是两种视图。**
- **E2**：六种容器 magic 全不匹配；510/510 文件的体积差恒为 **4096**；`dd` 原始字节与逻辑明文
  **510/510 逐字节相同** → 信封 = 4096 字节前缀 + 完整原文，内容没坏。
- **E3**：写者决定形态。python/perl（含 `env -i`、含 launchd 脱离 DSH 进程树）写 `.md` → 信封；
  node / `/bin/cp` / bash 重定向 → 明文。**扩展名矩阵：只有 `.md` 受影响。**
- **E4**：读侧分成两组且各自稳定（12 秒 × 24 次轮询无变化，非竞态）；
  失败那一侧的进程（DSH Electron pid 39297）**载入了 `libtr_monitor_enc.dylib`**，python 没有。
  另实测：**DSH 的 write 工具写 `.md` 是明文的** —— 写者身份必须逐个测，不能按 App 猜。

**事实与推断分开**：事实 = 上述可复现的观察与注入库加载；推断 = 「前缀由 `/usr/local/.trld`
这套代理施加、Electron 族被排除在透明还原之外」（无法取得厂商内部实现，标推断）。
本批此前一度怀疑在装的卡巴斯基 sysext，**现按证据更正为 trld**。
