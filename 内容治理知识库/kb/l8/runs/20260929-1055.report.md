## 一、"三处假绿"到底是什么

| 字段 | 原状态 | 为什么是假绿 |
|---|---|---|
| `half_life_days` | 生成器常量 `= 180`（509 条全同） | 值来自**反规范化步骤**，不在权威库；重生成即丢 |

### 回填 4 个字段到 `l3/candidates/rules.jsonl` 的 509 条规则

| 字段 | 性质 | 动作 |

| `owner` | **原有字段、原为空串** | 填入**角色位** |

**只填空字段与加新字段，未覆盖任何既有非空值**（脚本内有 assert 硬拦）。
序列化自检：`json.dumps(ensure_ascii=False, sort_keys=True)` 能逐字节复现原行 —— 保证写回不改变任何既有字节形态。

### 政策：三档半衰期（`l3/registry/half-life-policy.json`）

| 档 | 条件 | 值 | 条数 | 理由 |

| A | `p_level = P0` | **365** | 21 | 法务红线，依据法规与监管口径，按年复核 |

## 三、F8：生成器改为从权威库读

改动（`gen-host-library.py`）：
- `owner` / `half_life_days` / `valid_until` 三个字段**从规则行读**，不再用常量
- 常量降级为**兜底值**（`OWNER_FALLBACK="法务"`、`DERIVED_HALF_LIFE_DAYS=180`），
  且每次兜底都写进 `derivation.json → governance_fallbacks`（**不静默**）
- `derived_defaults` 只剩真正属库级政策的 `data_level`/`sensitivity_level`
- `OWNER` 更名为 `LIBRARY_OWNER`（它是**库/子库级接受人**，与逐条 `owner` 是两件事）
- `data_level`/`sensitivity_level` **保留为库级政策常量**（全库内部材料、无自然人信息），
  但在代码里写明理由，不让它变成下一个未登记的常量

### 顺手修掉一个**静默 bug**（本次实测发现）

```
原写法 pick_best(rows, "verification", lambda v: 0 if v == "已归纳" else 1)
```
权威库 `verification` 的实际取值只有 **「待验证」(447) / 「已支持」(62)**，**没有「已归纳」**。
于是 rank 恒为 1 → `sorted` 稳定排序 → **退化成"取第一行的值"，且一声不吭**。
这正是本库的招牌病：**枚举与现实的桥断了，代码静默降级**。
已改为显式枚举 `VERIFICATION_ORDER = {"已支持": 0, "待验证": 1}`。
