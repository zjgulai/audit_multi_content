## 三、F2 最重要的发现：**健康分 100，但 508 个错误**

### 3.1 为什么 100 分是误导性的

七维里 **三维 noData**（覆盖率 / 利用率 / 幻觉率），健康分**只在有分母的维度上算**。
所以 508 个 error 摆在那里，**健康分照样 100**。

> **这直接证明修复计划里"六维全部进分母（F4 + F10）"是必须的。**
> 只要覆盖率与利用率是 noData，健康分就永远不能用来判断"库能不能用"。

### 3.2 E026 × 452 的根因：**打分尺度不匹配，不是内容不合格**

复现加载器的打分函数（Python 逐条重算），结果与探针**完全一致**：**452 不合格 / 57 合格**。

| 指标 | 实测 |
|---|---|
| 正文长度 | 中位 **1,051** 字，最短 689，最长 11,169 |
| 长度分公式 | `min(20, n/500)` → **要拿满分 20 分需正文 ≥ 10,000 字** |
| 1,000 字级条目实际长度分 | **1.8 – 2.5 / 20** |
| 不合格主因 | **400 条：长度分被压到 2 分左右**；52 条：信息密度分低 |
| 其余维度 | 去重分 20/20（满分）、语言质量分 ~20/30 |

**结论**：本库条目是「结论卡片」形态（1,000 字级），而长度分是**按网页文章尺度**归一化的
（10,000 字才满分）。满分上限因此只有 `2.1 + 30 + 20 + 30 = 82.1`，阈值 60 →
必须靠密度与语言两维补足 37.9 分，而中文规则文本的 2-gram 去重比天然在 0.4–0.6，
密度分普遍只有 11–19。**这是尺度问题，不是内容缺陷。**

**插件自己的口径**（README「已知偏差」）：
> "上游那套是给**网页抓取的连续文本**调的参，用在结构化的知识条目上会系统性压低表格类内容的分数。
> 阈值暂不动（保持 60），但**表格型条目分数偏低是已知偏差**。"

→ 已知偏差只提了「**表格型**条目」，而本库的 452 条主因是「**长度维度尺度**」——
**这是一条尚未被插件记录在案的、更普遍的偏差**。

**处置建议（不在 F1/F2 范围内，待定）**：
1. **不修内容** —— 把 1,000 字结论卡片灌到 10,000 字是灌水，方向错了
2. 把 452 条 E026 登记为**已知偏差**，在验收口径里显式排除，并要求"排除必须写明理由与复现方法"
3. 评估是否向插件侧提「长度分尺度」问题（`QUALITY` 的 `/500` 是硬编码，改它影响所有库）

## 五、追加发现（F2 收尾时挖到）：`_meta/manifest.json` **文件名冲突** —— 一个会静默毁数据的陷阱

`W035`（"没有条目基线"）是**真的**，尽管 `_meta/manifest.json` 明明存在（6.6 MB）。

### 根因：两个不同用途的产物，撞了同一个文件名

| | 加载器要的「条目基线」 | 工作台要的「镜像载荷」 |
|---|---|---|
| 谁读 | `dsh-kb` 的 `readManifest()` | `kb/.work/kb-hostlib-serve.py`（供工作台 4317 知识库页） |
| 谁写 | `writeManifest()`（`kb_ingest` / `kb_check --accept-baseline`） | `kb/.work/gen-host-library.py` |
| 期望顶层键 | **必须有 `entries`**（`{ [id]: {file, ghash, bhash} }`） | `manifestVersion / generatedAt / generator / version / root / libraryName / collections / docs / counts` |
| 现在这个文件是哪种 | — | **镜像载荷**（顶层无 `entries`） |

`readManifest` 的判据是 `doc.entries && typeof doc.entries === "object"` → 现有文件不满足 → 返回 `null`
→ `hasBaseline = false` → **W035**。**所以 W035 报得对，不是误报。**

### ⚠️ 陷阱：在上面跑 `accept_baseline` 会清掉镜像载荷

`writeManifest` 的落盘是**整文件重写**：

```js
writeFileSync(f, JSON.stringify({
  version: 1, updated_at: ..., note: "条目基线：…", entries,
}, null, 1))
```

→ `manifestVersion / generator / collections / docs / counts` 等键**全部丢失**。
**即：一旦有人对 `kb/view` 执行 `kb_check --accept-baseline`（或 `kb_ingest` 成功路径），
工作台镜像载荷就被静默覆盖，`kb-hostlib-serve.py` 与工作台知识库页会一起坏掉，而且不会报错。**

### 另有一处不一致

现有镜像载荷里写着 `"root": "/tmp/l8-view-staging"` —— 它是在**临时 staging 路径**下生成的，
记录的根不是真实根。`version: 53e5ed80…` 的语义也未在文件内说明。

### 处置建议（列入 F3）

| 方案 | 做法 | 取舍 |
|---|---|---|
| **(a) 重命名镜像载荷（推荐）** | 镜像载荷改名 `_meta/mirror-payload.json`；同步改 `gen-host-library.py` 与 `kb-hostlib-serve.py`；`_meta/manifest.json` 让给加载器基线 | 两个用途彻底分开，各自格式自由演进 |
| (b) 暂不处理 | 记入 `open_issues`，**并在 F3/F4 里明确禁止对 `kb/view` 跑 `accept_baseline`** | 零改动，但陷阱一直在 |
| (c) 合并格式 | 让 `gen-host-library.py` 也写兼容的 `entries` 键 | **不够** —— `writeManifest` 仍会清掉镜像侧的其他键 |

**在 (a) 落地前，(b) 必须执行**：把"禁止对 `kb/view` 跑 `accept_baseline`"写进 F3 的施工注意项。
