## 一、L1 索引：`OI-L1-001` 是误报，`OI-L1-002` 比记录的更严重

### 1.1 先证伪 `OI-L1-001`

OI 原文说"少 131 条有效资源的段"，影响写的是"**L6 检索读 index → 会漏这 131 条的段**"。两条都错。

**第一条：L6 不读这个索引。** 决定性证据是数出来的，不是推的：

| 消费者 | 实际输入 | 是否读 `l1/index/l1.jsonl` |
|---|---|---|
| L2 splitter | `glob("kb/l1/<目录>/*.json")` 逐资源文件 | 否 |
| L6 建索引 | `kb/l2/units.jsonl` 经 L3 口径过滤 | 否 |

`grep -rl 'l1/index' kb/l6/` → **0 处命中**。`l1/index/l1.jsonl` 的引用只出现在历史运行报告与抽取脚本自己里。

**第二条：那 131 条不是内容丢失。** 拆开看：

| 构成 | 条数 | 真实情况 |
|---|---|---|
| `media_*` 资源 | 129 | 正文在 `kb/l1/media/<rec>/ocr.json`，**不在** 5 个批次目录里 → 以资源为单位不进索引 |
| 真无正文的资源 | 2 | 1 个 Google Drive 文件夹（`unreachable`）+ 1 个飞书 drive 文件夹（`no_scope`） |

那 129 个 media 资源的图，文本其实**已经进了索引**——作为**父 bitable 记录的 `segments`**（`kind=image_ocr`/`image_visual`）。实测：

```
valid media 资源: 129
  这些资源的图片总数: 240   其中已进索引: 240   未进: 0
```

**240/240。** 这已写成一个常驻检查（`media_coverage`），缺失数必须恒为 0。

所以 `OI-L1-001` 的"130 张图 OCR 检索不到"是**双向都错**：L6 不读该索引，且图 OCR 一条没丢。真实影响只剩一条：索引作为**审计投影**少算 media 资源这一层，按资源数对账语料规模时会偏小。

**处置**：判为误报关闭，附证伪三据。**故意不给索引补 media 行** —— 补了会把同一段文本重复计数。改为把这条口径写成机器可查的 `media_coverage`。

### 1.2 `OI-L1-002` 是真的，而且长大了

OI 记 77 行，实测 **202 个资源 / 1,247 行**。

根因（读代码确认）：写索引的循环（`.work/l1_extract_v3.py:436-457`）只遍历批次目录里的 `*.json`，**从不读台账 `status`**。所以已 `invalidated`/`retracted` 的资源，其段仍留在索引里。

为什么从 77 涨到 1,247：OI 写于 `20260924-1730`，其后又有记录被作废/撤回。作废数：`invalidated` 206 + `retracted` 36 = 242 个资源，其中 202 个在索引里有残留行。

**顺带一个反向确认（好消息）**：L2 侧**已经正确排除**了这 77 张失效图 —— L2 内 `#img.` 单元恰为 240 条，与有效父记录一一对应。所以失效内容**没有**进 L2/L6。OI 写的"检索会召回已失效内容"同样不成立。

### 1.3 新登记 `OI-L1-003`：索引必然漂移

原先索引只在 `l1_extract_v3.py` **全量抽取的尾部**写出，没有独立入口。实测：

```
索引 mtime          2026-09-24 16:27:11
它应覆盖的最新源文件  2026-09-24 16:54:54   ← 晚 27 分钟
```

资源文件在抽取之后仍被后续批次改写，而索引不再重写，且没有任何检查会告警。

### 1.4 修法与结果

新增常驻工具 **`kb/l1/index/rebuild_l1_index.py`**（`--check` / `--write` 两态）：

- 写入前按台账**最新状态**过滤（只收 `ok`/`extracted`），并把每种被排除状态连同理由写进报告
- 原子替换（`.tmp` + `os.replace`）
- `--check` 四查：**陈旧**（索引 mtime vs 源文件最晚）、**虚报**（僵尸行）、**缺段**、**多余**，外加 `media_coverage`；有漂移即 `exit 1`，可直接挂进巡检
- 台账最新状态取值分布：`ok` 1292 / `extracted` 240 / `invalidated` 206 / `no_scope` 49 / `retracted` 36 / … → 有效 **1,532**

修前体检与修后：

```
修前：索引体检 [DRIFT]
  陈旧：索引 mtime 1790238431 < 源文件最晚 1790240095
  虚报：1247 行 / 202 个资源已失效却仍在索引内
  缺段：1 段当前语料有、索引没有
  多余：1098 段索引有、当前语料没有
  图片 OCR 覆盖 240/240（缺 0）

重建：14,858 行 / 1,603 资源 → 13,613 行 / 1,403 资源（剔除僵尸 1,247 行）

修后：索引体检 [OK]        ← 四项全清，exit 0
  图片 OCR 覆盖 240/240（缺 0）
```

写盘后确认是明文（首 3 字节 `7b 22 61` = `{"a`），非 4096 字节信封。

## 二、L6：不需要重建 —— 重建是幂等空操作

### 2.1 先纠一个我自己上一轮量错的地方

我第一轮用 `l6/bm25/docs.jsonl` 的 **`doc_id`**（那是整数序号 0,1,2…）去比 `l2/units.jsonl` 的 **`unit_id`**，得出"1,899 个 doc_id 与 9,805 个 unit_id 零重叠 → L6 与当前 L2 完全断链"。**这个结论是错的**，`doc_id` 与 `unit_id` 不是同一个字段。

改用 `unit_id` 重比：

```
L2 unit_id=9805   L6 bm25 unit_id=1899
  L6 ∩ L2  = 1899      ← 全部命中
  L6 独有  = 0
  L6 的 source_sha256 命中当前 L2 sha 集合: 1899/1899
  L6 抽 1899 条，anchor 仍能在当前 L1 找到: 1899/1899
```

**L6 引用零失效。** 它不是"旧了 5 天"，是按 L3 口径筛出的 1,899 条子集。

### 2.2 那"重建 L6"有没有必要？先看重算口径

重算可用口径得 **1,982**，比已索引的 1,899 **多 83 条**。逐 id 差分：新增 83、移除 0。

于是问题变成：这 83 条该不该进索引。量了一下，答案很清楚：**不该**。

| | 已收录 1,899 条 | 候选新增 83 条 |
|---|---|---|
| 中位字符数 | 67 | **24,703** |
| > 2,000 字符 | 1 条 | **82 条** |
| 最长 | 31,450 | 45,080 |
| 不同开头数 | — | **7** |

那 83 条长这样：

```
60 × 'Skip to content Switch to your local sto…'
 9 × 'Zum Inhalt springen Jetzt zum lokalen Sh…'
 5 × 'Aller au contenu fermer 🚚 LIVRAISON GRAT…'
 4 × 'Saltar al contenido cerrar cerrar Cambia…'
 2 × 'Przejdź do treści close 🔥Tygodniowe okaz…'
```

来源是 `momcozy.com` 及 `ca/de/eu/fr/uk/es/pl/au` 各站的**产品页 / 博客页 / 集合页**，外加 `drugs.dxy.cn` 临床指南页 1 条。全是 `unit_type=clause`、`kb_type=wording`、来源 `#正文`。

**这是整页抓取，不是知识。** 而纳入的代价：

```
总字符量     292,642 → 2,400,729   （×8.2）
估算段数       3,654 →    21,258   （×5.8）
```

后果：每个与哺乳/吸奶器相关的查询都会命中巨型产品页，把精确的规则条目挤下去。**纳入会毁掉检索精度。** 所以这不是"少收了知识"，是**拒绝把网页全文当知识**。

### 2.3 用系统本来就设计好的机制钉住

`l6_scope.py` 的文档里写着"若 `kb/l6/SCOPE.txt` 存在，则按其中列出的 unit_id 取子集"。但读代码发现：**`SCOPE.txt` 只被 `l6_scope.py`（报告器）读，建索引的 `l6_build.py` 不读** —— 而它写 registry 时却记 `scope_file = SCOPE.txt`（文件存在即记）。等于**声称"本次索引按 SCOPE.txt 取了子集"，实际根本没理会**。这是静默失真的溯源声明（此前从未创建过该文件，所以一直没暴露）。

三处修改：

1. **`l6_scope_lib.apply_scope_file()`**（新增）—— `SCOPE.txt` 的唯一读取实现，报告器与建索引器同源调用。被排除条数计入 `filter_distribution` 的 `*|outside_scope_file`。
2. **`kb/l6/SCOPE.txt`**（新增，1,899 条）—— 头部写清为什么拒绝那 83 条，以及"新增 unit_id 是人的动作"。
3. **`l6_build.py:67` 的护栏**：原为 `assert len(kept) == 1899` 字面量。护栏本身是对的（防口径静默漂移），但钉成字面量后**合法增长与口径改坏无法区分**，只能改代码才能重跑 —— 而改代码正是最该避免的绕过方式。改为与 registry 记录的上次范围比对，漂移默认仍停，须显式 `--accept-scope-delta` 放行，并把**逐 id** 差额（added/removed）写进 `scope.scope_delta`。

### 2.4 重建结果：完全空操作

```
可用单元 1899｜P0 证据单元（不入向量）321
口径差额：新增 0 移除 0（上次记录 1899 → 本次 1899）
BM25（自实现）：1899 文档｜本次切词 0 条｜索引无变化 → 不重写文件
握手：可用（返回 384 维，期望 384，范数 3.119）
向量：单元 1578 个 → 段 2088 条｜被分段单元 281｜新增/变更 0｜复用 2088｜embedding 调用 0 次｜失败 0
索引投影 1899 行（未变不写）｜registry（重写）｜总耗时 5.5s
```

**这是最好的结果：幂等性被证明，而不是被声称。** 文件系统层证据：

| 产物 | mtime | 是否被改写 |
|---|---|---|
| `l6/bm25/docs.jsonl` | 14:03:36 | 否 |
| `l6/vectors/vectors.jsonl` | 14:19:19 | 否 |
| `l6/index/l6.jsonl` | 14:19:19 | 否 |
| `l6/registry/l6.json` | 10:58:08 | 是（唯一） |

registry 键无增无减，只有 `run_id` 与 `scope` 变了。
