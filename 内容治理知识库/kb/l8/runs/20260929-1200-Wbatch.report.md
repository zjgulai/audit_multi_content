## 一、四个码的修法

### W019 —— `_meta/kb-classes.yaml` 的 `owner` 键

加载器 `loadKbClasses()` 只读 `classes` / `ranking` / `multi`，**从不读 `owner`** ——
一个不生效的顶层键，而同一文件里别的键真的在生效，最容易被误判成"已接线"。

三选项里选了**删除**：owner 的正确落点是 `_meta/collections.yaml`（workbench 从那里按子库取
owner/status/entry_count），那里已写。留下的唯一作用就是让人以为它管事。同时改了生成器
（否则重新生成会把它写回来）。顺带：原值是**人名**（`刘华丽`）—— 库级接受人用具名人是刻意的
（与逐条 `meta.owner` 是两件事），故 `collections.yaml` 保留，只在无人读的这份里删掉。

### W023 —— 509 条缺 `source.record_ids`

原指纹只到「表 @rev」粒度 → 回源只能判断「这个表变过没有」，判断不了「哪条记录变了」。
本库为此付过代价：追「rev 98→367」最后只能人肉核 5 条。

**为什么这次能确定地填**：证据单元锚点形如
`#专家修订汇总表/recvoyJ6L9s6Mi/修订位置（原文引用）`，记录 id **就在锚点里**，不是猜的。
新函数 `record_ids_of(rows)` 逐行提取，实测 **509/509 全取到**（每行 1–57 个，均值 2.3）。

⚠ 踩到的坑：`frontmatter()` 对**嵌套列表**一律走 `yaml_scalar()`，而它对 list 做的是 `str(value)`
→ 落成 `record_ids: "['recXXX']"` 这样的**字符串**。加载器判的是 `Array.isArray(...)`，
**字段填了、告警照报，而肉眼看着像填对了**。已改为 flow 列表 `record_ids: [recXXX]`
（与 `kb_class` 同形）。配套硬校验是 E035：元素必须是非空**字符串**，填数字会换来一条 error。

### W035 —— 条目基线不存在（真形状是**文件名一名两义**）

`readManifest()` 读 `<root>/_meta/manifest.json`，要求顶层有 `entries` 对象；
读到别的 schema 就返回 `null` → W035 → **「条目被删掉」与「治理字段被原地改写」都发现不了**。
这不是理论风险：**2026-09-22 六条 L0-raw 原文存档被整体删除，检查器本身什么都没说**，
当时靠 entry_count 与词表死引用碰巧才看出来。

同一个文件名被两类消费方以不同 schema 要求：

| 消费方 | 要它当什么 | 硬编码处 |
|---|---|---|
| 发布链 | 自包含**镜像载荷**（`docs[].text` + sha256） | `gen-host-library-l4.py:366`、`gen-host-library-product.py:482`、`kb-hostlib-serve.py:25`、`publish.sh` |
| 加载器 | **条目基线**（顶层 `entries`） | `kb.js` `MANIFEST_FILE = "manifest.json"` |

同一棵树不可能同时满足。故按**输出目标分开命名**：生成器新增 `--payload-name`，
**默认保持 `manifest.json`**（发布链不受影响），生成 `kb/view` 时显式传
`--payload-name workbench-mirror.json`。

`kb/l8/manifest_baseline.mjs`（新增常驻工具）负责在腾出来的路径上建基线。
它会**先看清目标路径上是什么**，若发现"有文件但顶层没有 entries"就**拒绝覆盖**退出码 3。

建立结果：**509 条**，91,337 字节，明文，含 `file`/`ghash`/`bhash`。

### W036 —— 509 条缺 `evidence_group`

枚举来自 `_meta/evidence-groups.yaml`：`rule / evidence / sample / clause / clue / coordinate`。

口径：本视图 509 条**全部**是 `rules.jsonl` 蒸馏出的可判定规则（`kind=fact`、全在 `L1-facts`、
每条带 `p_level` + 命中表达 + 处理方式）→ **`rule`**。不是 `evidence`/`clause`/`sample`：
那三类材料留在 L1 单元层，没有升成条目 —— 本视图只有 `3_措辞表达库` 一个子库。

⚠ `evidence_group` 在加载器 `GOVERNANCE_FIELDS` 内（**它参与检索排序**），所以这次回填是
**治理事件而非排版调整**：按 W034 的要求先在 `_meta/ledger.ndjson` 补了一行 why
（`human: false` —— agent 按人工批准的批次执行，**不冒充人工先例**），再刷新基线
（`changed: 509, added: 0, removed: 0` —— 无删除）。

字段反过来说明了一件事：`require_on_new` 一直是 `false` 是**对的**，一旦置 true，
509 条会集体升级成 E042 error。

## 二、我自己造成的两处破坏（均已修）

### 1. 已发生：Python 写 `kb/view` 落成信封 → E001 × 509

第一次落盘用了 `shutil.copy2`。加载器随即报 **509 条 E001「缺 frontmatter」**，
并因 `loadAll` 拿不到条目把**条目基线刷成 0 条**（`removed: 509`）。

隔离实验（同一份 4,532 字节的 md）：

| 落盘方式 | node 看到 | 判定 |
|---|---|---|
| `shutil.copy2` | **8,628 字节**，首字节随机二进制 | ❌ 信封（4,532 + 4,096 前缀） |
| shell `cp` | 4,532 字节，首 3 字节 `---` | ✅ 明文 |

**而 Python 的 `stat` / `sha256` / `head` 对信封完全免疫** —— 它照样报 4,532 字节、
sha256 与源文件一致。所以当时那个"明文自检"（用 Python 读首 3 字节）**结构上不可能发现这个缺陷**，
它给了一个假绿灯，然后由加载器来报错。

> **纪律**：① 落进 `kb/view` 的文件只用 shell `cp` 或 node 写，不要用 Python 写；
> ② 校验必须用**消费方运行时**（`which_enveloped.mjs` / `scan_envelope.mjs`），不要用自己的语言自证；
> ③ 留底也要用 `cp` —— 信封版的留底在回滚时会把信封带回来。

回滚后逐项复验（errors 454 / warnings 2740 / health 98.4 / 基线 509 条），确认无残留。

## 三、剩下三项：为什么**不该由 agent 修**

### `E026 × 454` —— 不是缺陷，是**口径错配**

闸门口径：正文 ≥200 字符且总分 ≥60（长度 ≤20 分 = `n/500` 封顶 + 密度 30 + 去重 20 + 语言 30）。
这四维是为**手写散文条目**设计的。

本库正文是**规则行的忠实渲染**（规则原文 / 命中表达 / 判为违规的依据 / 处理方式 /
适用范围 / 证据单元明细），样例 1,305 字符 —— **不是写得薄，是规则本身就短**。
实测 454 条全部落在「分数 <60」分支（短正文分支 0 条），总分 52.5 / 55.8 / 59.9（min/中位/max）。

**明确否决「往正文灌水凑长度」**：按 `lengthScore=min(20,n/500)` 反推，分别需要新增约
**801 / 3,151 / 7,000** 字符即可过线 —— 也就是给每条规则补 0.8k–7k 字的**非知识内容**。
那正是本库明令禁止的"为指标造数据"，灌水还会拉低 density（去重比）并按 `(.)\1{5,}` 扣 language 分，
属于用一个假绿换另一个假绿。

两条诚实路径（都需人工决策）：① 给 QUALITY 闸门加**按库分档**的口径（插件侧改、需留痕）；
② 若权威库确有未渲染的长文本则渲染出来 —— 本轮核对正文已渲染主要字段，预计收益有限。

### `W020 × 2218` —— 机器只报疑似，判归人

加载器原话："要么合并（新建 + supersedes 留痕，不许原地改写），要么把两者的分工写进 summary。
**机器只报疑似，判归人**"。合并会改知识口径并触发 AP14，是业务判断。样例元字段 Jaccard 0.61、
正文 0.59 —— 相似度只说明"同源同族"，不说明"该合并"。

### `W021 × 10` —— 判为解析伪影，但也不自动改

样例：「同一个键「recvunn」+ 单位「(无)」 取值不相交 —— 本条 6，对端 4」。键名 `recvunn`
是记录 id 前缀被截断的产物，不是知识里的键。另一类比较的是**各条目自己的命中表达条数**
（每条规则天然不同），不是对同一量的两个断言。加载器已声明"**不许自动裁决**"，故只记判定待复核。

## 四、`W025`：待决策（修它会把一个假绿换成真的红）

生成器「补丁 E」的注释自己写明：`related` 是"给每条规则挂几个 related 邻居
（**用来把孤岛率从 1.00 打下来**）"。两个依据：

- ① 同 `rule_code` —— 真的规则族关系（37 条规则、22 个码）
- ② 同主来源表 —— 文档原话是"每条指向稳定序上紧随其后的 N 条，**使全组都有入边**"，
  即**为过门槛而制造的合成边**，不是关系

加载器只认「`related` 为空/不存在」才消警（把内容搬进 typed keys **不算**），
所以修它必须删/清空 `related`。而孤岛率 = 没被任何条目引用的占比，清掉合成边后只剩 37 条有真边
→ **孤岛率约 0.93，超过 ≤0.2 阈值，该维度转红**，健康分随之下行（当前 98.4，熔断线 60）。

| 选项 | 做法 | 后果 |
|---|---|---|
| A | 只让生成器不再新写 `related`，存量不动 | 合规字面要求；W025 仍报 1 条；**孤岛率仍是假绿** |
| B | 删合成边，只把同 `rule_code` 的真边迁成 `complements` | W025 归零；**孤岛率转真红（≈0.93）** |
| C | 合成边也迁成 `complements` | W025 归零且保持绿，但**类型是编造的** —— 已排除 |

**建议 B**，与 F10「健康分从 100 掉到 98.4 是假绿被拆掉」同一处置逻辑；但它改的是一个已公开的
健康数字，需人确认。真孤岛率 ≈0.93 本身是有价值的业务结论：**472/509 条规则与其他条目
没有任何真实引用关系** —— 要真正降下来需要来源表提供真实的关联列（当前没有），属业务动作。

## 九、`W025` 已按选项 B 落地（人已确认）

决策：**B —— 删合成边，只保留真有依据的关系并迁成 typed link。**

- 只保留「**同 rule_code**」这一条真有依据的关系（共用一个码、是该码下的不同条款），落成 `complements`

  所以两件事必须一起做

  也不是「互相矛盾」—— 类型必须由证据决定，不能为了让字段好看挑一个

结果的诚实边界：`complements` 在这里的含义是**同规则族**，**不是语义上论证过的互补**。
逐条的语义互补仍要人写。
