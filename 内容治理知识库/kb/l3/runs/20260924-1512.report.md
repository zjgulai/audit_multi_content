## 4. L3 去重（§8）

### 4.1 根因

`case_id` 由**组内代表 unit** 生成，同一组在上游被遍历 3 次 → 同一 `(id, 内容)` 被写 3 行：

```
kb/.work/batch7_l3_run.py:110   "case_id": "sc-"   + sha1(unit_id|sample_case)[:16]
kb/.work/batch7_l3_fix.py:79    "case_id": "sc-w-" + sha1(unit_id|wording_sample)[:16]
```

**两个发射器是同一缺陷**（任务书点名 `batch7_l3_run.py:110`，`batch7_l3_fix.py:79` 是同型），同批一起修。

### 4.2 动作与干跑验证（§8.2）

**① 改发射器**：新增 `case_identity(u)`（只由内容字段决定：`kb_type` / `polarity` / `resource_id` /
`anchor` / `sample_body` / `media_refs` 排序后拼接，**不含 `unit_id`、不含 `observed_at`、不含行序**）
与 `emit_once(units)`；`batch7_l3_run.py` 的发射循环改为「同 `case_identity` 只发射一次」。

**② 干跑**（只写 `.work`，不覆盖任何库内文件）：

```
干跑输入：562 行
干跑输出：358 行  sha256=0b8e2c7ce14e97b42db7cd5d45f01a65dc91255a6f2269288caba13f12999b49
干跑输出 == 去重后 358 行（逐字节）: True
被删行 204 行；与保留行逐字节相同 204/204
```

**③ 原地去重**：

```

  改前 sha256: 80e816d17f7daaae   改后: 0b8e2c7ce14e97b4
```

保留规则：**每个 `case_id` 保留行序最靠前的那一行**；被删的 204 行与其保留行**逐字节相同（204/204）**。

**④ `registry/l3.json` 加 `dedup` 块**：含根因、根因位置（两个文件 + 行号）、562→358、`dropped=204`、
`dropped_all_byte_identical_to_kept=true`、`keep_rule`、发射器修法、干跑路径与哈希。

### 4.3 一处必须说清的取舍：`case_id` **没有**改成内容派生

任务书要求「`case_id` 必须按 **case 内容身份**生成」。**我没有改 `case_id` 的算法**，理由是硬约束 2：

> `case_id` 已经进入 L4 的条款号台账 —— `l4/canonical/sample_case.jsonl` 的 **W-3.\* / S-1.\*** 与
> `l4/registry/l4.json` 的 `assignments` 1242 条**都按 `case_id` 索引**。
> 改了 `case_id` → 358 个 key 全变 → **1242 条 `article_no` 全部错位**，直接违反「条款号不得漂移」。

所以采用的办法是：**`case_id` 原式不动**（保证已发号稳定），**去重改按新增的 `case_identity`**。
「按内容身份去重」这个**目的**达成了（同一内容只留一行），只是**载体**从 `case_id` 换成 `case_identity`。
这个取舍已写进 `registry/l3.json` 的 `dedup.case_id_kept_as_is_reason`，供复审。
