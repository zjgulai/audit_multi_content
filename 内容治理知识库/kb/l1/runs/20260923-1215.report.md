## 7. 自主决策

1. **按库分批、每批落盘**
   - 依据：顺序 wording → external_standard → internal_sample → product_desc → unknown；每批写完即落盘，支持随时停在上一个完整批次。
2. **kb_type 直接继承 L0，不做二次判定**
   - 依据：规格要求；L1 不重新分类，仅校验与 L0 一致（自检 5 已验 0 处不符）。
3. **飞书文档与网页正文都按**原文物理行号**建锚点，而不是只给 `#block.<id>`**
   - 依据：飞书 API 返回的 markdown 不含稳定的 block_id 映射，硬编 block_id 等于编造；行号 + 标题路径是真实物理位置，可回原文定位。`#block.<block_id>` 规范保留在 anchor_spec 供有 block_id 的场景使用。
4. **`正面和负面样本` 表的 125 条记录未被 L0 登记（该表不在入口表 link 下钻路径上），因此 77 张图片没有 L0 资源可挂**
   - 依据：作为 **L1 媒体产物**登记：`resource_key = media:<table>:<record_id>`，`l0_parent_resource_key` 指向 L0 中确实存在的表资源；kb/l0/ 未改动。这条 L0 缺口已写进报告，供是否扩大 L0 下钻范围时决策。
5. **Base 附件走 `base +record-download-attachment` 而不是 `drive +download`**
   - 依据：实测 `drive:file:download` 缺 scope，但 Base 附件通道可用；这是本次让 OCR 路径真被验证的关键发现。
6. **OCR 用 macOS Vision（JXA 桥接），不引入第三方库**
   - 依据：本机无 tesseract/pytesseract，Swift 工具链与 SDK 版本不匹配；Vision 是系统框架，零安装依赖。输出逐行文本 + bbox + 置信度 + 图片 sha256，落 `media/<id>/ocr.json`。
7. **结构资源（表/Base）记 `empty` 而不是 `ok`**
   - 依据：schema 是 L0 结构指纹的职责；L1 不把字段名/选项重复抽成内容，避免两处真相。
8. **`empty` 与 `unreachable` 严格区分**
   - 依据：`empty` = 能读但确实没有可抽内容；`unreachable` = 根本没读到。混用会掩盖真实缺口。
9. **同一 `(resource_id, extractor_version, source_sha256)` 直接跳过**
