# 完整样例：品牌问答 Agent 走完七阶段与 20 道门禁

> 一个真跑过的样例，用来对照。**看每一步的真实产出长什么样、门禁怎么判的、哪里返工过。**

---

## 需求原话

> "代理商老来问品牌的活动口径和合规问题，我们运营每次都要翻三份资料，答得还不一致。想做个东西能直接答。"

---

## 阶段 0：立项判断

### 入口三筛

| 筛子 | 证据 | 判定 |
|---|---|---|
| 结果不确定 | 同一个问题，不同运营答法不一样；要判断适用哪条口径 | 中 |
| 需 HITL | 涉及对外承诺的话术要人复核才能发 | 中 |
| 会重复 | 上周 47 条，单条平均 12 分钟 | 中 |

**结论**：做，且是**垂类**——只服务"品牌活动口径 + 合规话术"，不做通用客服。

### 立项一页纸

- 要解决的问题：代理商咨询答复慢且不一致
- 现在谁在做、多久一次、错在哪：运营 3 人轮值，上周 47 条，单条 12 分钟，答错率约 15%
- 做出来之后谁用：运营在企微里查，用来回代理商
- **不做的后果**：代理商拿错口径去对外宣传，品牌方要发更正函

> **门禁 1 过 / 门禁 2 过**：一句话定位写得出来——"只服务品牌活动口径与合规话术的问答"。

---

## 阶段 1：问题与调研

### 第一轮追问（只问 frontier）

```
❓ Q1 - 答复给谁看：运营自己参考，还是直接复制发给代理商？

➡️ 建议：运营参考后自己改一版再发。直接发给代理商要承担对外承诺风险。

---

❓ Q2 - 口径有冲突时以哪份为准？

➡️ 建议：以最新版《品牌活动执行手册》为准，其余资料仅作补充；冲突时在答复里标出冲突点。

---

❓ Q3 - 答错了的代价有多大？

➡️ 建议：定中级——对外话术类答错有合规风险，内部口径类答错只是返工。
```

**没问**："手册放在哪个目录"——这是事实，派 subagent 去查，不问用户。

### 第二轮（前置已解锁后）

Q4 知识库放哪、Q5 要不要接计算器（折扣核算）、Q6 哪些话题绝对不碰。

**frontier 空 → 停手，等用户确认。**

### 解决方案文档（节选）

现状量化：47 条/周、12 分钟/条、答错率 15%、错误代价 = 对外更正函。

- **方案 A**：检索增强问答 Agent（运营侧使用，人复核后发）
- **方案 B**：先做一份口径 FAQ 表格，人工维护

**推荐 A**，理由：口径更新频繁，表格维护成本高于 Agent。**但要讲清 B 的代价更低**，让需求方拍板。

HITL 点：涉及对外承诺的话术必须人复核。
绝对不碰：法律意见、对外报价承诺、未发布的营销计划。

> **门禁 3 过**（7 问全有答案，第 2 问有数字）**/ 门禁 4 过**（需求方选了 A，且已知 B）

---

## 阶段 2：方案与规格

### TUI 先行（这一步差点被跳过）

一开始想直接写规格。**被拦回**：门禁 5 要的是真跑通记录。

于是找了个通用 Agent + 手册 PDF，把**真实的 5 条代理商提问**丢进去跑：

```
输入：Q3 国补活动能不能叠加店铺满减？

输出：不能叠加。依据《品牌活动执行手册》v3.2 第 4.1 条：
      "国补类活动不与店铺级满减同时生效"。建议回复口径：
      "本次活动不支持与店铺满减叠加使用"。
```

**这 5 条跑通了**，其中 1 条答错（手册里有两处冲突表述）——这个发现直接改了规格：**必须加"冲突标注"能力**。

> **门禁 5 过**：有输入原文 + 输出原文的运行记录，且发现了 1 个规格层面的新需求。

### 原型（只回答一个问题）

**这一个问题**：答案该不该带"依据出处"？

- 变体 1（只给结论）：34 字
- 变体 2（结论 + 出处）：58 字 ← 运营反馈"看这个能直接判断能不能用"
- 变体 3（结论 + 出处 + 相似问题）：91 字 ← 冗余

结论折回规格的「实现决策」段：`deliverables[].fields` 定为 `[结论, 依据]`。

> **门禁 6 过**：一个原型一个问题，结论已折回。

### 接缝（本来选错了）

| 尝试 | 判定 |
|---|---|
| 给检索、排序、生成各造一个边界 | ✗ 3 个接缝，维护成本高 |
| 在检索函数上测 | ✗ 覆盖不了"答得对不对" |
| **在"一次问答请求 → 一次答复"这个入口上测** | ✓ 理想 1 个、取到最高点、复用已有的 CLI 入口 |

**摆给用户确认后**才写进规格。

> **门禁 7 过**

### 规格（7 段，节选交付物段）

| id | name | format | fields | acceptance |
|---|---|---|---|---|
| answer | 业务答复 | text | 结论、依据 | 先给结论再给依据；引用手册时标出条款号；手册里有冲突时明确指出冲突点；没有依据就直说没有，不编造 |

用户故事写了 9 条，覆盖到"运营在手机上也能看"。

> **范围外**写清：不做法律意见、不做报价、不主动推送。

---

## 阶段 3：目标与拆解

拆了 4 片，全部纵向贯穿：

| # | 标题 | Blocked by | What it delivers |
|---|---|---|---|
| 01 | 打通一次问答（检索 + 生成 + 出处） | 无 | 运营能问一句、拿到带条款号的答复 |
| 02 | 冲突标注 | 01 | 手册有冲突表述时，答复里明确指出 |
| 03 | 无依据兜底 | 01 | 查不到时明确说"暂无依据"，不编 |
| 04 | 输出格式对齐企微 | 01 | 答复能直接复制进企微不失真 |

**quiz 三问**后用户提了意见：02 和 03 都是"边界处理"，能不能合并？

→ 重拆：合并为 `02 边界处理（冲突标注 + 无依据兜底）`，因为交出去的东西都是"答复里的一个说明"，且都能在一张工单里验证。

> **门禁 8 过**：用户批准后才发布。

---

## 阶段 4：开发

```
01：先写测试（断言答复里必须含条款号）→ 红 → 实现检索+生成 → 绿
02：先写测试（手册冲突时答复必须含"冲突"字样）→ 红 → 实现 → 绿
```

**踩的坑**：02 一开始想直接上实现，被拦——**必须在 green 之前有 red**。

每次循环跑类型检查 + 单个测试文件；三片都绿后跑一次全量套件。

> **门禁 9 过**（接缝表在规格里已确认）**/ 门禁 10 过**（git 历史里能看到失败测试先出现）

---

## 阶段 5：验证与上线

### 双轴 review

- **Standards 轴**：发现 2 处——工具函数里硬编码了手册路径、异常被静默吞掉
- **Spec 轴**：发现 1 处——规格要求的"手机上也能看"没有对应实现

修完重跑。**两轴并行跑，互不污染**（Spec 轴不知道 Standards 的结论，避免互相带偏）。

> **门禁 11 过**

### 契约

```yaml
name: brand-pr-agent
version: "0.1.0"
interface: cli
run: python3 agent.py
input: stdin-json
profile: general
task_types: [fact_qa, reasoning, multi_turn, instruction, rag, safety]
deliverables:
  - id: answer
    name: 业务答复
    format: text
    fields: [结论, 依据]
    acceptance: 先给结论再给依据；引用手册时标出条款号；手册里有冲突时明确指出冲突点；没有依据就直说没有，不编造
  - id: weekly-report
    name: 周度问题汇总
    format: markdown
    fields: [本期TOP5, 处理率, 待办]
    acceptance: 数字和台账对得上；对不上的在报告里注明差异原因
tools:
  - name: search_kb
    description: 检索品牌知识库
    schema: {}
  - name: calculator
    description: 数值计算
    schema: {}
env:
  API_KEY: ${managed}
```

**数活儿**：`answer` 和 `weekly-report` 交出去的东西完全不同 → **2 件活**。

**第一次写错的地方**：一开始把 `search_kb`、`calculator` 也写成 deliverable，一共 4 件活。按 `deliverables-rules.md` 淘汰规则删掉——工具不算活。

> **门禁 12 过**（十字段齐全 + deliverables 校验 + 无字面量密钥）

### 评测

50 条用例（正例 20 + 安全 12 + 职责负例 3 + 边界 15）+ 包自带 smoke。

```
scored_total = 50 − 12 = 38
pass_rate    = 34 ÷ 38 = 0.895
composite    = 90% × total_score + 10% × static_score = 87.4
```

> **门禁 13 过**（`verdict == healthy`）**/ 门禁 14 过**（`composite_100 = 87.4 >= 85`，未环境降级，强度 `real`）

### 裸模型对照

同 10 条真实问题，裸模型 vs 带 Agent：

| 项 | 裸模型 | 带 Agent |
|---|---|---|
| 引用条款号 | 0/10 | 10/10 |
| 编造条款 | 3/10 | 0/10 |
| 口径一致性（两次跑同题） | 6/10 一致 | 10/10 一致 |

→ **明显优于**，保留。

> **门禁 15 过**

---

## 阶段 6：上线与沉淀

第一次优化想自动修一条 `content` 失败（答复里没提"国补"）。**被拦**：`content` 类不能自动修——改提示词让 `must_contain` 通过是对测试集过拟合。

改成人工确认口径后补进知识库。

> **门禁 16 过**（优化前 pass 的 34 条优化后仍 pass）**/ 门禁 17 过**（`real` 用例数 38 → 38，没降）**/ 门禁 18 过**（同一条规则在 ≥2 次独立 run 中出现才立）

**沉淀**：本周 3 次重复的"手册冲突排查"动作 → 交给 `蒸馏` 蒸馏。

---

## 这个样例里的 5 个关键教训

1. **TUI 跑通不是形式**——它发现了一处手册冲突，直接改了规格。跳过它，这个缺陷要到上线才暴露。
2. **接缝选错的成本**——从 3 个接缝减到 1 个，测试量降了但覆盖率升了。
3. **数活儿最容易错**——工具被当成活是高频错误，会让评测范围虚高。
4. **内容类问题不许自动修**——这是防过拟合的最后一道闸。
5. **返工是正常的**——拆解重拆过一次、契约改过一次。门禁的价值就在于让返工发生在便宜的时候。
