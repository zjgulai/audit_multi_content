# 七阶段 SOP

每个阶段固定五项：**输入 / 动作 / 产出 / 准出门禁 / 回退到哪**。

---

## 阶段 0：立项判断

- **输入**：一句话业务需求
- **动作**：过入口三筛（结果不确定 / 需 HITL / 会重复 ≥3 次）；确认取向是垂类不是通用
- **产出**：《立项一页纸》四行
- **准出门禁**：三条筛子全中，且第四行"不做的后果"写得出来
- **回退**：不中 → 不做 Agent，给出替代路径（脚本 / 规则引擎 / 表格公式 / 直接做完）

> 写不出"不做的后果"，说明这件事不重要，先别做。

---

## 阶段 1：问题与调研

- **输入**：立项一页纸
- **动作**：无情追问，把模糊需求逼成可量化问题
- **产出**：解决方案文档
- **准出门禁**：7 问全有答案 + 需求方确认方向 + 方案**不限于一个**
- **回退**：继续追问（不是"先记 TODO 往下走"）

### 追问机制：设计树 + frontier

把决策建成一棵树。每个节点是一个待定决策，会分叉出依赖它的下游决策。

- **frontier（前沿）**= 所有"前置条件已确定、现在就能问"的问题
- **一轮问完整个 frontier**，每题编号、附上推荐答案，**然后停下等答复**
- 用户答完，树变形：已定的决策把 frontier 往外推，解锁下一层
- 依赖本轮某个未决问题的问题，属于**下一轮**，这轮不问

一轮的格式：

```
❓ Q1 - <问题标题>：<问题正文，可多段，可给选项>

➡️ <推荐的答案>

---

❓ Q2 - <问题标题>：……

➡️ <推荐的答案>
```

**两条硬规矩**：

1. **查事实是 Agent 的活，不是用户的活。** frontier 里某个问题需要环境里的事实（文件、代码、数据），派 subagent 去查，不要问用户你能自己查到的东西。
2. **决策是用户的。** 每个决策都要摆到用户面前等答复，不要替他拍板。

**什么时候算完**：frontier 空了——每个分支都走过，没有 silently 假设的东西。**用户确认达成共识之前，不要动手做。**

### 需求量化 7 问

| # | 问题 | 为什么问 | 后面变成什么 |
|---|---|---|---|
| 1 | 现在这件事谁在做？ | 找到真正的用户 | 用户故事的角色 |
| 2 | 多久做一次？一次多久？ | 判断值不值得投入 | 入口三筛第三条的证据 |
| 3 | 现在最容易错在哪？ | 找到价值着力点 | 评测用例的靶子 |
| 4 | 错了的代价是什么？ | 定安全等级 | `safety` 维度权重 |
| 5 | 做出来之后怎么算成功？ | 定验收标准 | `deliverables[].acceptance` |
| 6 | 有没有现成资料/经验可以喂给它？ | 定知识来源 | `tools` 里的检索工具 |
| 7 | 哪些事它绝对不能做？ | 定边界与安全 | 安全用例 + 行为约束 |

### 解决方案文档至少要覆盖

- 问题陈述（用户视角）
- 现状与痛点（**量化**：频次、耗时、错误率）
- 解决路径（**不限于一个方案**）
- 明确写出哪些地方需要人确认（**HITL 点**）
- 边界与不做的事

## 阶段 2：方案与规格

- **输入**：已确认方向的解决方案文档
- **动作**：TUI 跑通 → 原型验疑点 → 写 7 段规格 → **定接缝**
- **产出**：规格（7 段）+ 原型
- **准出门禁**：真跑通过一次 + 接缝已与用户确认 + 范围外写清
- **回退**：跑不通 → 回到阶段 1

### 2.1 TUI 先行（反共识，最重要的一步）

```
业务问题
  ↓
用 TUI（终端 UI）+ 通用 Agent + 对应 RAG/Skill
  ↓
先把这个具体问题真解决掉 —— 拿到一个真实可用的答案
  ↓
把解决路径逆向拆解 → 多步、带输入输出的稳定工作流
  ↓
才补规格文档、才做 UI、才上工程
```

**PRD 不必前置编写**。先跑通，"这个方案到底行不行"几十分钟内就有答案；先写 PRD，要等工程做完才发现方案不成立。

**门禁**：没真跑通过，不给进阶段 3。不要用"我觉得应该可行"代替跑通。

### 2.2 原型只回答一个设计问题

| 项 | 规则 |
|---|---|
| 输入 | **一个**设计问题（这个状态模型对不对？这个界面该怎么长？） |
| 输出 | 一次性产物（逻辑问题 → 单文件 HTML；UI 问题 → 同一路由下可切换的多个变体） |
| 变体数 | 默认 3 个，最多 5 个 |
| 存放 | 一次性分支，不混进主代码 |
| 结束 | 答案**折回规格/主代码**，原型本身留作一手来源 |

**最大的坑**：选错了要验证的分支（该验 UI 的去验逻辑），等于全废。

### 2.3 规格 7 段

不做访谈，直接综合已有上下文。段落与约束：

| 段落 | 写什么 | 关键约束 |
|---|---|---|
| 问题陈述 | 用户视角的问题 | — |
| 解决方案 | 用户视角的方案 | — |
| 用户故事 | `作为<角色>，我想要<功能>，以便<收益>` | 要**极其详尽**，覆盖所有方面 |
| 实现决策 | 要建/改的模块、接口、技术澄清、架构决策、schema 变更、API 契约、交互 | **禁止写具体文件路径和代码片段**（很快过期） |
| 测试决策 | 什么是好测试（只测外部行为，不测实现细节）、哪些模块要测、同类测试先例 | — |
| 范围外 | 明确不做什么 | 防范围蔓延 |
| 附注 | 其他 | — |

**唯一例外**：原型产出的片段若比散文更精确地编码了决策（状态机、reducer、schema、类型形状），可内联进"实现决策"并注明来自原型——**只留决策密集的部分，不要整个 demo**。

规格写完发布到 issue tracker，打 `ready-for-agent` 标签。

### 2.4 接缝（seam）选择

**接缝 = 你打算在哪个边界上测试这个功能。** 这是最容易做错、也最值钱的一个决定。规则与反例见 `seams-tickets.md`。

**接缝必须在写规格时就和用户确认。** 后面 TDD 会严格按这个接缝来，改接缝等于返工。

### 2.5 人工确认点

- 测试接缝是否与预期一致
- 用户故事是否覆盖全
- 范围外是否写清

## 阶段 3：目标与拆解

- **输入**：规格
- **动作**：拆 tracer bullet 垂直切片工单，声明阻塞边，quiz 后发布
- **产出**：工单一票一文件
- **准出门禁**：切片纵向贯穿 + 阻塞边正确 + **用户批准**
- **回退**：重拆

规则见 `seams-tickets.md`。要点：垂直切片四规则、`blocked by` 必填、宽重构走 expand–contract、先 quiz 后发布。

---

## 阶段 4：开发

- **输入**：已批准的工单
- **动作**：在约定接缝上 TDD，一次只推进一个垂直切片
- **产出**：代码提交（必要时交接文档）
- **准出门禁**：接缝已确认 + 每轮都有 red 先于 green
- **回退**：接缝不对 → 回阶段 2

```
红    先写一个失败的测试（必须在写实现之前）
绿    写最小的实现让它通过
重构  清理（重构本身归 code-review 管）
```

**铁规矩**：接缝没确认不写测试；必须在 green 之前有 red；一次只推进一片。

**每一次循环都要跑**：类型检查（频繁）、单个测试文件（频繁）、全量测试套件（最后跑一次）。

大量独立切片可并行时，用 subagent 分发，但每片必须自带上下文（规格摘录 + 接缝 + 验收标准），不要指望子 agent 读全量仓库。

---

## 阶段 5：验证与上线

- **输入**：完整实现
- **动作**：双轴 review → 三级验证 → 过门禁
- **产出**：review 报告 + 评测报告（**只交付 HTML**）
- **准出门禁**：双轴都过 + `composite_100 >= 85` + 未环境降级 + 证据强度 strong + 明显优于裸模型
- **回退**：进 opt 流程修副本

### 三级验证

| 级别 | 验什么 | 判据 |
|---|---|---|
| 代码级 | 实现对不对 | 双轴 review + 测试套件 |
| 能力级 | 答得好不好 | 评测集通过率 |
| 业务级 | 有没有用 | **以裸模型为基准的同场景对比** |

### 双轴 review

两轴并行跑，**互不污染**：

| 轴 | 问什么 |
|---|---|
| Standards | 这些改动符合本仓库的编码规范吗？（含 smell 基线） |
| Spec | 这些改动忠实实现了最初的 issue / 规格吗？ |

**执行前提**：固定点（commit / 分支 / tag / merge-base）必须可解析，diff 必须非空，否则不派 subagent。没有规格时跳过 Spec 轴。

### 裸模型对照（整套体系的验收根）

1. 选同一批真实场景问题
2. **裸大模型跑一遍**，记录输出
3. 带 Skill/Agent 跑一遍
4. 对比**输出质量**和**稳定性**
5. 更优才保留；Skill 池到 2000+ 规模后做组合测试减资，剔除冗余与降质项

> 判据原话：没有 skill 跑得比裸模型还好，那这个 skill 就是废物，就是在降质。

## 阶段 6：上线与沉淀

- **输入**：已上线的 Agent
- **动作**：交接、迭代、把重复动作蒸成 Skill
- **产出**：交接文档、成长记录、候选 Skill 清单
- **准出门禁**：留出门禁（优化前 pass 的优化后仍 pass）+ 强度门禁（`real` 用例数不下降）
- **回退**：回滚该次优化

### 归因三分派

| 类别 | 判据 | 能否自动修 |
|---|---|---|
| `structural` | 实现缺陷（工具桩抛 `NotImplementedError`、作答为空违背协议） | **能** |
| `content` | 作答内容不合期望 | **不能**，交还人工 |
| `environment` | 环境降级 / 缺模型端点 | **不能**，改码无效 |

**为什么 `content` 绝不自动修**：改提示词让某个 `must_contain` 通过，是针对测试集过拟合，不是提升能力。**防过拟合靠留出集，不是让人去拟合已有用例。**

### 成长必须可证伪

| 防线 | 规则 |
|---|---|
| 不写没有证据的规则 | 规则必须指向 **≥2 次独立 run** 的 observation |
| 不假装做了做不到的事 | 能力阶梯只按证据晋级；训练类任务标 `blocked` |
| 不用环境问题衡量成长 | 成长曲线只统计真正校验了作答内容的用例 |

**"证据不足"是合法结论。** 没有模型端点时全部用例拿不到作答、没有一条 `real` 证据，此时报"成长"或"退化"都是编造。

### 沉淀

重复 ≥3 次的动作 → 交给 `蒸馏` 蒸馏（**自己创建的 Skill 必须优先自用**——自己都不敢用，说明 Skill 有缺陷）。
