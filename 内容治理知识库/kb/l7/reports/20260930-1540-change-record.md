**怎么发现的**：`read` 工具报 `binary file` —— 宿主侧（node）读不出来，而 python 侧一切正常
（这正是指南说的「用自己的语言自检看不见信封」）。

**怎么修的**（没有猜结构，先验证再动手）：

1. 用 python 视角把两份文件 dump 成 `/tmp/{p0,recall}.dump.txt`（python 读得穿信封，内容即预期内容）；
2. 确认 dump 内容完整（含新 §写档档位、version 1.1.0）；
3. 用**干净通道** `/bin/cp` 把 dump 落回原路径；
4. 逐项验证：`wc -c` == python `getsize`（7493 / 9539）、`od -c` 首 3 字节为 `---`、`read` 工具可读。

**为什么没有扩散**：两处只改了**库内源**，**装位还没回灌**，所以装载位一直是干净的 v1.0.0；
修正后才 `cp -p` 回灌，并 `cmp` 逐字节确认一致。

**复查**：`kb/kbpy l8/envelope_census.py` → **结论 OK**（信封只剩已知的归档证据 + 可再生备份两类，本轮新增的 0 个）。
**纪律重申**：**写 `.md` 一律走 node 或 `/bin/cp`，绝不用 python**；写完必须用**非 python 通道**读回校验。

## ⑦ 评测期污染事件（2026-09-30 15:4x，留痕）

**事实**：会话的 skill 目录里，`kb-canonical-lookup` 一度显示为

> 【SHADOW-PROBE】这是项目级影子副本，用于验证项目根 .dsh/skills 是否覆盖用户级同名 skill。

即有人在**项目根建了 `.dsh/skills/kb-canonical-lookup/SKILL.md`**，按宿主的装载位优先级**顶掉了用户级真品**
（`~/.dsh/skills/kb-canonical-lookup/`）。该影子文件现已不在（有界排查：工作区根无 `.dsh`、
三层内无 `.dsh`、工作区根与三个评测工作台内无 `SHADOW-PROBE` 残留）。

**为什么必须当事故处理**：影子存在期间跑的任何**盲测轮次**，被测会话看到的是影子副本而不是被评测的 L4 skill
→ 那一轮的「触发/不触发」判定作废，F1 会被系统性压低（FN 虚高）。带着这种数字出报告 =
把环境污染当成 skill 缺陷。

**处置**（按批驱动纪律「先核对落盘、再判定」）：

1. **中断**受影响的评测 subagent（`kb-canonical-lookup` 那个），要求**从零重跑 3 轮**，
   并说明影子是否影响过已跑的轮次；
2. 向另一个评测 subagent 发**预防性禁令** + 要求自查自报；
3. **写入范围收紧为硬约束**：评测 subagent 的唯一可写位置 = 各自工作台目录；
   **禁止**写 `…/kb/**`、`~/.dsh/skills/**`、`~/.agents/skills/**`，
   以及**工作区根或任何祖先目录下的 `.dsh/`、`.agents/`** —— 这次污染正是这条边界被越过造成的；
   要验证「宿主怎么解析 skill」只许**只读观察**，不许建影子文件；
4. 因此本批评测的 **F1 数字必须标明「影子清除后重跑」**，否则不予采信。

**教训（可复用）**：skl 评测这类「靠宿主解析 skill 来判定触发」的测试，**环境本身也是被测对象的一部分** ——
任何在装载位上留下的探针都会直接篡改测试结果。评测前后都应核一遍装载位与 catalog 是否干净。
