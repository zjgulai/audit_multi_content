## 3. 两条「服务活着但链路可能已断」的风险（本次新发现，未被任何闸门覆盖）

### 风险 1：写入通道 node 偶发 -9，降级路径**无声**

闸门④ leg④（沙箱重生成）实录：
```
[gen][warn] node 落盘第 1/2/3 次失败（-9），重试
[gen][warn] node 落盘失败（-9）：
[gen][warn] 退回 python 写盘：宿主侧加载器可能读不出这批条目（会被封成信封）
沙箱产出 510 md / 信封 510；加载器直读 E001 509；health 50
```
- 机制：`gen-host-library.py: resolve_node()` 三条候选（PATH node → DSH Electron → ChatGPT node）
  全部被 **SIGKILL(-9)**。本会话独立复现：ChatGPT node `Killed: 9`、Cursor node -9。
  疑似与 `kb/view/_meta/GUIDE.md` §八 记的注入型监控/加密代理（`/usr/local/.trld`）有关。
- **危险点**：`write_text_plain()` 降级**正常返回、不抛异常**，生成器退出码仍 0；
  `publish.sh` 只检查 `if ! … gen-host-library.py`，**退出码检查对此完全无效**。
  → 一次偶发 -9 就能把整个视图变成 510 条信封（框架 health 78 → 50、E001 509），**且发布链不报错**。
- 现况：DSH Electron node **实测 3/3 正常**（读 9762 字节），故当前活库**未受损**。
  这是**已装引信未引爆**，不是已发生的损坏。

### 风险 2：服务用 python 读、加载器用 node 读 —— 信封对两者不对称

- `kb-hostlib-serve.py:62` 用 `open(path, encoding="utf-8")`，**python 通道看得见信封**。
- 加载器所在 DSH 运行时是 node 通道，**看不见信封**。
- 后果：视图一旦被封信封，**服务照常吐出全部 1347 篇（看起来完全正常）**，
  而加载器同时报 509 × E001。**外部体检只看服务 health=200 会给出假绿灯**。
