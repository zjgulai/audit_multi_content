# 守衡调用层（POST /review）· 变更与验收记录

- **时间**：2026-09-30
- **目标**：让「守衡」（= 飞书应用 `dsh-kb` / `cli_aa2243de0438dcd7` 的 bot 身份）能调用知识库的评审工作流
- **本轮结论**：**本机侧就绪并验收通过（4/4）；守衡侧通路未配，端到端「从飞书调一次」尚未完成。**

---

## 1. 为什么是 API，而不是"让守衡加载 skill"

skill（`kb-review` → 专项 → `kb-content-review` → 裁决）是给 **agent** 的入口；
守衡是 **bot**，它的运行时里没有 skill 加载机制。所以给机器开了同一条链的 API：

```
守衡(bot) ──HTTP──▶ POST /review ──▶ 依据(P0 + 509 条 + BM25) ──▶ decide() ──▶ 三态结论
                                            ▲
agent ──skill 文本──▶ kb-review ──让位──▶ 专项 ──▶ kb-content-review ──┘   （同一套引擎）
```

关键：**这条 API 是确定性的、不经过 agent** —— 无人值守安全，也不依赖那个还没确认的无头入口。

## 2. 改了什么（两处代码 + 一处服务）

| 文件 | 改动 | 为什么 |
|---|---|---|
| `kb_api.py`（工作区根，**不在 `kb/l7/**` 里**） | 新增 `POST /review`（走 Bearer token，与既有路由同服务/同端口/同引用契约）；API 路径传 `write_report=True` | 守衡原来只能"查"（`/match` `/search` `/rule`），没有"评" |
| 同文件 | import 前 `os.environ.setdefault("KB_INTERP_OK","1")` | **服务原先冷启动会失败**：`kb/l6/retriever.py` 的**导入期**解释器守卫会 `execve` 成 `python3 retriever.py <uvicorn 的参数>` → argparse 报错退出。原来跑着的那个进程不是这样起来的，所以问题一直没暴露 |
| `kb/l7/review-engine/core/with_kb_evidence.py` | 加 `write_report` 参数 + 回传 `report_path` | 适配器默认 `--dry-run`（冒烟用）→ API 调用不落盘，没有审计痕迹 |
| `com.dsh.kbapi`（launchd） | `launchctl kickstart -k` 重启（uvicorn 无 `--reload`） | 让新代码生效 |

备份：`kb/l7/_backups/kb_api.py.bak-<时间戳>`。

## 3. 验收（4/4，实测）

| # | 判据 | 结果 |
|---|---|---|
| 1 | 调得通、结论对 | `state=BLOCK` ｜ `confidence=0.97` ｜ `issue_count=10` ｜ `evidence_complete 10/10`；每条带 条款号 `W-1.18` / 库《措辞表达库》/ anchor / `source_sha256` |
| 2 | 幂等 | 同文本两次：`state` 相同、`content_version` 相同（= sha256）、`review_id` 不同 |
| 3 | 鉴权 | 无 token → **HTTP 401** |
| 4 | 不伤老路由 | `/match` 仍返回 H05 / P0 / BLOCK |

补充：`/review` 响应带 `report_path`（如 `kb/l7/reports/20260930-120823.review.md`），
且该报告 **python getsize == node statSync().size（差 0）** —— 宿主读得到，不是信封态。
响应里显式带 `confidence_note`「启发式，未做金标标定；不得当成法律合规概率」。

## 4. 守衡侧还差什么（两条路，都需要飞书侧配合）

| 路 | 机制 | 前置 | 实测现状 |
|---|---|---|---|
| **(a) 长连接事件**（推荐，不需要公网） | 本机 `lark-cli event consume im.message.receive_v1` → 调 `/review` → `lark-im` 回帖 | 守衡应用要开**事件订阅**、启总线 | ⚠️ `lark-cli event status` 显示的是**另一个应用** `cli_aa2e11d952f85be9`，且 `Bus: not running` —— 与守衡不是同一个 app |
| **(b) 公网直调** | 守衡（云端）HTTPS 调 `/review` | 8787 要挂上公网 | ⚠️ 现有 ngrok 隧道 `scrambled-collision-exception.ngrok-free.dev` 的目标是 **4401（工作台）**，不是 8787 → 需另开隧道 |

**安全前置（做 (b) 之前必须做）**：`kb_api.py` 监听 `0.0.0.0`，token 默认值是 `dsh-kb-dev-token`
（plist 里也写死了这个默认值）→ 同网段任何人都能查库。**先把 token 换成随机值**（plist 的
`EnvironmentVariables.KB_API_TOKEN` + 调用方同步），再考虑暴露到公网。

## 5. 诚实边界

1. **没有从飞书侧真实调用过一次** —— 本机 curl 4/4 通过，但守衡侧事件订阅/隧道都没配，
   所以「守衡可调用」目前是**通路就绪、端到端未验**。
2. `/review` 只覆盖**文字**模态；图片/视频各自专项的证据链未按本手册验证。
3. `confidence` 是启发式（引擎自述未做金标标定）；`coverage` 里图片/视频标 `not_applicable`，
   不是"检查过没问题"。
4. 服务此前**冷启动会失败**这一点：本轮修了，但说明 `com.dsh.kbapi` 的 `KeepAlive` 一直在重启失败循环里 ——
   建议顺手看一眼 `/tmp/dsh-kbapi.err` 的历史（我只看了尾部）。
