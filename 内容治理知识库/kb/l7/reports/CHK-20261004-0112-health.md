## 5. 并发观察（环境风险，不是库的缺陷）

**先说方法学限制**：本机的 bash 每次调用都新起一个 shell，**ppid 数 ≠ 会话数**。
所以下面分「已确认事实」和「合理推测」两栏，不许混着读。

**已确认事实（可复核的读数）**

- `kb_loop_claim.py status` → **「无认领」** ⇒ 采样时没有任何会话持有循环的全局单槽。
- 采样瞬间 `ps` 里 **两个 `l8/workflow_check.py` 进程的 ppid 都是 `76788`** ⇒
  那是**同一个会话**先后起了两次（`CHK-20261004-0105`、`CHK-20261004-0106`），
  **不是两个会话在抢**。（本表初稿曾写成"2 个会话"，实测后已改 —— 记录在此以免误读。）
- `kb/l7/runs/index.jsonl` 现有 1083 行、**107 个 RUN id 重复**，其中 **80 行带 `write_merges`**
  （同 run 幂等合并；例如 `20261004-0054` 带 `previous_at` + `write_merges:1`）。
  ⇒ **不下"双计事故"的结论**：绝大多数重复已归因到合法合并，其余**未逐条归因，标"未判定"**。
- `_chk-run-20261004-0110/` 的 `run.sh` 时间戳为 01:09、`RUN.txt` 为 `CHK-20261004-0110`
  ⇒ 跑表前后确有**另一套体检档**在开跑，其产物目录 `_chk-run-20261004-0110/` 与本轮并列存在。

**合理推测（写出依据与推翻条件）**

- 采样瞬间有 **7 个以上 `l6/retriever.py` 进程分属 6 个以上不同父 shell**，且命令行引号风格／脚本结构各不相同
  → **推测**同机同时有多个独立 agent 会话在检索。
  **成立条件**：父 shell 分属不同会话。**推翻条件**：若这些父 shell 其实来自同一条会话的并发工具调用，则只有一个会话。
  **本轮无法证实或证伪**（ppid 不携带会话标识）。

**风险提示（照抄库内纪律，不是本轮的发现）**：这条循环**同一时间只准一个会话跑**；
不同 BASE 的第二个会话**照样**该被全局单槽挡住（`kb_loop_claim.py` 是**全局单槽**，不分槽）。
体检档不属于循环、不受该锁约束 —— 所以多个体检档并发不会被拦，
但也因此**没有任何机制**防止多份体检表互相覆盖读数。
**本轮据此采取的做法**：只跑只读闸门、零修复、不动 `kb/l0…l6` 与 `kb/l7/registry/*.yaml`。
