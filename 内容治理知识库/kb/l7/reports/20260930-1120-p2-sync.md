## 1. 命令面

```bash
# 预演（默认）：跑闸门 + 跑引擎的干跑档，不落盘
kb/kbpy l7/scripts/kb_pipeline.py --sync --only L2

# 落盘（要显式加 --apply；写档白名单目前只开 L2）
kb/kbpy l7/scripts/kb_pipeline.py --sync --only L2 --apply --run 20261001-0830
```

- `--sync` **必须点名层**（`--only L1,L2` 或 `--all`），不点名直接拒（exit 2）。
- 写档白名单 `SYNC_ALLOWED = ["L2"]`（两周只读观察期的口径）。要跑别的层，必须显式
  `--allow-beyond-policy` —— 越界要**说一声**，不是顺手就能跑。
- L0 **没有**写档引擎登记：它的写档一律人工（飞书 token 有效期只有 ~2h）。

## 2. 三条红线（都在代码里，不靠人记）

| 红线 | 实现 | 实测 |
|---|---|---|
| ① 先归档再写 | `ARCHIVE_BEFORE_WRITE = {"L3": ["kb/l3/rejected.jsonl"]}`：写 L3 前把台账复制到 `kb/l3/_archive/rejected-pre-<run>.jsonl`，**逐字节复制 + sha256 校验**；归档失败即拒绝写 | 归档成功且 sha 一致（4,216,927 字节）；把归档目录改成不可写 → exit 1 拒绝（E2） |
| ② 编排器自己持锁 | `kb/.work/.kb.lock`，`O_CREAT\|O_EXCL` 抢锁；**锁分四态**（见 §3）；`finally` 里必然释放 | 造一个「持有者还活着」的锁 → exit 2 拒绝（C） |
| ③ 遇红即停 | 每层写之前先跑该层闸门（白名单里的），红就不写这一层、**也不往下走** | 把夹具里的 L2 闸门改成必红 → exit 1，**停机且数据一个字节没动**（D） |

## 3. 顺带挖出来的一个真问题：库上躺着一个 2026-09-24 的旧锁

第一次跑 `--sync --only L2` 就被它挡住了 —— `kb/.work/.kb.lock` 里是：

```json
{"run_id":"20260924-1730","pid":94890,"at":"2026-09-24T17:18:17",
 "status":"finished_partial","released_at":"2026-09-24T17:45:00", ...}
```

**上一个持有者自己宣布结束了（`released_at` 有值），只是没删文件。** 这类锁要是当成
「有人在跑」，写档编排就**永远起不来**（`.work/batch*.py` 撞到同一文件也是直接退出）；
反过来，把「pid 死了」一律当陈旧自动删，又会在真崩在中途时**偷偷放行第二次写**。

所以锁分四态：

| 状态 | 判据 | 预演档 | 写档 |
|---|---|---|---|
| `absent` | 文件不在 | 抢锁 | 抢锁 |
| `held-alive` | pid 还在 | **拒绝** | **拒绝** |
| `stale-declared` | pid 不在 **且** 有 `released_at`／`status=finished*` | **告警后放行**（不写盘，不抢锁） | **拒绝** —— 要人删掉它或 `--break-lock` |
| `held-dead` | pid 不在，且**没宣布释放** | 拒绝 | 拒绝（先判断有没有写坏） |

**本编排器不自动撬锁**：撬锁永远是人拍的板。那个 2026-09-24 的旧锁**本轮没删**
（它不是我的产物，也不在 `kb/l7/**`），已按上面口径如实报出来 —— 谁开写档谁先处置它。

## 4. 演练（`kb/kbpy l7/scripts/_sync_drill.py`）—— 8/8

在**夹具库**上真跑 `--apply`；夹具是 `kb/` 的镜像（真目录 + 文件软链），凡引擎会 append 的
文件都先换成**真副本**，所以写档动作伤不到真库。真库在演练前后各取一次 sha256 复核。

| 用例 | 结果 |
|---|---|
| 0 夹具就绪 | ✅ 夹具 L2 三份数据与真库逐字节一致（是真副本，不是软链） |
| A 预演不落盘 | ✅ exit 0，数据 0 变化，引擎自报 `[dry-run] 未落盘` |
| B 写档幂等 | ✅ run1/run2 都 exit 0，**两次后三份数据逐字节相同**，run2 报「产物变化 0 个」 |
| C 红线②锁 | ✅ exit 2，报「持有者进程还活着（pid=…）」 |
| D 红线③红闸门即停 | ✅ exit 1，`闸门：**红**` → **停下**，数据未动 |
| E 红线①归档 | ✅ exit 0，归档 sha 一致 |
| E2 归档失败即拒绝 | ✅ exit 1，报红线①不通过 |
| F 真库一个字节未动 | ✅ L2/L3 四份台账 sha256 前后一致 |

### 演练台两次踩坑（记下来，都是「夹具没做对 → 结论是假的」）

1. **夹具根下必须有一层 `kb/`**：引擎/闸门里全是 `kb/...` 相对路径，按 cwd 解析。
   少了这层，读取会**穿透回真库**（反测台也踩过同一个坑）。
2. **`kb_pipeline.py` 必须是夹具里的真副本**：它用 `__file__` 反推 `KB`；若还是软链，
   编排器会以为自己在真库上跑 —— **这是能写坏真库的那个错**，所以它排在 `REALIZE` 列表第一位。
   同理 `layers.yaml` 里的 `cwd` 要改写成夹具根。
