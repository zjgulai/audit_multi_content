## 5. 待确认（按 SKILL §6.1：事实 + 建议 + 理由 + 取舍）

### ① 根因未除：装载位改了不回灌库内源，下一次改动还会红

- **事实**：kb-l0-feishu 自己的 `SKILL.md §8.3` 规定的改文件流程是「备份 `~/.dsh/skills/kb-l0-feishu` → 追加 `references/CHANGELOG.md` → bump 版本 → 验明文」，**全程只在装载位上操作**，没有「回灌库内工作副本」这一步；而 `skills.yaml` 把 `l7/skills/kb-l0-feishu/` 登记为 source，`skills_check` 第 3 类逐文件比对。两者口径不一致 → 每改一次装载位就红一次。`references/gotchas.proposals.md` 更是 `scripts/retro.py` 每轮自动追加的文件，漂移会**反复发生**。
- **我的建议**：**改 `SKILL.md §8.3`，把流程补成「装载位改完 → rsync 回灌 `kb/l7/skills/kb-l0-feishu/` → 再跑 `skills_check` 证明 3 类归零」**（version bump 到 v1.2.4，CHANGELOG 记一条，依据写本 RUN）。这是**规则层改动**，按该 skill 自己 §8.2「规则层不许自动改」，我**没有动**。
- **理由**：不动的话，闸门绿是临时的——下一轮 L0 同步跑一次 `retro.py` 就会再红一次，值班人会把这条真信号当噪声忽略。
- **取舍**：另一种做法是把 `references/gotchas.proposals.md` 这类机器生成物排除出副本比对（改判据），但那样会让「源与实装脱节」这件事也一起失明；相较之下补流程更保守。**不做**的代价 = 每次改 skill 都要人工发现并修一次。
