## 三、为什么不认这条 PASS（**判断，非引擎结论；每条都给了可核依据**）

### 3.1 依据侧给的其实是「拒答」，被适配器转成了 PASS —— 这是最硬的一条

**已确认事实**（同一份引擎 JSON 内自相矛盾，可直接回读 `/tmp/img01-review-rerun.out`）：

- 顶层：`decision.decision = "PASS"`
- 同一份 JSON 的 `evidence_meta.state = **"拒答"**`

依据侧的判据原文（`~/.dsh/skills/kb-content-review/scripts/review.py:704-728`）：

```
covered = bool(safe_hits or cited_unit_hits)
...
    state = "PASS" if covered else "拒答"
```
其 `why` 字段逐字写着：*「PASS 必须建立在『知识库认识这个主题』之上：① 命中允许表述（安全词）规则；
② 单元层 Top3 里有一条既被规则引用、BM25 原始分又 ≥ 16.0；**两者都没有 → 拒答（无命中不等于合规）**」*

本次实测量的三个数：`safe_vocabulary_hits = []`、`rule_cited_unit_hits = []`、`covered = false`
（`rule_cited_anchor_pool = 959`，`coverage_bm25_min = 16.0`）。
⇒ 按 review.py **自己写的判据**，本单该出「拒答」。

**断点在哪**（代码位置已定位）：适配器 `kb/l7/review-engine/core/with_kb_evidence.py` 的 fail-closed 守卫是

```python
if str(ev.get("state") or "").upper() == "NEEDS_INPUT":   # ← 比的是这个哨兵值
```

而 review.py 在**覆盖信号不足**这条路径上给的哨兵值是 **`"拒答"`**（中文），不是 `"NEEDS_INPUT"`
—— 两者都出现在 review.py 里，映射成 `NEEDS_INPUT` 的那一处（`review.py:1188`）在
`report_memory_payload()` 里，**不是适配器读的那份 JSON**。
⇒ 守卫不触发 ⇒ 空 `findings` 直接喂给 `decide()` ⇒ **拒答被静默读成 PASS**。

这**正是**该文件注释里声称已修的那个洞，原文：

> *「依据侧**拒答**必须原样传下去（fail-closed 不许被打穿）…… 空 findings ⇒ `risk_items=[]` ⇒ `decide()` ⇒ **PASS**。⇒ **拒答被下游静默转成了放行**。」*

修是修了，**只修在另一个哨兵值上**。所以本次的 PASS，成立前提是「把一次拒答读成了零问题」。

### 3.2 图片本体从头到尾没有被读 —— 模态覆盖是缺口，不是「不适用」

**已确认事实**：

- 用户称送审「图片」，实际到达的只有**文字层 6 行**；**无文件、无可读 URL、无内容哈希**。
- 引擎 payload **写死** `content_type = "text"`、`coverage.image = "not_applicable"`，
  并自带一句 `note`：「本批只送审文字；其余模态不适用（**不是缺口**）」。**对图片送审而言这句话是错的。**
- `multimodal-provider-contract.json` 要求的 `provider / provider_version / content_hash / status`
  四项**一项都拿不到**。

**已确认事实（口径，`confirmed_by_user`）**：`kb/l7/review-engine/knowledge-base/input-scope.json` 的 `rule` 逐字：

> *Do not emit PASS until a URL or file is actually readable and required modality coverage is complete.*

⇒ 图片既不可读、模态覆盖也不完整，**按已确认口径不该出 PASS**。
`图片安全审查` skill 正文同向：图太小 / 遮挡 / 歧义不足以为安全事实定性时，出 `REVIEW` 或 `NEEDS_INPUT`，不出 PASS。
