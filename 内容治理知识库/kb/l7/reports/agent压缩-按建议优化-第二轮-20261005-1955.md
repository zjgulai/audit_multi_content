## 我自己的三个缺陷（逐个认）

1. **`or not d.get("issue_count")` 把合法 PASS（问题数 0）误判成「没拿到结论」** → 条件收窄。
2. **stderr 并进 stdout**（`2>&1`）⇒ 引擎的「飞书发布：…」日志排在 JSON 后面，模板解析失败 → stderr 单独走 mktemp。
3. **heredoc 拼接失误**：我用 python 替换模板时，`s.index("PYEOF", start)` 命中的是**开头那行**里的 `PYEOF`，
   于是新模板与旧模板死代码拼在一起、中间留下 `PYEOF'` ⇒ heredoc 一路吃到文末，
   python 读到 `PYEOF'` 直接 SyntaxError ⇒ **模板从未渲染过**。
   **这个缺陷是 agent 自己诊断出来并回报的**（round8b 链接单），不是我发现的。

⇒ **更严重的连带结论**：**round8 的提速不是模板带来的**（模板当时根本没跑通），
是手册那两条硬规则带来的。这点必须写清，否则等于把功劳记在没生效的改动上。
更正的完整版见 `report-output-contract.yaml` 的 `correction_20261005_review_run_heredoc`。

**教训**：替换代码块后必须**跑一次真实调用**验证，不能只验证被抽出的代码片段。

## 两条"看着能做、其实不能做"的（重要更正）

### ① P0 扩面 **不是接线**
`kb/l5/p0_patterns.jsonl` **就是 7 行**（L5 索引 7 行，历史快照 6~7 行），快路**已经 100% 加载**。
⇒ 扩面＝**新写红线规则**（要条款号依据 + 走 kb-pipeline 写档），是判据变更，得你拍板。
我最初把它写成「扩面（现只有 7 条模式）」，**说轻了**。

### ② 图片在 CLI 上**永远不可能 PASS**（结构性，未修）
`with_kb_evidence.py` 的 `coverage_provided` **只是函数参数、没有 CLI 口子**；
而 `_coverage_for` 对 `--content-type image` 无条件要求 `image`+`ocr` 带 provider 佐证，拿不到就记 `incomplete`
⇒ 走 CLI 的图片单**只能 NEEDS_INPUT**。
**而图不是判不了**：本机 OCR 完好，实测图里读出 **177 字**正文（`Bereit Fur Die Nacht, Supermama…`，880×1100），
provider 佐证其实都在手上 —— 只是没有口子交给引擎。
**未修**：加这个口子会让「图片可以 PASS」这个此前不存在的结论变成可能，属**改判据**，按库规要单独报批。
