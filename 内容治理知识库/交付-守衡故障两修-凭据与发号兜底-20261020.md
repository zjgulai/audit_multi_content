## 一、两个独立缺陷（不是一个）

| # | 缺陷 | 后果 | 证据 |
|---|---|---|---|
| A | lark-cli 的凭据**靠 macOS 钥匙串**解主密钥；钥匙串在自动化上下文里间歇性不可用 | 所有飞书调用失败（发布、设可见范围、发号读表） | 守衡日志 14:10 `设可见范围失败：keychain Get failed: keychain access blocked`；**注意这条是 `[agent]` 前缀 = 守衡主进程（launchd 起、不受 DSH 沙箱管辖）报的** |
| B | `content_id.list_table_content_ids()` 只 `except Exception`，而 `feishu_publish._lark_run` 抛的是 **`SystemExit`（`BaseException`，不是 `Exception`）** | 一个读表失败 ⇒ **整个引擎 exit=1、stdout 0 字节** ⇒ 结论 / 旁挂 / 报告 / 表行**全丢**，用户只看到「出故障了」 | 假 lark-cli 逐字复现：`rc=1 ｜ stdout 0 字节 ｜ stderr 只剩那一行` |

## 二、改了什么

### A. 凭据层：走 lark-cli 官方支持的降级（不改代码）

```bash
lark-cli config keychain-downgrade
# → /Users/lute/Library/Application Support/lark-cli/master.key.file
```

官方原文（`lark-cli config keychain-downgrade --help`）：「This is the supported fix for
environments like the Codex sandbox where the system Keychain is blocked.」
钥匙串条目**保留为冷备份**，命令幂等。

**代价（必须记住）**：主密钥从此是一个**普通文件**，同机同用户的任何进程都能读
（文件权限取代了钥匙串的 per-app ACL）。这是「自动化要能跑」与「凭据只对指定 app 开放」之间的取舍，选了前者。

### B. 韧性层：`kb/l7/review-engine/core/content_id.py`

1. `list_table_content_ids()` 增加 **`except SystemExit`** 分支 ⇒ 退回「读不到」，**不编号**；
2. 同时堵第二颗雷：`_lark_run(allow_fail=True)` 返回 `{"ok": false}` 时，原先 `d = {}` ⇒ `out=[]`
   ⇒ `next_seq([])=1` ⇒ 发出 `AD-…-001` **与表里已有号撞车**。现在按「读不到」处理。

两条都只改**失败路径**：`resolve()` 原本就有「拿不到号 ⇒ 退指纹 `AUTO-<sha12>` 并写明原因」的口径，
本次只是让它在 SystemExit 这一档也走得到。

# 追加（2026-10-20 15:1x）· 第三处：发号恒 `001`（Owner 追问「为什么旧单还有记录」后查出）

## 病灶
`list_table_content_ids()` **只读第一页 100 行**（`lark-cli base +record-list` 默认 `--limit 100`），
而结论表已有 ~190 行 ⇒「内容 ID」只看得见**最早那 100 行**，当天新写的行全在第 2 页、**永远看不见**
⇒ `next_seq([])=1` ⇒ **每一单都发 `AD-20261020-001`**。

实测（`--offset 100` 补读第二页后核表）：**今天 6 行共用同一个业务号**

| 写入时间 | 内容类型 | 结论 | 业务号 |
|---|---|---|---|
| 10:09:49 | image | PASS | `AD-20261020-001` |
| 11:24:38 | image | REVIEW | `AD-20261020-001` |
| 12:44:39 | image | REVIEW | `AD-20261020-001` |
| 14:22:14 | image | PASS | `AD-20261020-001` |
| 14:32:41 | text | REVIEW | `AD-20261020-001` |

⇒ 后果两条：① 按内容 ID 幂等的 upsert **认不出是哪一单**（15:12 那单落表是 `updated` 不是 `created`）；
② 按内容 ID 去重的三态统计会把 5 单算成 1 单。**这不是「重发」造成的，是全天都在砸。**

## 修法

# 追加二（2026-10-20 15:2x）· 第四处：**没有单实例互斥**（Owner：「重发就会撞上新老两单并行，这是 bug」）

## 病灶
`ws_daemon.mjs` **没有任何单实例闸门**，而 `shutdown()` 在 `process.exit(0)` 之前要
`await ws.stop?.()` —— 有链在飞时（单条 10~30 分钟）旧进程会继续活着；
launchd 的 `KeepAlive{SuccessfulExit:false}` 与此同时已经把新进程拉起来了。

⇒ **两个守衡同时连着飞书**。三条后果：
① 同一条消息被两个进程各处理一次（群里两条回执、两条结论）；
② 两条链并行 ⇒ 同一素材**开两单**（Owner 说的「重发就撞两单」就是它）；
③ 两个进程各写一份 `seen-messages.json` ⇒ **去重表互相覆盖**。

实测：同一 `msg`（`om_x100b625b636330a4b077dde11074e90`）在 `+2160s` 与 `+2973s`
被**完整处理两遍**（两次回执、两次起链）；今天 7 次重启（11:07 / 11:41 / 11:47 / 12:18 / 13:02 / 13:05 / 14:26）。

## 修法（代码在 `tools/`，不在本库）
- 新增 `tools/agent/single_instance.mjs`：占位前先判断持有者——**pid 活着且 `ps` 命令行含 `ws_daemon`** 才算「占着」；
  pid 已死／命令行不含 `ws_daemon`（pid 被复用）⇒ 按陈旧接手。锁**原子写**（tmp+rename），只删自己那份。
- `ws_daemon.mjs`：**建连之前**占位，占不到就 `process.exit(75)`（ex_tempfail ⇒ launchd 10 秒后重试，即「等」不是「并排跑」）；
  `shutdown()` 里 **先 `ws.stop()`（8 秒上限）再释放名额** —— 顺序反了就白做（名额一放新进程立刻建连，两连接并存的几秒又是同一个病）。

## 判据（含反向对照）
- `node tools/agent/single_instance.test.mjs` → **16/16**
  - A2「活实例拦得住」：拆掉 liveness 判断 ⇒ **精确变红**（已实做变异验证）
  - B1「复用 pid 不算占位」：把 `isLiveDaemon` 退化成只有 `process.kill` ⇒ **精确变红**（已实做）
    ⚠️ 第一版 B1 用 pid 1 取样，**假绿**——非 root 下 `kill(1,0)` 直接 EPERM，根本走不到 `ps` 那一步；
       改用本测试进程自己的 pid 才真测到。

  **建连之前**就退出（进程数仍为 1）。
- 既有回归未破：`node tools/agent/claim_preflight.test.mjs` **12/12**。
