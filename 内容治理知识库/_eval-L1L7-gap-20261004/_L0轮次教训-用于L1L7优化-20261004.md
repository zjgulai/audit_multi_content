## 二、八条教训

> 写法：**现象 → 依据 → 对 L1–L7 的动作**。前三条是「量具」，中间两条是「判据」，后三条是「纪律」。

### 教训 1（最贵的一条）★ 量具先于被测物：限时低于中位数时，分数测的是限时

- **现象**：v1.3.0 在 120s 下 79.0，看起来像**比起 v1.2.9 的 83.5 退步**；换 600s 变 85.7。
  即：**同一份 skill，分数从「封顶不合格」翻到「达标」，一个字的正文都没改。**
- **依据**：600s 批次的**中位数是 139s**，而 120s 口径的上限**就是 120s** ⇒ **超过一半的用例本来就要 120s 以上**。
  那条上限切掉的不只是长尾，是**中位数本身**。120s 下 187/312 超时、79 条空回复。
- **对 L1–L7 的动作（已做）**：L1–L7 批跑**统一 `--timeout 600`**，并**先跑基线**看中位数，
  再决定是否够用。**中位数逼近上限就说明口径不够，不许拿去评分**。
- ★ **可推广成一句前置条件**：**先证明量具的能量程覆盖被测物的中位数，再谈优化被测物。**

### 教训 2 ★ 接线先于优化：一个路径 bug 能造出「看起来很合理」的全假分数

- **现象**：第一版复测线 15 条记录全是 `reply=""`、`session_id=null`、`skills_loaded=[]`，
  而模型**其实答了**（正文在被截断的 `stdout_tail` 里）。
- **依据**：`session_dir_for()` 用 `os.path.abspath(cwd)` 拼会话目录名，而 macOS 上 `/tmp` 是
  `/private/tmp` 的软链 ⇒ 算出 `--tmp-…`，真实目录是 `--private-tmp-…` ⇒ **永远读不到会话**。
  **若拿去评分，全部用例都会被判「不触发」，P/R/F1 全是假的。**
- **对 L1–L7 的动作（已做）**：通用 harness 用 `os.path.realpath`；
  **找不到会话即抛 `SessionMissing` 中止（fail loud）**，不静默当"没触发"；
  `reply` **只从 `session.jsonl` 逐字取完整 assistant 文本**，`raw_stdout/raw_stderr` 另存旁路字段、**不顶替** `reply`。

### 教训 3 ★ 判据取「会话里的工具调用」，不取「助手回复的文本」

- **现象**：若用回复正则判"有没有加载 skill"，措辞一换就误判。
- **依据**：L0 全程以 `session.jsonl` 里 **`skill` 工具调用**为 `skill_loaded` 判据（`skills_loaded` /
  `skill_tool_calls` 字段），回复只作正文。
- **对 L1–L7 的动作（已做）**：`judge.py` / `run_round.py` 沿用同一判据；断言集只读会话产物。

### 教训 4 ★ 停滞判据：两轮落在噪声带内就停，不许继续烧会话

- **现象**：v1.2.8 = F1 0.954 / 82.6；v1.2.9 = F1 0.950 / 83.5。**F1 只差 0.004**，flaky 5↔8。
- **依据**：README 第二节自述——83.5 比 82.6 高的 0.9 分**来自 Script Quality 8→10 的口径校正，
  不是行为改进**；属同一水平的**会话级抽样噪声**。⇒ 按停滞规则**停**。
- **对 L1–L7 的动作**：**不设"必须改满 N 轮"**。每轮先看**差值是否落在噪声带内**；
  在噪声带内就停手去查**量具**（教训 1）或**判据**（教训 3），而不是继续改正文。

### 教训 5 ★ 留出卷（B 卷）是"没过拟合"的唯一证据

- **依据**：A 卷 F1 0.950、B 卷 F1 **1.000**；安全标签 3 轮 FP 0、组合标签 3 轮 FP 0。
  README 自述：A 卷剩余误触发集中在少数**语义真边界**题（要破坏的对象恰是 L0 本身、飞书表要出图、闸门修复），
  **不是普遍性路由缺陷** —— 这正是「没对 A 卷过拟合」的判据。
- **对 L1–L7 的动作（已做）**：B 卷**封印留出**、10 条、交付前才开卷；
  `kb-check` 原本**没有**封印 B 卷（只做过一次 53 条重跑且调用门槛没过）⇒ 本次**新出了 B 卷**。

### 教训 6 ★ 先例优先 + 同粒度修复：同一坑第二次出现时，照第一次的粒度改

- **现象**：`build-final-report.py` 自检把 `<td>` 里的子串 **`nan`** 当非法数据 ——
  而用例 67 的提示词含 `tenant_access_token`（**te·nan·t**）。
- **依据**：源版**已经踩过同一个坑**，留有 `_harness/test-cases.before-nanfix.html`；
  当时修法是把该单元格里的 `app_secret` / `tenant_access_token` **包成 `<code>`（仅呈现层，+26 字符）**。
- **我的失误（照实记）**：首遍我做成了**全文档批量包裹（+988 字符）**，**已回退重做**成同粒度（+26 字符），
  **AI 回复正文与提示词文字一字未动**。
- **对 L1–L7 的动作**：改产物前**先查有没有先例**；有就**照先例的粒度**改，不许顺手扩大。
  另：**凡"改产物让闸门过"的动作，必须报出改动字符数**，否则分不清"修 bug"和"改数据迎合闸门"。

### 教训 7 ★ 保真度缺口要写进报告，不许掩盖

- **依据**：盲测会话自述（逐字）——沙箱**只读**且**提权无审批通道**，
  官方脚本 `align_l0_feishu.py` 因要写快照/报告而**跑不起来**（`PermissionError`），
  被测模型改走**只读等价路径**（`lark-cli base +record-list` 流式拉取 + 内存比对）。
- **含义**：**写档阶段在盲测里跑不动**。触发判定不受影响（路由看 description 与加载证据），
  但它影响「回复里有多少数字是现场跑出来的」。
- **对 L1–L7 的动作（已做）**：L1–L7 的 7 件里，`kb-media-extractor` / `kb-ingest-extractor` 等
  **写档阶段同样会在盲测里受限** ⇒ 断言集**只判"该不该加载 + 有没有走对档位"**，
  不对"文件真的写成功了吗"下断言（**那是保真度缺口，不是 skill 缺陷**）。

### 教训 8 ★ 跑批用受管后台作业，不用 `nohup`

- **现象（L0）**：首轮用 `nohup` 起的 runner **随 turn 结束被终止**（轮次文件 mtime 停在 08:10–08:13）
  ⇒ 改用**受管后台任务**（单 job 内含 6 分片）。
- **现象（今天，重演）**：DSH 崩了一次，**后台作业随之消失**（`job_list` 空），
  断点只剩 6 个**空日志** + 159 个**空骨架目录、0 个文件** ⇒ 等于白跑，**没有可用进度可续**。
- **对 L1–L7 的动作**：① 跑批一律走受管后台作业；② **进度必须每完成一条就落盘**（jsonl 追加），
  否则崩了就没有断点；③ 崩后先分清「空骨架」与「真进度」，**空骨架要归档再清**（本次已归档到
  `_archive-崩前残渣-20261004/`）。

## 三、这些教训在 L1–L7 上的落地映射

| 教训 | 在 L1–L7 上落到哪里 |
|---|---|
| 1 量具先于被测物 | 通用 harness 统一 `--timeout 600`；基线先跑、看中位数 |
| 2 接线先于优化 | `realpath` + `SessionMissing` fail-loud + `reply` 只取 `session.jsonl` |
| 3 判据取工具调用 | `judge.py` 只认 `skill` 工具调用，不认回复正则 |
| 4 停滞判据 | 差值落噪声带即停，转去查量具/判据 |
| 5 留出卷 | B 卷封印；补出 `kb-check` 缺失的 B 卷 |
| 6 先例优先/同粒度 | 改产物报字符数；先查先例 |
| 7 保真度缺口进报告 | 断言集只判"该不该加载 + 档位对不对" |
| 8 受管后台作业 | 每完成一条即追加 jsonl；崩后先归档残渣 |

**另外三条已固化进工具的教训**（来自本次 L1–L7 工作台，非 L0）：

1. **`force_writable` 不许抹执行位**：曾把 `scripts/` 的 +x 一并抹掉 ⇒ 改为**保留原执行位、只加 owner 读写**，
   并**逐文件镜像源权限**——`kb-recall` 的 `convert_pdf_to_images.py` 在源里本就**不可执行**，副本照实，
   **没有擅自替它加 +x**（那属另行申报的优化项）。
2. **归档目录是证据，不许写入**：我曾误让 `output_assertions.py --run-dir …/_run-v130-120s` **写进归档**，
   靠「数字对不上」（Output 12.6→8.2）才发现 ⇒ 重建后 sha 与 `b1c552b487a77edb` 一致才恢复；
   现已加**护栏：拒绝写入 `_run-*` / `_archive*`**。
3. **tag 撞名会覆盖别人的评测线 profile**：`--tag recallfix` 覆盖了 L0 线既有的 `eval-recallfix`
   ⇒ 恢复原 `cordis.patch.yml`、自己的改名 `recallfix-l1l7`，并加**护栏：目标 profile 已存在且未 `--force` 就拒跑**。

## 五、对 L1–L7 优化顺序的结论

1. **先量具、后正文**：L1–L7 的任何一件，**先跑基线并看中位数**；中位数逼近限时 ⇒ 提升时，
   **不许**拿那次分数去判 skill 好坏。
2. **先判据、后结论**：崩溃/空回复/会话缺失**必须 fail loud**；「查不到会话」不许当成「不触发」。
3. **先静态封顶、后盲测**：七件里有 3 件（media / clause / ingest）**已由轨道 A 的 error 级缺陷
   确定性地封顶 ≤79**（正文超长 / references 与 scripts 全缺 / `compatibility` 字段非法）
   ⇒ 这三件**不必等盲测就知道基线不可能达标**，修复顺序应是**先解封顶、再谈其他**（已完成：三件 fix 均过校验）。
4. **一件一件来**：同一条评测线**同一时间只跑一件**（用户 2026-10-04 口径），
   跑完达标再进下一件 —— 既是降载，也让崩溃只损失一件、不损失一批。
