## 2. 为什么「重跑」等于没跑

```
$ kb/kbpy .work/l4_article.py 20260930-1600        # 干跑，零落盘
  候选规则 509 条（文件 1018 行）
  台账里已发出的条款号：509 个

只读模拟（照搬分配逻辑，不落盘）：
  ★ 若现在跑 --apply：新发号 0 条（沿用 509 条）
  ★ 新发号与 canonical 已定稿号冲突：0 个
  行里 article_no 非空：509/509     ← 回填是好的（13:11 那次没抹掉号）
  --apply 会追加的行数：0
```

`l4_article.py:157` 的判据是 `if rid in prev_assigned: 沿用，绝不重发`。
509 条全在册 → 全部沿用 → **不产生任何新号、不追加任何行**。

而且它**根本读不到那 733 条**：`l4_article.py:127` 只读 `CAND = kb/l3/candidates/rules.jsonl`，
`sample_cases.jsonl` / `scoped_clauses.jsonl` **一个都不读**。
→ 它**没有能力**重建那 1242 条。

`kb/l7/registry/layers.yaml` → L4 `engine` 只登记了：

  `S-1=sample_case·正负样本`、`E-1=scoped_clause`。

  两个 L4 检查器按**不同口径**算，各自只覆盖一半现实。

## 4. 「闸门过」≠「没事」：两个 L4 检查器，一个过一个是红的

```
$ kb/kbpy l7/scripts/l4_gate.py          →  ✅ 过（C1–C6 全过）｜定稿 1242 ｜退出码 0
$ kb/kbpy .work/l4_integrity.py          →  ❌ FAIL（退出码 1）
```

`l4_integrity.py` 红了 3 项，逐项判真伪：

| 项 | 判定 | 说明 |
|---|---|---|
| `l3_append_only` FAIL | ✅ **真红** | 前 1018 行哈希 `aa83d1f9…` ≠ L6 存档 `d9a28e25…` → L3 候选件被**原地重写**过（2026-09-30 13:11，无 run 记录；同 15:51 阻断单 §6） |
| `article_numbers` FAIL | ✅ **真红** | 判据 `len(latest)==509`（写死），现在候选件里冒出 `external_standard.jsonl` 的 123 条 → 632 条，超出该脚本设计口径 |
| `reproducible`「重跑追加 509 行」 | ❌ **假红** | `l4_integrity.py:162` 调子进程**不带 `--apply`** → 脚本干跑 exit 0 不写；检查器随后读到的仍是**陈旧** `inputs.appended_this_run=509`，把「陈旧值」报成「本轮追加」。`files_changed 无` 正说明实际零写入 |

→ **闸门绿而台账缺 733 个号**，因为 `l4_gate.py` 只复算 canonical×候选×L2，**从不读台账**。
`l4_integrity.py` 确实有「附加 A) 台账覆盖」，但它被写死成单形态口径，**看不到 1242**。

## 5. 如果照原样「重建」，会打坏什么

```
kb/.work/publish.log（已发布，守衡侧可查）
  [publish 09-30 16:04:21] 发布后指纹：
    1_外部标准库:…:375 | 2_内部正负样本库:…:358 | 3_措辞表达库:…:509 | 4_产品描述库:…:105
  [l4] manifest 已更新：collections 4 个，docs 1347 条
```
`E-1`(375) / `S-1`+`W-3`(358) / `W-1`+`W-2`(509) **就是这批已发布文档的 id 来源**。
重发号 = 已流出库外的条款号**改指到别的规则**（`W-2.137` 变成另一条），
且违背 `layers.yaml:279`「条款号一经发出永久占用、不复用」。
