## 1. 字段设计（12 列，已建）

| 列 | 类型 | 取值 | 为什么要有它 |
|---|---|---|---|
| **素材** | 文本（主字段） | — | 哪条内容。★ 原默认列名「文本」已改名（Bitable 主字段**不能删只能改名**） |
| **事件ID** | 文本 | `RF-YYYYMMDD-NNNN` | 唯一键，回指台账那一行 |
| **机器结论** | 单选 | PASS / REVIEW / BLOCK / NEEDS_INPUT | 系统说了什么 |
| **人判** | 单选 | 同上 | **人说了什么** —— 与上一列**并排**，差异一眼可见 |
| **差异类型** | 单选 | 漏放 / 误报 / 覆盖缺口 | **大白话**，省得人自己去比对两个状态 |
| **回流层** | 单选 | L3 规则权重 / L1-L2 正负样本 | 该往哪送 |
| **可否改库** | 单选 | ✅ 可改库 / ⛔ 只计数 | **红线的可视化** |
| **来源** | 单选 | 真实投放 / 历史打回 / 我构造 | 决定能不能改库 |
| **人判理由** | 文本 | — | 原样带过来，不改写 |
| **复核人** | 文本 | — | 追人（追不到 ⇒ 只计数） |
| **判定时间** | 日期 | — | — |
| **机器那一单** | 文本 | `run_id` | 回指评审记录 |

**三条设计意图（不是随手加的列）**：
1. **机器结论 与 人判 并排** ⇒ 「有多少问题」一眼看得出，不用翻两个地方。
2. **差异类型是白话**（漏放 = 机器放行而人拦下；误报 = 机器拦下而人放行；覆盖缺口 = 机器判不了而人判了）
   ⇒ 你不用先学会我们的黑话。
3. **可否改库把红线摆到台面上** —— 来源「我构造」或复核人不是真人 ⇒ ⛔ 只计数，**不进第二步（真写权重）**。

## 5. 实测踩到的 API 坑（记下来省得下次再试）

| 坑 | 正解 |
|---|---|
| 字段类型写 `single_select` | ⇒ 枚举是 **`select`** |
| options 包在 `property` 里 | ⇒ **不接受 `property`**，`options` 平铺 |
| `+record-create` | ⇒ **不存在**，用 `+record-batch-create`，`{"create_records":[{…}]}` |
| `update_records` 传数组 | ⇒ 是**对象映射** `{recordId:{字段:值}}` |
| `+record-list` 读不回 JSON | ⇒ 用 `+record-get --record-id` 读单条最稳 |
| 主字段想删掉默认的「文本」 | ⇒ Bitable 主字段**不能删，只能改名** |

⇒ 已把**字段映射 + 设计意图 + 这 6 个坑**写进 `kb/l7/registry/return-flow.yaml` 的
`feishu_projection:` 段（**真源在库里，不只在飞书**）。
