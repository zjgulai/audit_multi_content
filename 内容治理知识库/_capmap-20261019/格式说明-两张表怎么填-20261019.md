## 1. 表①「能力图谱」——13 个字段怎么填

字段顺序在 API 返回里不稳定（`+field-list` 与 `+table-get` 给的顺序不同），**别按顺序认字段**。

### 1.1 逐字段

| 字段 | 类型 | 必填 | 填什么（以样本为准） | 长度基准 |
|---|---|---|---|---|
| **能力ID** | 文本 | ✅ 主字段、唯一 | 语义稳定主键，形如 `BOT-QUERY-04` | ≤30 |
| **L1底座** | 单选 | ✅ | 7 个里选 1：数据通道 / 分析判定 / 交互编排 / 知识治理 / 推送投放 / 运营交付 / 底座 | 恒 1 值 |
| **L2入口** | 文本 | ✅ | 用户从哪进来。三段式：`<主体> · <页面/场景> · <动作>` | 均 31，最长 78 |
| **L3业务问题** | 文本 | ✅ | **业务自己的口吻**问一句话（「我/我们」视角），**以「？」结尾** | 均 27，最长 52 |
| **使用方法** | 文本 | ✅ | 怎么触发 → 发生什么 → 结果落在哪。给标识符，不给形容词 | 均 185，最长 538 |
| **案例** | 文本 | ✅ | 一个具体场景；构造件以「示例：」开头、**必须以「…示例，未实际验证」收尾** | 均 130，最长 388 |
| **案例类型** | 单选 | ✅ | **只有两个值**：`实测` / `构造` | — |
| **案例证据** | 文本 | ✅ | 实测=可回源的路径/时间戳；**构造=一个字面量「无」** | 均 145 |
| **代码引用** | 文本 | ✅ | `文件:行号` 多条，**半角 `;` 分隔**（149/174 用半角，10 条用全角「；」——不统一，但半角是主流） | 均 126，最长 285 |
| **边界限制** | 文本 | ✅ | **只写限制不写卖点**；多条用 ①②③ 编号；每条尽量带 `:行号`（139/174 带） | 均 272，最长 624 |
| **状态** | 单选 | ✅ | 6 值梯子（见 1.2） | — |
| **关键项** | 勾选 | 否 | 只有 **3 行**为 true，且都是「对外公告/早报」这类主链路卡 | 171 行 false |
| **as_of** | 文本 | ✅ | `YYYY-MM-DD`，**逐行记实测日**（不是整表一个日期：170 行 10-18、4 行 10-19） | — |

### 1.2 状态 6 值梯子（照样本分布理解语义）

| 值 | n | 语义（从样本反推） |
|---|---|---|
| `live` | 125 | 代码在、生产在跑、有真实使用 |
| `limited` | 27 | 能用但有硬限制（限定群/限定范围/需人工） |
| `degraded` | 7 | 在跑但已知坏了一部分（如检索被 5000 文件上限截断） |
| `broken` | 1 | 有入口但结果不对（`BOT-QUERY-GENERAL-20`：回「暂时没查到」其实没去查） |
| `gap` | 7 | 该有但没有/只有半条 |
| `not_built` | 7 | 完全没建 |

### 1.3 五条硬惯例（照做，否则一眼就看出不是同一套口径）

1. **`案例类型=构造` ⇒ `案例证据` 必须是字面量「无」**（49/49 成立），且「案例」里必须有「未实际验证」四个字。
   **`案例类型=实测` ⇒ `案例证据` 不许是「无」**（125/125 成立）。
   ⇒ 这一条是这个表最硬的自证机制：**不许拿构造当实测，也不许实测了却不给证据**。
2. **`L3业务问题` 是业务的话，不是技术描述**。样本：「把上次查询的完整清单导出成文件给我。」
   反面写法：「导出功能是否存在」。172/174 以「？」结尾。
3. **`边界限制` 写的是「什么做不到」**，逐条带行号。样本里 10 条带 ①②③ 编号，其余用「；」串。
   **还允许「核验补注」**：② 表里有 4 条带「｜核验补注：…」，记录第二轮复核纠正的错（如行号指错、事实表述错）。
   ⇒ **这套表是会自我纠错的，纠错留痕就在这一格。**
4. **`代码引用` 要指到行号**，不许只给目录；同一能力跨多个文件就多条。
5. **ID 命名**：`<命名空间>-<域>-<序号或slug>`。现有 5 个命名空间：
   `BOT-`（飞书机器人，76 处提 Emily）｜`WB-`（Web 工作台）｜`SYS-`（系统底座）｜`OPS-`（运营）｜`GAP-`（缺口）。

## 2. 表②「底座健康」——7 个字段怎么填

| 字段 | 类型 | 现状 | 说明 |
|---|---|---|---|
| **组件** | 文本（主字段） | 13 行 | 一条外部依赖/组件一行，带括注说明用途 |
| **当前状态** | 单选 | 正常 9 / 降级 4 / 故障 0 | 只有 3 值：正常 / 降级 / 故障 |
| **额度或余量** | 文本 | **13/13 全空** | ⚠️ 见下「两处口径漂移」 |
| **失效影响** | 文本 | 13 行 | ⚠️ 实际填的**不是影响而是业务问题**，与 L3业务问题同款写法 |
| **代码引用** | 文本 | 13 行 | `文件:行号`，多条用半角 `;` |
| **最近实测** | 文本 | 13 行全是 `2026-10-18` | 日期字符串 |
| **已知风险** | 文本 | 13 行 | 最长一格，写法=多条风险 + `｜核验补注：…` 纠错留痕 |

### ⚠️ 两处口径漂移（照现状填会照搬这两个缺陷，先说清）

1. **「失效影响」这一格填的是业务问题，不是影响。**
   例：`AnySearch` 那行填「要补全一个达人/编辑的 X 或 LinkedIn 背景，能不能搜到？」——
   这是「这个组件回答什么问题」，不是「它挂了会怎样」。
   ⇒ **这是不是有意的，我判不了**（无从查证当时的填写说明）。但它让「能力图谱 ①」与「底座健康 ②」的
   同一业务问题在两个表里重复出现，而真正的「挂了会怎样」反而没地方写。
2. **「额度或余量」13 行全空**。这一格的用途本是记配额余量（Exa 5000 次/月、Apify 每账号 $199…），
   结果一条没填 —— 配额信息全被塞进「已知风险」里了。

⇒ 替换 ① 表后，这里的 `能力ID` 引用会全部指向旧 ID（现在没有行，所以暂时不会悬空）。

## 6. 替换的六条纪律（我做的时候按这个来）

1. **先备份再动**：174 + 13 行已导出到 `_capmap-20261019/t1.ndjson` / `t2.ndjson`（可原样回灌）。
2. **不硬凑行数**：Emily 174 行来自一份显式规格（`SPEC_PR_AGENT_ABILITY_MAP`）；
   守衡侧没有对应规格，**能核出多少写多少**，凑到 174 就是造假。
3. **案例类型不许灌水**：没实跑的写 `构造` + 证据「无」+「未实际验证」。
4. **代码引用必须指到行号**，且指的行要真是那段实现（Emily 版就有 2 处「核验补注」承认行号指错——别重犯）。
5. **④ 表补 v2.0 行**，写清「数据源从 Emily/工作台 换成 守衡 本体」，并给依据（守衡 `tools/agent/*`、本次探查记录）。
6. **③ 表**：若要启用发版核对，得先定「验收ID」从哪来（PRD §15 的 9 项是现成候选）。
