## 三、为什么「改成跟文件一致」是错的：生成器源码是这么写的

`kb/.work/l4_article.py:180-183`（读文件在写之前）：

```python
raw_before = open(CAND, "rb").read()          # ← 追加【之前】读的
_base_lines = 1018                            # 硬编码：本批开始前的行数
prefix_bytes = b"".join(l + b"\n" for l in raw_before.split(b"\n")[:_base_lines])
old_sha = hashlib.sha256(prefix_bytes).hexdigest()
inputs = {... "base_lines": _base_lines, "base_bytes": len(prefix_bytes),
          "base_sha256": old_sha, "lines_after": ..., "appended_this_run": ...}
```

`base_*` 的定义是**「本批开始前的输入基线」**。把它改成「本批结束后的整文件哈希」，等于：

1. **`inputs` 块自相矛盾**：`base_lines(1018) + appended_this_run(509) = 1527` ≠ `lines_after(1018)`。
2. **同一个 509 行块既算基线、又算本次追加**（同一个区间被两份口径重叠认领）。
3. **台账不再见证那次写入**：`reproduce.expect` 白纸黑字写着「重跑时 `kb/l3/candidates/rules.jsonl` 逐字节不变」，而该文件 15:52:08 被追加了 509 行。把 base 改成现文件哈希后，注册表读起来像「本批开始时文件就是 1018 行 / 2778734 字节」——**那次追加的痕迹在台账层面被抹平了**。
4. `prefix_unchanged: false` **与实测相反**（现文件前缀逐字节未变 → 应为 `true`）；成因同样是 `_base_lines` 那个陈旧常量（文件当时只有 509 行，取「前 1018 行」= 整个文件 + 末尾空块补的一个换行）。

`CHANGE.md` 自述的理由「`base_lines` = 1018 = 全文件，故前缀哈希即整文件哈希」**不成立**：`base_lines` 不是「全文件行数」，是硬编码的「本批前行数」。

### 真值应该是（口径 A，仅建议，未写入）

`inputs` → `base_lines 509 / base_bytes 1387672 / base_sha256 54691908… / lines_after 1018 / appended_this_run 509 / prefix_unchanged true`。
改完它与现文件**依然不一致，而这是正确的** —— base 本来就是改前基线。
