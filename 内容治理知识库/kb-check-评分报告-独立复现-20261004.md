## 6. 前提质疑：我不认同「直接把 77 分当定论」这个走法

### 6.1 ⚠️ 这条硬阻断，与 skill 自己写的策略**正面冲突** —— 这是需要你裁的设计取舍，不是 bug

kb-check 自己的 description 写着（`SKILL.md:109-113` 对应的 description 段）：

> **先追问、不要加载本 skill**：… ② **只打 skill 名** ③ … **以上先问清别加载。**

而评测框架要求的是（`trigger-eval-cases.md:72`）：

> 打了斜杠但没给材料 → **应加载 {name}**，然后追问

**case 53 的题面 `"/kb-check"` 正是「只打 skill 名」—— skill 完全按自己写的规矩执行，因此被判未过。**

我的判断（**标明：这是判断，不是结论**）：

- 框架这一条有其道理：斜杠是用户的**显式调用**，拒载等于无视显式指令；
- 但 kb-check 的顾虑也**不是空穴来风**：它的体检档里 **门④ `workflow_check.py` 没有干跑档、会写 `kb/l8/`**，
  而 §1 要求 `cd "<本次库根>"` —— **在不知道是哪座库之前先跑，是有写错库的风险的**。
  （不过「加载」≠「执行」，这条辩护只成立一半。）

**⇒ 需要你裁：是改 skill 顺框架（在 description 里补一句「只打 `/kb-check` 也应先加载再追问」），
还是由团队显式记录该门槛对本 skill 的豁免口径。两者都是合法解，但必须**二选一并留痕**，
不能让现状悬着 —— 现状就是「按 skill 写的做，然后被框架判死」。**

### 6.2 ⚠️ 我用独立探针复现这条，**方向相反** —— 门槛结论不稳

我起了 **3 个独立会话**（干净上下文，只发原文 `/kb-check`）做无污染探针，随后中断。

**结果与 6.1 的框架判定相反**：探针 **3** 在收尾信息里说
「Gate ⑥ red is already registered in the failure playbook. Let me collect the remaining two background gates.」
—— 它**已经在跑第 ⑥ 道闸门**了。而「Gate ⑥」是 SKILL.md §1 的**正文知识**，description 里没有
⇒ **该会话实际已经加载并执行了 kb-check**。

同期落盘也对得上：`.work/.kbchkx-run` 内容为 `RUN=CHK-20261004-1307-KBCHKX`（13:07），
`_chk-run-CHK-20261004-1310/gate*.out`（13:07–13:10）。

**但这不能当强证据，我必须说清三个限制**：

1. 探针**被我在完成前中断**了，是**不完整**证据；
2. 探针是 **DSH subagent**，与评测 harness 的会话**形态不同**（前者的系统提示明写「用户点名 skill 就先加载」）；

**⇒ 结论**：**「调用门槛未过」这条硬阻断，在我的环境里没复现，反而出现了反向行为。**
它可能真实、也可能依赖 harness 形态。**建议在据此下最终上线结论前，独立重跑这 3 条调用用例。**
