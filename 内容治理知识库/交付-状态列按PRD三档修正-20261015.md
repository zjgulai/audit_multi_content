# 交付 · 「状态」列按 PRD 三档修正（2026-10-15）

> Owner 原话：「文档中，状态按照 prd：**待审 / 已修改 / 已发布**，现在填的错的。你修复下这个问题，
> 修复后落库，并把表格一起改下」

## 一、PRD 出处（逐字）

PRD §8.2：「多维表字段：内容 ID、产品线、渠道、内容类型、内容阶段（brief / final_content）、内容原文 /
**Agent 结论**、置信度、问题数量、问题分类汇总、报告链接 / 人工复核人、复核结论、sign-off 人、发布时间 /
**状态：待审 / 已修改 / 已发布**」
⇒ **三态（PASS/REVIEW/BLOCK）是 `Agent 结论` 的值域，不是「状态」的**。

## 二、实测病灶

| 表 | 状态列实际值 | 行数 |
|---|---|---|
| 采集表 `tblavfbMDMeRsulo` | BLOCK 12 / REVIEW 67 / PASS 1 | **80/80 全错** |
| 结论表 `tblCXPQVzfFWWCon` | REVIEW 361 / BLOCK 32 / PASS 48 / 待审 16 | **441/457 错** |

那一列的下拉里同时挂着 **6 个选项**（待审/PASS/REVIEW/BLOCK/已修改/已发布）；`已修改／已发布` 两档几乎没用过。
后果：读表的人分不清「这单判成 BLOCK」与「这单还没人处理」。

## 三、根因（两层，第二层比第一层更值得记）

1. `review_publish.statusOf(conclusion)` 按结论返回三态，而 `rowFieldsOf` 结尾**无条件** `f['状态'] = statusOf(conclusion)`。
2. **测试把错的行为断言住了**：`review_publish.test.mjs` 里 `eq(rp.statusOf('BLOCK'), 'BLOCK')` ——
   判据本身在保护缺陷，**改实现反而先红**。这是「判据形状错了比没有判据更坏」的又一例。
3. 第二条写入路径：批跑器 `RESULT_FIELDS` 含 `状态`，把结论表那一格原样搬进采集表
   ⇒ 人设的终态（已修改／已发布）也会被机器覆盖（这条边界 2026-10-08 就记着「等 Owner 一句话」）。

## 四、修了什么（四层）

| 层 | 改动 |
|---|---|
| 代码 | `statusOf()` **只返回「待审」**（PRD 三档里机器只拥有这一档）；三态继续只进 `Agent 结论` |
| 代码 | 新增 `HUMAN_TERMINAL_STATUS = ['已修改','已发布']` ＋ 补丁闸：库里是终态 ⇒ 机器**不写、也不改回** |
| 代码 | 批跑器 `dropHumanTerminalStatus()` 同口径；源行给的不是 PRD 三档 ⇒ 不搬**并出声**（`SKIPPED_FIELDS`） |
| 测试 | 旧断言改成 PRD 口径；新增「三态不许进这一格」＋「人设终态受保护」两条，**各带反向对照** |
| 数据 | 采集表 80/80、结论表 441 行 → 「待审」（`Agent 结论` 一格未动：仍是 12/67/1 与 361/32/15/48） |
| 结构闸 | 两表 `状态` 的 select 选项收敛为 `待审/已修改/已发布` ⇒ 以后写三态会**直接失败**，不再悄悄污染 |
