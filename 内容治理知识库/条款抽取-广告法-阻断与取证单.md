## 三、★ 查阻断时查出的真缺陷：3,389 个条款单元被整批丢掉

这一节请你优先看，**它比「广告法原文没给」更要紧**。

### 3.1 事实

库里**已经有**条款级单元，不是没有：

```
kb/l2/units.jsonl  unit_type=clause  共 3,871 个，分布在 133 个外部标准资源上
```

来源含 FTC《Health Products Compliance Guidance》（995 个）、
Google Ads 政策（289 + 281 个）、Amazon 广告帮助（33 + 32 + 24 + 23 + 19 个）、飞书 wiki（521 + 504 + 396 个）等。

L2 的切分器把「一个法条」写成了正式口径（`kb/l2/registry/l2.json → splitters.clause`）：

> **minimal_unit**: 一个法条 ｜ **status**: `ready_and_run`
> **how**: 章/节/条；正则识别 `第X条(之Y)` / `§X.X` / `Art. N` / `Article N` / `Section N` / `N.N.N`…

**但 L3 蒸馏器无条件拒绝全部条款单元**。`kb/l8/l3_distill_run.py` 第 337–356 行：

```python
cl = grp.get("clause", [])
if not cl:
    CONS["no_clause_text"] += 1
    rejected.append({"kind": "no_clause_text", ... "未产出可用条款文本（正文为页面脚本或编码载荷）…"})
    continue
for u in cl:
    CONS["clause_not_actionable"] += 1
    rejected.append({"kind": "clause_not_actionable", ... "条款文本不可判定：非自然语言条款（页面脚本 / base64 编码载荷），无法给出判定条件与阈值"})
```

**两个致命点**：

1. **`for u in cl:` 循环体里没有任何判定，直接落 `rejected`** —— 无论条款写得多清楚，一律判「不可判定」。
   这不是「判过了不合格」，是「**根本没判**」。
2. **`if not cl:` 分支的文案是错的** —— 它说「未产出可用条款文本」，
   但 `cl` 为空恰恰意味着**正文抓到了、只是没切出条款形态**。文案把「没切出来」写成了「没有正文」。

### 3.2 反证：这些条款**是可判定的**

`clause_not_actionable` 的理由是「非自然语言条款（页面脚本 / base64）」。以下是同一批单元里的真实文本：

| 资源 | unit_id | 逐字正文 |
|---|---|---|
| FTC Health Products Compliance Guidance | `10667b66717542295c22` | `If elements of an ad imply that the product also provides a disease benefit, the advertiser must be able to substantiate the implied disease claim even if the ad contains no express reference to a disease.` |
| FTC 同上 | `f93dab667943255fc526` | `Under Section 15 of the FTC Act, an ad is misleading if it fails to disclose information that is material in light of the claims in the ad or with respect to how consumers would customarily use the product.` |
| FTC 同上 | `5b16d7cd658068a5f6f4` | `[21] Thus, if the ad would be misleading without certain key qualifying information, that information must be disclosed.` |

这三条**已经是可直接落表的东西**：判定条件 =
「宣称隐含疾病功效」（即 `if elements of an ad imply … a disease benefit`），
处理方式 = SUBSTANTIATE / DISCLOSE，
条款锚点 = `#l.1-506`，且 `unit_id + source_sha256 + anchor` 三件套齐备。
**它们不是脚本，不是 base64。** 判「不可判定」与文本事实不符。

量化：全库 844 个 clause 单元含 `must / must not / may not / shall / prohibit / 禁止 / 不得 / 应当` 这类义务或禁止模态。

### 3.3 台账登记了，但**登记理由与代码实际行为不符**（这一条我改过一次，以现文为准）

先纠正本单早先一处**推断错误**（原写「3,869 个连账都没记」，**错了**，已删）：
拒绝台账**确实**登记了 clause 单元，只是换了 `kind`。实测如下。

台账里 `unit_type == "clause"` 的行共 **1,830** 行，带 `unit_id`：

| `kind` | 行数 | 理由（逐字） |
|---|---|---|
| `unit_level` | **1,748** | `条款不可判定或已被同库其它条款覆盖，未产出「判定条件 + 阈值/词表」形态` |
| `no_rule_derivable` | 82 | `不构成可判定的「命中→替换」或「修订前→后」对` |

而 clause 单元总数是 **3,871**（3,389 个 `kb_type=external_standard` + 482 个其他）。故：

| | 数 |
|---|---|
| clause 单元总数 | 3,871 |
| 台账里以 `unit_level` / `no_rule_derivable` 登记的 clause 单元 | 1,830 |
| **未被任何一行登记、也未成规则的 clause 单元** | **约 2,041** |
| 其中以 `clause_not_actionable` 登记的（代码里写死的那条 kind） | **2** |

> 口径提示：`l8/l3_reject_ledger_rebuild.py` 会把单元级拒绝按 `reason_of(u)` 归一成
> `kind: "unit_level"`（第 106 行），所以代码里写的 `clause_not_actionable` / `no_clause_text`
> **不是**台账里最终看到的 kind。查台账时必须按 `unit_type` + `reason` 查，**按 kind 查会查错**——
> 本单第一版就是这么查错的。

**真正的问题不在「有没有记账」，在「记的理由是假的」**：

那 1,748 行的理由是「条款不可判定**或**已被同库其它条款覆盖」。可是按第 3.1 节读的代码，
`for u in cl:` 里**既没有判「可不可判定」，也没有做任何「是否被其它条款覆盖」的比对**——
它无条件落 `clause_not_actionable`。也就是说：

- 「不可判定」这个结论**没有任何判定过程支撑**；
- 「已被同库其它条款覆盖」这个条件**在代码里根本不存在**，是理由文案里凭空多出来的一个选项。

**理由与行为不符，比没记账更坏** —— 没记账看得出缺，记了假账则后面每个人都以为这批条款真的被判过了。

### 3.4 对供给链的实际影响

这正是「为什么 L4 定稿永远空着」的机理解释：
条款素材 → L2 切出 3,389 个可判定候选 → L3 **全数丢弃** → L4 发号 **0 条**（`canonical/rules.jsonl` 0 字节）。
**供给链断在 L3 的这 20 行代码上**，不在素材上。

### 3.5 修法（**我没有改**，等你定）

按库内既有纪律（2026-09-29 那批「补干跑档」的做法），建议在副本上改、留回归：

1. **区分「没切出来」与「切出来但不可判定」**：`if not cl:` 的文案改成「未切出条款形态（正文已抓到）」，不要写成「没有正文」。
2. **`for u in cl:` 里补真判定**：对每个 clause 单元判「是否含判定条件 + 阈值/词表/处理方式」；
   通过 → 产出 `form: "external_standard"` 的候选行（`kb_type: "external_standard"`、
   填 `article_no` / `effective_from` / `effective_to`）；不通过 → 落`rejected` 并给**逐单元的具体理由**，不许一句通用话覆盖。
3. **把拒绝理由改成拿得出依据的**：现台账 1,748 行的理由是「条款不可判定**或**已被同库其它条款覆盖」，
   但代码里两件事都没做。要么补上真判定（可判定 → 成规则；不可判定 → 逐单元给理由），
   要么把理由文案改回与代码一致的「未切出可用条款形态」，**不许留着这个够不着的「或」**。
   另需处理约 2,041 个 clause 单元无任何登记行的缺口（对账要 `unaccounted == 0`）。
4. **改完必跑**：`kb/kbpy l7/scripts/l3_gate.py`（判据 C1 会逐条核新增证据能否回指 L2）＋
   `kb/kbpy l7/scripts/l7_gate.py`；`kb/kbpy l8/l3_reject_ledger_rebuild.py <RUN> --apply` 重建台账。
5. **红线①照旧**：任何 `--apply` 前先把 `kb/l3/rejected.jsonl` 归档并校验 sha256（本库真发生过台账从 11,860 行掉到 1,053 行）。

## 四、顺带一条数据质量问题

169 个 clause 单元的正文里**还带着 HTML 标签**，例如：

```
All ads must clearly indicate that terms and conditions apply …</span> </li> <li> <span class="a-list-item">Advertisers must comply with all applicable local laws and regulations governing advertising to children.</span> </li
```

（`url__https____advertising.amazon.com_help_G4U9JBZH3664JWX2`，unit `499adc0f57242ad4c418`）

即 L1 抽正文时未剥标签，且**一个单元里被塞进了两个不同的要求**（「条款须显著」与「须遵守当地儿童广告法」）。
