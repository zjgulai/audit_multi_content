## 三、但这个改法不对：`base_*` 不是「文件的哈希」，是「本批开始前的输入基线」

生成器 `kb/.work/l4_article.py:180-183 / 248-252`：

```python
raw_before = open(CAND, "rb").read()
_base_lines = 1018                      # 硬编码：本批开始前的行数
prefix_bytes = b"".join(l + b"\n" for l in raw_before.split(b"\n")[:_base_lines])
old_sha = hashlib.sha256(prefix_bytes).hexdigest()
inputs = {... "base_lines": _base_lines, "base_bytes": len(prefix_bytes),
          "base_sha256": old_sha, "lines_after": ..., "appended_this_run": ..., "prefix_unchanged": ...}
```

`base` = **改前**的基线。把它改成**改后**的整文件哈希，等于：

1. **`inputs` 块自相矛盾**（改前也矛盾，成因是 `base_lines` 那个陈旧常量）：
   `base_lines(1018) + appended_this_run(509) = 1527`，而 `lines_after = 1018`。
2. **改后的 base 与追加块重叠**：同一个 509 行块既算「基线」又算「本次追加」。
3. **台账不再见证那次写入**：`reproduce.expect` 白纸黑字要求「重跑时 `kb/l3/candidates/rules.jsonl` 逐字节不变」，而该文件 15:52:08 被追加了 509 行。把 base 改成现文件哈希后，注册表读起来像「本批开始时文件就是 1018 行 / 2778734 字节」，那次追加的痕迹在台账层面被抹平。

### 真值是哪几个（实测，不是推测）

| 口径 | 行数 | 字节 | sha256 |
|---|---|---|---|
| **本批改前**（= L3 注册表 + 旧备份） | 509 | 1387672 | `54691908da8e8b59f4ca5e3affd6a565bc760b614258052cc0646a17c70cab1d` |
| 生成器实际写进 `base_*` 的（含 +1 字节伪影） | 1018 | 1387673 | `416fb828fdfc790deb722ef7d3dbf286613605fc38effcb77d69e51791176de9` |
| 现文件（改后写进 `base_*`） | 1018 | 2778734 | `aa83d1f98bc86857254bfa4f908ebd6d1a869f868cb04970522d154f776b0dac` |

- 旧值**不是**「不复现的值」（`CHANGE.md` 第一节的说法不准确）：`416fb828…` = **改前文件 + 一个换行** 的哈希，正是生成器对「以换行结尾的文件」做 `split` → 末尾空块也被补一个换行（1387672→1387673）算出来的。复现：
  `python3 -c "import hashlib;b=open('kb/l4/_pre-rebuild-20260930-1550/rules.candidates.jsonl.bak','rb').read();print(hashlib.sha256(b+b'\n').hexdigest())"`
  → 它就是**改前基线**，因此本来就不可能等于现文件。
- `prefix_unchanged: false` **与实测相反**：现文件前 1387672 字节与 `_pre-rebuild-…/rules.candidates.jsonl.bak` **逐字节相同** → 前缀其实未变（应为 true）。
