## 0. 先说结论：这不是"料不好"，是**我们自己 2026-10-08 的一次修复造的**

**`kb/l8/rechunk_l1_segments.py`（2026-10-08）** 解决的问题是真的：
13 份飞书链接类 L1 产物**整篇塞进 1 个 `#正文` 段**（最长 188,828 字）⇒ L2 出 1 个巨 clause 单元
⇒ 被 L6 的 `oversize_gt_8000` **整份挡在索引外** ⇒ 守衡检索不到那 1,754,363 字。

**它的修法**：按 `\n` 切行后重新分组到 `TARGET = 4000` 字符，锚点改成 `#l.<起始行>-<结束行>`。
**它对没有换行的长行，退化成纯字符切**：

```python
if len(line) > target:                      # 单行超长：先冲掉手上的，再切这一行
    n_split = (len(line) + target - 1) // target
    ... line[k*target:(k+1)*target] ...
```

而**抓取来的网页正文正是"少数几个超长行"** ⇒ **切出 [3800,4000] 的定长块、边界落在词中间**。

> ⇒ **修一个尺寸问题，造了一个内容问题。** 这批块在 L2 变成 `clause` 单元 → L3 变
> `scoped_clause` 候选 → **已发号 3155 个**（E-1.1…E-1.3155）。

## 3. 方案（三选一，我推荐 A）

### A ★推荐★ 重分块改为「按句子边界切，再按句聚合到 target」
- 做法：对超长行**先按句末标点切句**（`. ! ? 。！？` + 空白/引号），再把整句聚合到 ≤ `TARGET`；
  **任何情况下不许把句子切开**；单句本身超 `TARGET` 时才退回字符切**并在 anchor 上标记 `/hard`**。
- 代价：`kb/l8/rechunk_l1_segments.py` 要改；**L1 重分块 ⇒ L2 ⇒ L6 索引 ⇒ 评审链单元层召回会变**
  ⇒ **必须先建固定回归集**（见 §4）。号**不回收**：那 3155 个号里被替换掉的**永久留空**。
- 好处：**治本**，且新块天然满足 C9 的"两端在句子边界"。

### B 只加判据、不重切（现状）
- 已做：C9（挡 1774）＋ C10（挡 121）。**零风险、已在位。**
- 代价：**剩下 848 条仍然不是条款**（育儿书正文/参考文献）⇒ **外部标准库仍然零供给**；
  而且**下次日更还会切出新碎片**（L1 重分块是幂等的：`rechunk` 只碰 `#正文` 单段产物，
  已切过的不再进 ⇒ 存量不会再增，但**新的抓取资源会**）。

### C 把 `external_standard` 的 clause 切分器换成「正则识别条款边界」
- 依据：`kb/l2/registry/l2.json → splitters.clause.how` 已写明语义
  「**章/节/条；正则识别 第X条(之Y) / §X.X / Art. N / Article N / Section N / N.N.N**」。
- 代价：**命中率取决于源料有没有这些标记** —— 实测 2733 条里**只有 1.4% 含条号**
  ⇒ 对这批网页抓取料**几乎等于全丢**。**不推荐单独用**，但**可以作为 A 的第二道**。
