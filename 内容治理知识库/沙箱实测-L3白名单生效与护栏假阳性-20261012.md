## 4. ★★ 预先存在的缺陷：L3 写不出 `rules.jsonl`

沙箱① 与沙箱② **都**打出：

```
⛔ 拒写（闸③ 行数护栏）：kb/l3/candidates/rules.jsonl —— 行数骤减 1018 → 509（降 50%，护栏阈值 20%）
⛔ 拒写（闸③ 行数护栏）：kb/l3/rejected.jsonl      —— 行数骤减 4149 → 2188（降 47%）
```

### 4.1 护栏本身是好的，它是为一次真事故加的

`l3_distill_run.py:616-622` 逐字：

> ★ 第③道（**2026-10-02 实测加的，不是预防性设计**）：本脚本跑一次，`rejected.jsonl` 从 **10,661 行掉到 2,611 行**（少 8,050 行）——
> 与 2026-09-29 那次事故（11,860 → 1,053）是**同一个模式**。
> ⇒ 要真的接受骤减，须显式设 `KB_L3_ALLOW_DROP=1`（人开闸）。**这样"数据消失"从静默变成必须有人点头的事件。**

### 4.2 ★ 但它对 `rules.jsonl` 是**假阳性** —— 比的是两种不同序列化的**裸行数**

| 文件 | 现文件 | 引擎本次算出的 | 是真是假 |
|---|---|---|---|
| `rules.jsonl` | **1018 行 = 509 唯一 `rule_id` × 2** | 509 行 = 509 × 1 | **假阳性** |
| `rejected.jsonl` | **4149 行 = 4149 唯一 `unit_id`（无重复）** | 2188 行 | **真骤减，护栏正确** |

`rules.jsonl` 那 ×2 是 **L4 把条款号「追加」回候选件**留下的：
同一个 `rule_id` 两行，**只差一个字段** —— 一行 `article_no=''`、一行 `article_no='W-1.18'`
（实测 `r-37b49eadb72d7dc2` 的两行，键集合完全相同，唯一差异键就是 `article_no`）。

**⇒ 引擎写的是「一规则一行」，而盘上是「一规则两行」，护栏把序列化形状差读成了数据骤减。**

### 4.3 后果

- **`kb/l3/candidates/rules.jsonl` 从此写不进盘**（只要 L4 追加过条款号副本）。
- 它现在的 mtime 是 **10-12 11:29**、sha `92694e86bc2f4964…` —— 那是**本会话目标 6 的产物**，
  **不是 L3 写的**。⇒ L3 的候选规则自那以后没有真正刷新过。
- **`kb/l3/rejected.jsonl` 也一起被挡住**（且它是真骤减，本就不该无脑放行）。
- **为什么一直没被发现**：L3 的 run 记录（`kb/l3/runs/<RUN>-L3.json`）**只写 `run_id` / `skill` / `dry_run`，
  不记写入结果**。⇒ 「拒写」发生在 stdout，没进任何台账。

## 5. 我的推荐

### ★ 推荐 A：修护栏的**比较口径**（不是放松它）
把闸③ 从「比裸行数」改成**比语义条数** —— 对 `rules.jsonl` 比**唯一 `rule_id` 数**，
对 `rejected.jsonl` 比**唯一 `unit_id` 数**，其余文件沿用行数。
- **理由**：护栏要守的是「**数据消失**」，不是「行数变化」。现在它对 `rules.jsonl` **永远拦**、
  对 `rejected.jsonl` **拦得对** —— 一把尺子两种结果，根因是它比错了量。
  修完 `rules.jsonl` 才可能被 L3 刷新，10/19 #1 也才有下半场。
- **代价**：动的是**为真事故加的安全闸**，必须：① 反向对照（造一次真骤减 ⇒ 尺子必须精确变红）；
  ② 保留 `KB_L3_ALLOW_DROP` 人开闸；③ 修完要人看一眼「509 vs 509」确实是同一批规则
  （我已实测：`新 0 / unchanged 509`，逐条是同一批）。

### 推荐 B：把「写入结果」记进 L3 的 run 记录
- **理由**：这次是靠沙箱才发现的；`refused` 只打在 stdout ⇒ **静默**。
- **代价**：动 run 记录的字段（下游读者的契约要看一下）。

**不推荐 C**：直接 `KB_L3_ALLOW_DROP=1` 重跑 —— 那会把 `rejected.jsonl` 那 47% 真骤减也一起放行。
