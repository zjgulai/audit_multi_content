# 守衡「调用模型失败」—— 不是网络，是「给 12000 的预算只准花 120 秒」

- 日期：2026-10-26（事故 10:06–10:18 CST）
- 触发：Owner 贴出守衡回给刘华丽的一句
  「我这边调用模型失败了，没法回答这个问题。失败原因：超时 层失败（请求超时）：超时/20 · 1 跳 :: This operation was aborted」
- 结论：**结构性必超时**，不是偶发网络问题。已修，并落了两条判据 + 三条反向对照。

---

## 一、现象（盘上的读数，逐条可回读）

| 来源 | 读数 |
|---|---|
| `PMO/logs/ws_daemon.log` | `★ 收到消息 … 原文="你好"`（10:06:43）→ `💬 回复 102 字，耗时 683907ms`（10:18:07） |
| `PMO/logs/ws_daemon.log` | `↻ 模型失败（层=超时），可重试=true → 已入补发队列（1 条）` |
| `PMO/logs/llm_failures.jsonl` | `2026-10-26T02:14:47.230Z layer=超时 retryable=true n_attempts=4`，四条 attempt 全是 `请求超时: This operation was aborted`、`code:20` |
| `PMO/logs/ws_outbound.jsonl` | 10:18:07 那条外发正文就是上面那句（102 字） |

算术对得上：**4 次尝试 × 120 s + 退避 0.8/1.6/3.2 s ≈ 485 s**，而收到消息到失败落盘正好 **484 s**
⇒ 四次尝试**每一次都恰好撞满 120 秒上限**（不是上游回了错，也不是 DNS/连接失败）。

## 二、根因：两个常量从未一起算过

`llm.mjs::post()` 把单次请求写死 **120 s**（`timeoutMs = 120_000`），
而 `config.llm.maxTokens = 12000`。本机实测（端点 `~/.dsh/shouheng-llm.env` → cliproxy → `deepseek-v4.1-flash`）：

| 探针 | 读数 |
|---|---|
| 小请求（20 字内） | 200 / **1.0 s** |
| 真实会话上下文（1413 条、19.0 万 prompt token）只回 2 字 | 200 / **8.7 s** ⇒ **prefill 不是瓶颈** |
| 长回答（`max_tokens` 用到 3635） | 200 / 31.8 s（≈114 tok/s） |
| **满预算作答**（`max_tokens=12000`，reasoning 7998） | 200 / **155.9 s**（≈77 tok/s） |

⇒ **任何把预算用掉大半的回答，在 120 s 上限下都不可能成功**。
而四次重试**各自从头重新生成**，于是 683 秒全部白等，最后仍落在同一句失败话术上。

同批的两条旁证（同一窗口、同一份输入）：
- 排在后面的「你可以回答问题吗？」4 次调用都**刚好没撞满** 120 s ⇒ 答出来了（1780 字）——
  同一时刻、同一端点，差别只在「这一份回答用了多久」，与输入大小无关。
- 事故后（10:27）复测：同一份 19 万 token 上下文、生产默认参数，**16 s 答完**（`ok:true`）。

## 三、顺带查出的两个次级缺陷

1. **失败原因印的是 `超时/20`**：`20` 是 `DOMException` 的**数字** `code`（= `ABORT_ERR`），
   而 `LAYER_BY_CODE` 的键是字符串码 ⇒ 查不到 ⇒ `why` 原样印了个数字。
   代价：这是群消息里唯一一句给业务人看的排查线索，却印成人读不懂、也不在封闭集合里的东西。
2. **「谁掐的」没有区分**：`AbortError` 同时盖住「我方看门狗到点」与「上游/网关断流」，
   两者都印成「请求超时」⇒ 自己的超时预算太紧，读起来像网络不好（这次正是如此）。

## 四、修法（三处，都在 `tools/agent/`）

| 文件 | 改了什么 |
|---|---|
| `config.mjs` | 新增 `llm.timeoutMs`，默认 `max(120 s, 30 s + maxTokens × 20 ms)` = **270 s**（≈50 tok/s 地板 + 余量，比实测 77 tok/s 留 1.5 倍）；可由 `SHOUHENG_LLM_TIMEOUT_MS` 覆盖；**启动横幅与 `maxTokens` 并排打出来**（原先只有 maxTokens ⇒ 没人算得出 120 s < 156 s） |
| `llm.mjs` | ① `post()` 用 `config.llm.timeoutMs`，并在**真的因看门狗到点**被 abort 的那个错上打 `WATCHDOG` 标记；② 失败原因写明「我方 N 秒看门狗掐断（预算 max_tokens=…，不是网络问题）」；③ **超时类重试上限单独一档 = 2 次**（网络/限流类仍是 4 次）；④ `DOMException` 数字码归一（`20 → ABORT_ERR`、`23 → TIMEOUT_ERR`） |
| `llm_errors.test.mjs` | 新增 L8 / L8b / L9 / L9c / L9d / L11 / L11b 七条判据 + C6/C6b/C7/C7b/C8/C8b 六条反向对照（全部离线：L9 打本机一个**永不回话**的 http 服务器，1.1 s 收工，0 token） |

判据形状（为什么这么写）：
- **L9 用行为判，不读源码文本**：真的让请求超时一次，数 `attempts.length === 2`、看 `error` 里有没有「看门狗」。
  反向对照 C7 把「4 次」喂给同一把尺子 ⇒ **必须红**；C7b「2 次 + 写明看门狗」⇒ 必须绿。
- **L11 判两个常量的关系**：`timeoutMs ≥ max(120 s, maxTokens × 20 ms)`；
  反向对照 C8 直接喂事故当天的原值（120000 / 12000）⇒ **必须红**。
- **L8/C6 判串**：喂一个 `{name:'AbortError', code:20}` 的样本，摘要里必须是 `超时/ABORT_ERR`，
  且**不许**出现 `/20`。

## 六、没有做的事（边界，别外推）

1. **没有改成流式（streaming）**。那才是这一类问题的根治（把「总时长上限」换成「多久没吐字」），
   但要动 SSE 解析、`tool_calls` 增量拼装、`reasoning_content` 回传三处，属于换协议层，风险面大。
   建议下一步：先用 `test/_probe_relay.mjs` 那套探针验中转站支不支持流式，再单独一轮做。
2. **没有改 `maxTokens`**，也没有开 `SHOUHENG_REPLY_THINK=off`（实测关思考快 **5.9 倍**，
   但那是产出口径问题，得 Owner 定）。
3. **失败话术一个字没改**（除了失败原因本身现在能读懂了）。失败的仍会入补发队列；
   但「补发」会被「记忆里已有真回答」这一条跳过 —— 这次「你好」那条就是这样被跳过的，
   是否该跳**没判**，留作独立议题。
4. 本件不证明上游以后不会再慢一次；只证明「我方不会在自己的 120 秒上先把回答掐死」。
