## 一、规则（Owner 2026-10-14 原话）

> 「守衡的**所有**输出中不允许包含 `**` 星号，修复后落库。」

拆成三句可判的话：

| # | 规则 | 为什么 |
|---|---|---|
| R1 | **`msg_type: 'text'` 载荷里不许有一个 `*`** | 飞书按纯文本渲染 ⇒ `**` **字面**显示 |
| R2 | **卡片 payload 里不许有一个 `*`**（模板自己写的也算） | 同上：Owner 看到的那张回执卡上那句是**代码**写死的 |
| R3 | **卡片的纯文本视图**（降级兜底 + 台账正文）不许有 | 它只在出事那一跳才被看见，最难发现 |

**不在规则内的两处**（写清楚，免得后人「顺手统一」）：

* **`code_block` / 代码块内的 `*`** —— `**kwargs`、`select *` 是**内容**不是标记，摘它就是改内容；
* **不认识的新 tag** —— 宁可漏，不许改内容（白名单是「知道它在渲染什么」才摘）。

## 三、判据怎么跑（每个数都带复现命令）

```bash
node tools/test_agent.mjs                      # 出站与卡片的行为级断言
```

| 判据 | 在哪 | 守什么 |
|---|---|---|
| 正反例 | `test_agent.mjs` 第 3 组「plainify」 | `**` 三种写法都要摘干净 · **下划线不许动**（`user_id` 是标识符） |
| **行为级** | 同上「真发一次（网络打桩）」 | 把网络换掉，`replyMarkdown` 真跑一遍，**看它准备发什么** |

## 四、这次是怎么被发现的（事故读数，可复算）

Owner 在私聊里看到的是 `1. **能查的我查完再说** —— …`，星号**字面**显示。
对应台账 `PMO/logs/ws_outbound.jsonl` 的 `2026-10-14T05:04:32.785Z`（`mode: 'reply'`）。

**真因**：`replyMarkdown()`（「回复某条消息」，**最常走**的一条）把 markdown 原文直接塞进
`msg_type: 'text'`，一个字都不转；而 `sendMarkdown()` 那条路转富文本，本来就干净。
⇒ **最常走的路最脏，而它不报错、不降级、不留痕。**

**按形态分账**（`verify_outbound.py` H2 每次都会打这行读数）：

| 形态 | 修复前带星号 / 总数 | 会被人看见吗 |
|---|---|---|
| `reply` | 24 / 39 | **会** |
| `text` | 1 / 1 | **会** |
| `post` | 73 / 86 | 不会（转 bold 节点；台账存的是原文） |
| `reply-card` / `card` | 340 / 354 · 132 / 235 | 卡片正文走 markdown 渲染 |

★ **两种形态混在一起数会得出「492 条」** —— 一个既吓人又不准、且**指不出该修哪儿**的数。
所以判据按发送形态分账，而不是数总数。

## 六、为什么这道闸门只能靠纪律 + 一个检查器（写下来，别以为它已经是强制的）

`restart_shouheng.sh` 是**一个脚本**，不是**唯一的入口** —— 任何能跑 `launchctl kickstart`
的进程都能绕过它。**2026-10-14 实测绕过了一次**：现行进程 14:11:07 启动，
而 `PMO/logs/restart-ledger.jsonl` 最后一条是 04:53:16Z；上一个进程是**干净收尾**
（`launchctl kickstart -k` 式），`launchctl` 的 `runs` 87 ≠ 台账条数。

**代价不是形式上的**：没读「群里最后一条消息距今多久」⇒ **重启窗口吃掉的消息事后补不回来**，
而《内容治理数据采集》那条正事当时就挂在群里。

**执行点**：`tools/verify_shouheng_ops.py` 的 **E5** —— 它比的就是
「进程启动时刻 vs 台账最后一条」，过期或缺失就报红。**这次它真的红了**
（这正是它存在的意义：纪律靠人守不住时，至少有一个东西会说话）。
**它不是强制的**（§2.7 那条自认的边界：闸门是纪律 + 检查器，不是内核级拦截）。
