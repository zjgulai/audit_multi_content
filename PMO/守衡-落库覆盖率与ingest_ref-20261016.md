# 「落库」这把尺子量不到的那一类改动（2026-10-16）

> 留底件。入库条目：`ref-shouheng-ingest-coverage-blindspot-20261016`（`kb/view/3_措辞表达库/L1-facts/`）。
> 本件同时记当天另外两件与它连着的事：**批跑器是长驻进程、改完不重启等于没改**，
> 以及**同一个坏形状只在一条路径上出现**（这决定了「去哪儿验证」）。

## 〇、起因（Owner 原话）

> 「**你修复的内容落知识库了吗？**」

而我当天的回答只能是「**没有**」—— 我修完 FIX-037/038 只提交进了本仓（`f749cfd`），
**没入库**。与此同时，那条规矩自己的读数 `python3 tools/verify_ingest_coverage.py` **全绿**：

```
入库 7 条｜被拒 3 行｜动过的留底件 7 个
  ✅ 守衡-图片与视频读数-20261016.md …
  ✅ 守衡-送审问题与媒材链接-20261016.md …
```

⇒ **读数绿 ≠ 活儿落了。** 它量的两样东西里，根本没有我这次的产物。

## 一、根因：那把尺子的口径漏了一整类

`verify_ingest_coverage.py` 的度量口径是
「今天动过的 **PMO 留底件**」 × 「今天入库的条目」，
而它自带一份**逐个点名**的豁免清单（设计意图正当：「留底件被动过 ≠ 必须入库」，
索引/台账/规程那三类不该逼人入库）：

```python
#: 不要求入库的（索引/台账/规程这一类的落点）—— 逐个点名，不用模糊匹配
'已修问题索引.md',
'守衡-回复卡片模版与语域规程.md',
```

⇒ 一次**只动了索引与规程、根本没有留底件**的修复，**两个集合里都不出现** ⇒ 读数恒绿。
而 FIX-037/038 恰好就是这个形状：产物 ＝ git 提交 ＋ 两行 JSONL ＋ 索引，
**没有留底件**。

> ★ 更根本的一层：那把尺子量的是「**留底件**有没有被条目指向」——
> 它默认「有改动就会有留底件」。而这条默认**不成立**。
> 一句话：**度量口径漏了一整类产物，读数就会在那一类上恒绿**（本项目的老病，换个地方长出来）。

## 二、修法：把「该不该进库」挂到**记录本身**上

按 Owner 批准，`PMO/已修问题.jsonl` 每条新增 **`ingest_ref`**，`verify_fixed.py` 加 **A7**：

| 取值 | 判据 |
|---|---|
| 字符串 ＝ 知识库条目 id | 必须**真的解析得到**（`~/.dsh/Momcozy知识库/kb/view` 下按文件名**全库递归**找，**不写死子库名**）；视图在本机找不到 ⇒ 记**未测**，不判红（同 FIX-035 的三态纪律） |
| `{"not_needed": "<理由>"}` | 理由**非空**即可 —— 多数纯工程修复属这一档，但**理由要写出来** |
| **没写** | `FIX-037` 起**判红**（不许不表态）；更早的记**未测**（那条规矩上线前落的，不是坏） |

**反向对照 C3（成对·四半）**——缺一半就证明不了「未测」不是后门：

1. 指向**真的**条目 ⇒ 不报红；
2. 指向**不存在的**条目 ⇒ **必红**；
3. 生效起点**之后不表态** ⇒ **必红**；
4. 生效起点**之前不表态** ⇒ 记**未测**、**不判红**。

> 变异自证：把「核条目在不在」那一行拆掉 ⇒ C3 **精确报出**「② 指向不存在的条目竟然没报红」；还原后 13/0。
> 另：反向对照的假记录 `good[0]` 也**必须**带上 `ingest_ref` —— 否则 A7 会把它记进「未测」，
> 而 C2 的 ③ 断言「`p3` 与 `u3` 都为空」当场变红（实测就是这么发现必须补那一行的）。

## 三、同一天连着发现的第二件：**长驻进程里是旧代码**

修完不等于生效。当天实测：

| 路径 | 进程 | 启动 | 代码 |
|---|---|---|---|
| 交互（@守衡） | `ws_daemon` pid 64874 | **11:11:14** | ✅ 已带修复（模块 mtime 11:09:36 **早于**启动） |
| 批跑 | `batch_review_runner` pid 41257 / 41513 | **10:52:29 / 10:52:41** | ❌ **旧代码**（早于 11:09 的改动） |

**证据**：台账第 **1306 行**（**11:18:55**，即守衡重启**之后**）照样是「（未填）⤶读数段」——
因为它出自那两个 10:52 起的旧进程。**node 在启动时锁定模块，改文件不会热更新。**

处置：杀掉两个重复进程（第二个启动脚本自带守卫 `pgrep -f batch_review_runner && echo "已有别的批跑器在跑，先不动"`，
但两个只差 12 秒 ⇒ **守卫有竞态没拦住**），**只起一个**（pid 88454，11:30:56）。
它自带跳过逻辑（`!(st.items[...] ?? {}).answered_at`）⇒ 已答的 29 行自动跳过、**本轮只跑 16 条**，不会重发已发的卡。

> ★ 重启时**不要传全量清单然后祈祷它幂等**：先读那段 `todo` 的过滤条件，确认它会跳过，再起。

## 四、同一天连着发现的第三件：同一个坏形状**只在一条路径上出现**

| 路径 | 评审结论卡 | 含「（未填）」 |
|---|---|---|
| 交互（@守衡） | 133 张 | **0 张** |
| 批跑 | 357 张 | **16 张** |

⇒ **@守衡 验不到这个形状**：交互路径的卡是 **41–43 字**的短卡（§5.3 标准形），
根本没有 `fields` 那一块；而批跑路径（无真人对话）模型会把整段机器答案倾倒进 `fields`。
**「去哪儿验证」本身要先量清楚** —— 否则会拿一条不出该形状的路径去证「修好了」。

★ 同一处还留了个**潜伏缝**（当时未堵）：`ws_daemon.mjs:500` 那条交互调用传了 `verdict53`
却**没传 `machineAnswer`** ⇒ 万一模型哪天在交互路径上也吐 `fields`，读数会照样漏。
要堵它得先改 `verify_cards` 的 `J13a3e2`（它现在钉着「没声明就不许动」）——那是**口径决定**，不是 bug 修复。
