# 守衡 · 全链验收与两处缺陷（2026-10-05）

> **这是什么**：委托方说「开始做」之后，拿事故那张图走了一遍**生产路径的全链验收**
> （`kb_review_chain` → DSH headless 在知识库工作区跑 L4→L5→L6→L7 + 评审链 → 落报告 → 写飞书）。
> 结果：**链路是通的，但它同时暴露了两处真缺陷** —— 一处写在委托方的表里（假 PASS），
> 一处藏在守衡自己的写通道里（留痕/回读/快照从未真正跑通）。
> 两处都已处置，两处都装了判据。

## 一、验收怎么跑的（不是打桩）

| 项 | 值 |
|---|---|

| content hash | `2c6c40ad5bdc0e450e0d0b3d9f47daef28659bc70cbb56f672366edd63d8630a`（**实测 = 上述 text 的 sha256**） |

| 报告 | `kb/l7/reports/RT-20261005-IMG-01.review.md`（11.8KB） |
| 层前置 | `RT-20261005-IMG-01`，四层各一个 subagent、真加载本层 skill；四条审计红 0 |

**结论：`NEEDS_INPUT`（引擎 fail-closed 拒答，退出码 3）**，`published=false / reason=no_conclusion`。
两条理由（链自己写的）：① 供给链新鲜度前置未通过；② 送来的只有图上文字层，**图片本体从未到达**。

> ★ 报告里有一句必须原样记住的读数：四层虽然红 0，但 **L4/L5/L6 的绿建立在预演台账上**
> （`dry_run=true` / `applied=false`）—— 只能读成「逐层调用机制通了」，
> **不能**读成「这些层真落盘过」。`🟡E5 ×3` 就是这个意思。

| 写入时间 | 2026-10-05 07:42:26（表内 29 → **30** 条） |

**归因（三条独立证据，缺一条都不算钉死）**：

1. 发布件里的 `content_version` == 我送审 text 的 sha256（逐字对上）；
2. 层前置 BASE == 我这次跑的 `RT-20261005-IMG-01`；
3. **守衡侧没有发过任何话** —— `PMO/logs/ws_outbound.jsonl` 最后一条仍是 06:37 那句「正文我读不了」，
   入站事件日志也没有新消息。⇒ 这条不是守衡写的，是**知识库那条链自己**写的。

**根因（链自己定位到代码行）**：适配器 `kb/l7/review-engine/core/with_kb_evidence.py` 的
fail-closed 守卫比的是哨兵值 `NEEDS_INPUT`，而 `review.py` 在「覆盖信号不足」这条路上给的是
**中文 `"拒答"`** → 守卫不触发 → 空 `findings` 喂给 `decide()` → **一次拒答被静默读成零问题 → PASS**。
文件注释里声称已修的那个洞，**只修在另一个哨兵值上**。

配上 KB 自己 `confirmed_by_user` 的口径——

> *Do not emit PASS until a URL or file is actually readable and required modality coverage is complete.*

——这条 PASS 不成立。链的敏感性提示也写着：本单准确状态是「**证据不足以判**」。

## 四、顺带修掉的真缺陷：守衡写通道的 `batchGet` 六处调用点

**现象**：上面那次「标记复核结论」第一次**被工具自己挡住了** ——
`snapshot_failed：改之前读不到这些记录的旧值（field validation failed）—— 没搬走旧值就不改，已中止`。

**根因（实测，不是推断）**：`appTableRecord.batchGet` 的 `record_ids` 必须放在 **body（`data`）** 里，
放到 query（`params`）里飞书回：

```
code = 99992402 · field validation failed
field_violations = [{"field":"record_ids","description":"record_ids is required"}]
log_id = 20261005082040C23AF9EB8F20344668AC
```

而 `lark_write.mjs` 里 **6 处**全写成了 `params`：`updateRecords` 的快照与回读、
`createRecords` 的回读、`deleteRecords` 的提议读 + 删除前快照 + 回读。
⇒ **「留痕 / 回读 / 删除前快照」这三条纪律从未真正跑通过**；只是它们全是 fail-closed，
所以没有破坏过任何数据，只是「改记录」这条路一直走不通。

**为什么自证一直是绿的（这一条比 bug 本身更该记）**：
`lark_write.test.mjs` 用的是**假客户端**，而假客户端**不校验调用形状**；
更糟的是，**两个测试桩里也写着 `args?.params?.record_ids`** ——
**代码与假接口共享了同一个错信念**，于是两边永远自洽。
这就是 §2.4.1 那句话换了个地方长出来：**假接口比真接口松，假数据就是真数据的形状。**

**修法两层（缺一层都还会再来一次）**：

| 层 | 做了什么 |
|---|---|
| 代码 | 6 处 `params: { record_ids }` → `data: { record_ids }`，并在 `lark_write.mjs` 里留下实测证据（错误码 + log_id），下一个人不用猜 |
| **判据** | `lark_write.test.mjs` 新增 `guardBatchGet()`：假客户端**在进打桩之前**按真接口契约校验，形状不对就直接回真接口那句错；另加 **3 条反向对照**（0a 放 params 必拒 / 0b 放 data 必放行 / 0c 空 ids 必拒） |

**读数**：修后 `node tools/agent/lark_write.test.mjs` → **44/44 全过**；
真机上那次写 → `ok=true`、**`readback="consistent"`（回读纪律第一次真正执行）**、留痕已落
`PMO/logs/lark_writes.jsonl`。

## 七、这一轮最值钱的一句

> **假接口的契约比真接口松，就等于没有接口。**
> 六处调用点、三条纪律、一个一直全绿的自证 —— 全都建立在「假客户端照单全收」之上；
> 而**两个测试桩里写的也是错的那个字段位置**，于是错误自洽了整整一个版本。
> 判据必须钉在**真接口的契约**上（错误码 + 字段名 + log_id 都是实测来的），
> 不能钉在「我们以为它长什么样」上。
