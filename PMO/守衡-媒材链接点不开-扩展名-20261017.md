# 媒材链接「点开无法查看」：文件没扩展名（修复 + 已存在的三条一起修好）

> Owner 原话，逐字：
> 「审查报告中的　送审内容：图片 1 张　／　图片 1：点开查看　——　**点击后无法查看，修复下**」
> 并追加：「**修复后落库，避免下次打不开**」。

---

## 一、真因（三步追到底，不是猜）

| 步 | 读数 | 说明 |
|---|---|---|
| ① 文件本身是好的吗 | `drive +download` 下回来 **83,421 字节**，魔数 `ff d8 ff e0 … JFIF` | **是一条完好的 JPEG**。字节没问题。 |
| ② 权限设对了吗 | `permission_public.link_share_entity = tenant_readable`，协作者里有 bot + 两个 openid | **权限也没问题**。 |
| ③ 那为什么打不开 | `drive +preview --list-only` 回 **`1060006 file type does not support preview`** | 飞书按**文件名扩展名**判类型；这个文件叫 `守衡送审素材-image-1`，**没有扩展名** ⇒ 当成未知二进制 ⇒ 点开就是个死页。 |

**决定性验证**：把同一个 token **只改名**成 `守衡送审素材-图片-1.jpg`（不加扩展名之外一个字），
再 `+preview` ⇒ **立刻通过**。token 不变 ⇒ 已经发出去的链接（群卡片、报告、表里那一格）**全都照样可用**。

**根因链**：
`feishu.fetchMessageImage` 故意把字节存成 `.img`（不让它在临时目录里伪装成图片，是那条窄豁免的边界）→
`media_link.collectMediaLinks` 造名字时只用 `守衡送审素材-${kind}-${index}`，**没有带扩展名** →
上传后飞书不认识类型。**中间没有一处是"错"的，错在没人负责给名字加扩展名。**

---

## 二、修法

1. **`media_link.mjs` 新增 `magicExt(path)`**：只读前 16 字节魔数认类型 ——
   `jpg / png / gif / webp / bmp / heic / mp4`；**认不出就返回空**（宁可看见「没扩展名」，也不编一个假后缀）。
2. **新增 `withMagicExt(name, path)`**：名字**没有**扩展名时按魔数补；**已经有扩展名的一个字不动**。
3. 上传那一跳改成 `--name withMagicExt(name, f)` —— 一个入口，所有调用方都受益。
4. 文件名标签顺手改成中文：`守衡送审素材-图片-1.jpg` / `守衡送审素材-视频-1.mp4`
   （这串名字是**用户在云空间里看到的**，`image`/`video` 对业务侧没有意义）。
5. **已存在的三条一起修好**（`PMO/_rerender-20261017/media-repair-20261017.json`）：

| token | 改名前 | 改名后 | preview | link_share_entity |
|---|---|---|---|---|
| `B8w1b56…` | 守衡送审素材-image-1 | 守衡送审素材-图片-1.jpg | ✅ ok | tenant_readable |
| `Ghw3brk…` | 守衡送审素材-image-1 | 守衡送审素材-图片-1.jpg | ✅ ok | tenant_readable |
| `VOcQboB…` | 守衡送审素材-image-1 | 守衡送审素材-图片-1.jpg | ✅ ok | tenant_readable |

> 中间那条 `B8w1b56…` 第一次回读报 `1060007`，**再查一次就是 ok** ——
> 那是「预览还在生成」的瞬时态，不是坏链。记在这里，免得下次有人把它当成第二种故障。

## 三、判据

`media_link.test.mjs` 新增 M6a–M6d 四条（**43/43 通过**）：

| 判据 | 盯什么 |
|---|---|
| M6a | 魔数认得出 jpg / png / mp4 |
| M6b | **认不出就返回空**，`withMagicExt` 也不加（不编假后缀） |
| M6c | 没扩展名 ⇒ 补；**已有扩展名 ⇒ 一个字不动**（反向对照） |
| M6d | **真传到 CLI 的 `--name` 必须带扩展名** —— 拆掉修法就精确变红 |

其余读数：`test_agent` 268/0｜`dual_track --selftest` 126/0｜`verify_cards` 347/0。

---

## 四、边界

1. **这是「名字」的缺陷，不是「权限」或「字节」的缺陷。** 上一版把 fail-closed 全押在
   「回读 `link_share_entity === tenant_readable`」上 —— 那个读数一直是绿的，**而链接一直是死链**。
   ⇒ 教训：**「能打开」= 权限对 ＋ 类型认得出**，两条都要有判据；只量其中一条，另一条坏了也全绿。
2. **video 那一档只补 `.mp4`/源文件名带的扩展名**，没做「截帧另存预览图」这一类增强。
3. **旧文件只改名、不重传**：重传会得到新 token，已发出的卡片/报告里的旧链接照样死链。
4. 如果将来素材是**飞书不认识的格式**（例如某些私有编码的 mp4），名字对了也仍可能预览不了 ——
   那种情况只能照实说「下载可以、预览不行」，**这条没做**（目前没有这种素材的实例）。
