## 一、病灶：空正文那一支**要求「这一轮用过工具」**

`agent.mjs` 里处置「空正文」的分支（2026-09-30 加的）条件是
`empty && cut.cut && toolTrace.length` —— 它假定额度是被**工具返回体**撑爆的，
所以处置是「折叠工具结果、关掉工具重写一次」。

而这次的形状是**这一轮压根没调工具**（`toolTrace` 为空）⇒ 那一支**不触发** ⇒
落到下面通用的「截断」分支 ⇒ 通用分支只做一件事：**附一句截断说明**
⇒ **那句说明自己成了回答**：群里收到的是一条通篇只有说明、没有一个字答案的消息。

判据层面的教训与 §2.4.7 同形：**那一支的条件写得比故障的形状窄**，
于是没被它覆盖的那一种照样出事，而日志读起来像"已经处置过了"。

## 二、修法（两半，缺一半都不算修好）

| 半 | 落在哪 |
|---|---|
| **重写一次**：空正文 ＋ 额度耗尽 ＋ **没调工具** ⇒ `llm.chat(messages, { thinking: { type: 'disabled' } })` —— 额度是被**推理**吃光的，关掉思考才会有正文的位置 | `agent.mjs`（新分支）；`thinking` 透传在 `llm.mjs` |
| **兜底**：重写仍写不出正文 ⇒ 落 `fallbackReply()`，并把这一轮标成 `truncated`；**空正文永远不许只带一句说明出门**（通用分支里另加一道 `if (!reply)` 的闸） | 同处 |

★ 两条**刻意保留**的语义：① 有工具那一支**不动**（它是另一个故障形状，处置手段不同 —— 那边有东西可折叠）；
② 重写那一次**不带重试循环**：它只试一次，失败就兜底 —— 免得把一次故障变成一串调用。

## 三、判据（`tools/test_agent.mjs` 第 18d 组，2 条，含反向对照）

真起一个**假 LLM 端点**（http server，`SHOUHENG_LLM_BASE_URL` 指过去）真跑一遍 `handleMessage`：

1. 正向：内核第一次回「正文 0 字 ＋ `finish_reason=length` ＋ reasoning 12000 tok」
   ⇒ 断言 ① 回复非空、且**不是那句截断说明**；② 内核被调 **2** 次（重写真发生了）；
   ③ **重写那次带着 `thinking:{type:'disabled'}`**；④ **第一次不带**（否则第 ③ 条恒真）。
2. 反向对照：内核第一次就给出正文 ⇒ 只调 **1** 次、正文原样。

实测 **249 通过 / 0 失败**。

### 写这两条判据时我自己连错两版，比 bug 本身更值得记

- **第一版：假端点跑在父进程里，而子进程用 `spawnSync` 起。**
  `spawnSync` **阻塞父进程的事件循环** ⇒ 端点一个请求都答不了 ⇒ 子进程的请求连得上、
  永远等不到回应 ⇒ 表现是「**0 次请求 ＋ 被超时杀掉**」，而报错看着像**内核挂住了**
  （指向完全无关的方向）。改法：异步 `spawn` ＋ await close（事件循环空着，端点才答得上话），
  并加一条看门狗超时 —— 真挂住时是**红**，不是把整个自证拖死。
- **第二版：按「第几次请求」发响应 —— 判据是假绿的。**
  这条消息在内核回话**之前**已经有一次模型调用（**模型侧**，`max_tokens=8000`、无工具），
  于是「空正文 ＋ length」被喂给了模型侧，内核那次反倒直接拿到正文 ⇒
  **前两条断言蒙对了**，只有「重写带没带关思考」把它揭穿（实测 `thinking=undefined`）。
  改法：判据**按角色识别**（`messages[0].content` 含「你是「守衡」」的那次才是内核），
  与调用顺序解耦。
- **一句话**：一条断言在错误的对象上通过，和一条没有断言，在报告里长得一模一样。

## 四、这一跑还验证了「不写飞书」怎么证

Owner 这次的指令是「不用写飞书，把结果私聊发我」——而现成的
`re_review_reply.mjs --dry-run` **只挡发群消息，照样建云文档、照样落表**（已知缺陷）。本次的拦法：

- 表格：注入一个**读放行、写抛错**的客户端（`lark_write.__injectClient`，那是现成的测试缝）；
- 建文档 / 上传媒材 / 改权限：`SHOUHENG_LARK_CLI` 换成**拒写的替身脚本**；
- 状态目录、外发台账、写入台账全部指到临时目录。

**飞书没被动这件事是用回读证的**：真台账 `PMO/logs/lark_writes.jsonl` 在那一跑前后
**12 分钟内 0 行**，且日志里明写「合并报告**没建成**（照实说，不编链接）」。
★ 不能拿"拦截计数"当证据：我那个替身代理自己有个 bug（对象分支里引用了越界的 `name`），
落表失败报的是 `name is not defined` —— **是我的锅，不是链路的问题**，
而它恰好让"拦截计数 = 0"这条证据失去意义。**判据要选那个不会被自己的 bug 污染的。**
