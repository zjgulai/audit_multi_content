## 一、它回答什么问题

**「我们这些天在 DSH 里做过的判断，哪些是对的、哪些是错的、哪些其实是库不够用 —— 有没有办法自动收进知识库，并让评审链的 skill 照着长？」**

一台机器跑六段：

```
DSH 会话（~/.dsh/sessions/**/session.jsonl.zstd）
  │
  ├─S1 抽取──── 解 zstd → 只留人话（source.kind=user）+ 系统产出 → 会话台账
  ├─S2 案例化── 按人话切段 → 案例单元（诉求 + 产出 + 紧跟的那句人话）
  ├─S3 判定──── 三源指针 → 正例 / 反例 / 缺口·引擎拒答 / 待人工复核 / 冲突
  ├─S4 归位──── 按供给链 L0–L7 各自的记录形状出**入库候选**
  ├─S5 蒸馏──── 三重验证 → 每 skill 的「可执行 / 禁止 / 风险」Schema 卡片
  └─S6 补丁──── 逐 skill unified diff + §2.8 口径的影响面报告
```

## 二、怎么重跑

```bash
bash tools/session_distill/run_all.sh                 # 预演（一个字节都不落盘）
bash tools/session_distill/run_all.sh --apply         # 真写
bash tools/session_distill/run_all.sh --apply --since 2026-10-01   # 换起点
```

`run_all.sh` 先跑**六段自证**再跑数据 —— 判据坏了跑出来的数没有意义。
退出码：`0` 无红无未测 ｜ `1` 有红 ｜ `2` **0 红但有未测**（未测 ≠ 通过 ≠ 红）。

单独跑某一段：

```bash
python3 tools/session_distill/s3_judge.py --selftest    # 只验判据
python3 tools/session_distill/s3_judge.py --apply       # 只跑这一段
python3 tools/session_distill/s7_verify.py --rerun      # 全链守恒 + 幂等
```

## 三、幂等与水位线

| 项 | 落点 |
|---|---|
| 水位线 | `_evidence/watermark.json` —— 记 `session_id@sha256` |
| 幂等键 | `(session_id, sha256(源文件字节))` |
| 增量语义 | 会话是**活日志**，会随对话继续增长 ⇒ **sha 变了就重抽，没变就跳过** |

**幂等的真判据（F1/F2）**，不是「未变数 == 台账数」：

1. `重抽·源未变 == 0` —— 源没变的会话**一条都不许重抽**；
2. `入选 == 新会话 + 源变了的重抽` —— 没有第三项。

> ★ 第一版写的是「未变 == 台账数」，而那条**恒不可能为真**：跑一次 S1 的二十秒里，
> 就有 8 条会话在别的窗口里长出了新内容。**恒假的断言比没有断言更糟** ——
> 它会让人开始不看报告。改成上面两条之后，它既能被证伪，也确实在正常工作。

## 四、「正误」只认三源（模型不单独定正误）

| 源 | 落在哪 | 本轮用到 |
|---|---|---|
| **① 人的原话** | 会话内**下一句人话**里的纠正/确认措辞 → 指针 `session_id:seq` | 203 处 |
| **② 链自己的红** | 层闸门红 / 审计红 / 退出码 4·5 / 退 1 | 25 处（真红） |
| **② 链自己的红 · 补** | **自认错误** —— 证据在**我的回应**里（§4.3） | 171 处（强 113 / 弱 58） |
| **③ 库里已有裁定** | `regression-set.yaml` 的 80 条 solid（带 `expected` 三态）+ `sample_cases.jsonl` 的 946 条 | 44 处 |

**判定规则写死在代码里**：反例指针 > 正例指针；两类都有 = `冲突·待人工复核`；
一类都没有 = `待人工复核`。**「没有指针」永远不等于「正确」。**

### 4.1 三个必须分开的信号（混起来方向就反了）

| 信号 | 是什么 | 算不算「错」 |
|---|---|---|
| `NEEDS_INPUT` / `coverage_not_covered` / `覆盖缺口` | **拒答** —— 引擎说「我判不了」 | ❌ 不算。库自己的口径：「这不是素材有问题，是库对该题材没有可依据的条款」 |
| `库忙` / `认领被占` / 退出码 3 | **并发繁忙** | ❌ 不算。`kb/l8/review_run.sh:28` 原文：「3=认领被占（库忙 —— **不是**闸门红）」 |
| `闸门红 N` / `退出码 4·5` | **真红** | ✅ 算 |

> ★ 这三个**最初全被我的正则当成了「红」**，于是 1736 条里报出 1119 处「红」（真红只有 25 处），
> 整份分布整体反向。改判据前先看分布 —— **一行正则的极性错一次，结论就全错**。

### 4.2 措辞是**代理**，所以有两道护栏

- **否定护栏**：「不可以」不许被读成「可以」；
- **疑问护栏**：「视频为什么**不适用**？」「我还**可以**去验证了**吗**？」是提问，不是纠正/确认
  —— 护栏落在**小句**上，因为中文靠标点分提问与结论，不靠措辞分。

且确认分**强弱**：`没问题/对的/通过了` = 评价**产出**（强）；`同意/照这个` = 同意**方案**（弱）。
**弱确认只证明方向被接受，不证明产出正确** —— 本轮 178 条正例里 135 条是弱的。

### 4.3 第四条通道：**自认错误**（覆盖率抽查逼出来的）

抽样「链没给结论、人也没纠正」的案例时发现，里面藏着真纠正 —— 但**证据在我的回应里，
不在人的话里**：

```
人：「「80 条」不是 prd 的任务，不要理」
我：「我上一轮把它当成了知识库进度写进去了 —— 那是操作批次，不是这张表要跟的功能」
```

原来的判据只看**人话**，于是这一类（自认）**一条都收不到**。补上之后反例从 90 涨到 230。
★ 它是**我自己的声明**，不是外部裁定 ⇒ 一律标 `需人工确认`，且分强度：
强 113（「我上一轮说错了」）／弱 58（「你说得对」这类，可能是同意新提的点而非承认上一步错）。

### 4.4 「无判定对象」不是「待人工复核」

504 条被判成 `无判定对象·过程记录` —— 它们是**派活 / 提问 / 拍板 / 定位修复**，本来就没有
正误这回事。判据是机械的：**没有三态结论 + 没有任何指针 + 不是送审单**。

> ★ 一开始我把它们挂在「待人工复核」里，于是那个队列虚高到 921 条。
> **那是分类错，不是人工量问题** —— 让人替一个不存在的问题签字，比漏判更浪费。
> 单列之后：待人工复核 **921 → 307**。

## 六、边界（**说明它不做什么**）

1. **不写 `kb/l0…l7`** —— 沙箱外；且 `kb/l7/registry/write-gate.yaml` 里只有 `batch8/batch9` 两条凭据，
   两条都写明「只覆盖当轮、不自动续期」⇒ **本轮没有任何一条覆盖它的开闸凭据**。
2. **不改 `~/.dsh/skills/`** —— 补丁是**候选**（标准 unified diff），落盘是人的动作。
3. **不发号** —— `article_no` / `rule_code` 一律留空。发号是 L4 的动作，要人过闸。
4. **不替人拍板** —— `待人工复核` 保持原样，不为了让数字好看而清零。
5. **`productionReady` / `canonicalWrite` 恒 false**；E 级上限 = **E2（草稿级、可审查、未获批）**。
