### 为什么值得修（不只是把红变绿）

病是这个仓反复记的那个形状：**代码引用了 PRD 的某一节，而没有任何东西保证那一节的名字/口径还对得上。**
PRD **刚重拉过**（内容变了 6846 字节）⇒ **现在正是核对「代码引的那一节到底叫什么」的最佳时机**。
晚一点做，等代码又多几处引用，成本更高，而且中间任何一次 PRD 改版都会让旧引用悄悄过期。

### 怎么开工（建议顺序）

1. `python3 tools/verify_prd_baseline.py` 拿到完整 53 条清单（每条带 `文件 · §x.y`）
2. 读 `H3` 的实现，**先搞清登记表在哪、字段是什么**（别猜 —— 这个仓今天的教训全是「猜字段」）
3. 逐条核对：**代码里引的那个 `§x.y`，在刚重拉的 PRD 里是不是还叫那个名字**
   - 对得上 ⇒ 补登记
   - 对不上 ⇒ 那是**真缺陷**（引用的章节改名/挪位了），要改代码或改引用，**不许只补登记了事**
4. 复跑 `verify_prd_baseline.py` 复绿；`verify_depad.py` 复验

### 一条纪律

**别为了让脚本变绿而机械补 53 行。** 第 3 步的「对不上 ⇒ 真缺陷」是这件事的全部价值所在 ——
如果 53 条全对得上，那说明这个检查只是缺人补登记；**只要有一条对不上，那就是一个真 bug**，
而它此前被埋在 53 条噪音里没人看见。

### ★ 顺带修掉一个**扫描器自己的**缺陷（不是登记缺口）

`REF_RE` 对**写在 JS 正则字面量里**的转义写法读错了：

```js
// tools/agent/dual_track.mjs:564
/未达 3 条，不适用 PRD §5\.3\.3/.test(rdSmall.block)
```

`\.` 里的反斜杠把 `(?:\.\d+)*` 掐断，于是这处被读成 **`§5`（功能需求）** ——
不是「少登记一条」，而是**凭空多出一条仓库里根本没写过的引用**，逼着人给一个
不存在的节号补登记。那正是「为了变绿机械补一行」。

修法两处：`REF_RE` 允许 `\\?\.`；新增 `_norm_sec()` 把 `5\.3\.3` 归一成 `5.3.3`
（**归一必须放在捕获之后、当键之前**，否则同一个节号会因两种写法记成两个键，
「登记表里有、仓库里没有」和它的反面会同时红）。全仓只有这 **1 处**转义写法。

## 六、`obj_edit_time_bj` 与漂移告警（2026-10-12，委托方选定「两件一起做」）

### 起因：一次手工考古

上游 17:44:01 删掉正文里一个空行。守衡按规矩报了漂移，消息说
「请给我一分钟重拉一次基线并记新指纹」—— **但没说上游是什么时候改的**。
而「现在就拉，还是等它改完」正是读者唯一要判断的事。当时为答这个问题，只能：
翻 daemon 日志时间线（17:43:37 还绿、17:45:08 已变）**再加上**手工调一次
`drive/v1/metas/batch_query`，才拼出那个 90 秒的窗口。

### 顺带查出的第二个洞：一个「能解析但已过期」的读数没人管

`obj_edit_time_bj` 有指令（检查器自己第 593 行印着要更新它）、也有一条断言 `A6` ——
但 `A6` 只判「**可解析且落在合理区间**」（它治的是「秒 vs 毫秒读错」）。
**没有任何东西拿它跟上游比**，所以一个过期值照样通过。
后果实测：索引一直写着 `2026-09-24 19:10:54`，而正文当天已经改过两次 ——
其中一次是本文作者上午重拉时**自己跳过了这个字段**。

### 修法

| 落在哪 | 是什么 |
|---|---|
| `verify_prd_baseline.py` 的 `fetch_edit_time()` | 只读 `drive/v1/metas/batch_query` 取上游 `latest_modify_time`（**兼容秒/毫秒**：实测这个接口回的是秒，`1791798241` → 17:44:01） |
| **新断言 `A7`**（L3） | 索引的 `obj_edit_time_bj` 必须**等于**上游最后改动。与 `A6` **成对**：A6 判能否解析，A7 判是否同一个时刻 |
| 漂移块 | 印出 `上游最后改动 <北京时刻>（N 分钟前） · 改动人 <姓名>` |
| `prd_baseline.mjs` 的 `parseDrift()` | 把这一行**可选**捕获，进告警正文 |

### 三条纪律（都有断言，且都变异验证过会红）

1. **`at` 必须是可选捕获** —— 老版本检查器的输出没有那一行，若因此把整条漂移丢掉，
   「上游改版」这条告警会直接消失，比少一个字段严重得多。反向对照：不带那一行的输出
   **仍必须解析出漂移**，只是 `at` 为 null。
2. **取不到上游时刻 → 落「未测」**，与 `fetch_raw` 失败同一档待遇（不许当它过了）。
3. ★ **绝不往群里印 `open_id`** —— 那是内部标识，业务同事看不懂，与「库内命中（读数）」
   那类原始倾倒同一个病。姓名**只在要印的时候才解析**（`name_of()`，仅漂移时调用，
   不让日常检查多两次网络调用）；**解析不到就整个不印**，不退而印一个看不懂的字符串。
   实测解析出「陈紫璇」。
